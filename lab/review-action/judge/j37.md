# REVIEW A

**Review of PR #23017: Preserve inline comments when updating an existing dependency group**

The PR is already merged. I read the diff only and didn't build it or run the tests.

**Summary:** `uv add --dev` on an inline `dependency-groups` table used to call `fmt()` on the outer table every time. That wiped the comments around the keys. Now the sort and `fmt()` only run when a new group key is inserted. The fix is small, targeted and correct for the stated case.

**Code quality**
- The `new_group` flag in `add_dependency_group` is clear. The new comment explains why formatting is skipped, which is the right kind of comment.
- The second function (the group-creation path) now returns early if the group exists. That is cleaner than the old nested `if !group_exists`. It also drops the stale comment saying "Reformatting can drop comments", which is fine.
- AGENTS.md prefers let chains over nested `if let`. In the first hunk, `if new_group { ... if let Some(..) = ... }` could be `if new_group && let Some(..)`. But the sort sits in the same block, so nesting is reasonable.

**Potential issues**
- **Ugly output in the test snapshot:**
  ```
  dev = [
  "ok==1.0.0",
  ], # Local development
  ```
  The array is multi-line, but its items and closing bracket aren't indented, because the outer table is no longer reformatted. Comments are preserved, but the result is awkward. It's valid TOML and is arguably better than losing the comments. Still, it locks in unpolished formatting as expected behavior. A follow-up could format only the modified array, or set its decor and indentation explicitly.
- The old `fmt()` also normalized spacing around keys. After this change, a hand-written but oddly spaced inline table stays as it was, and only newly inserted keys get normal spacing. That is probably the intent, but it is a behavior change.
- The early `return Ok(())` in the group-creation function skips the code after the `fmt()` block. I only saw the diff hunk, so please confirm nothing else in that function needed to run for existing groups.

**Performance and security:** No concerns. The change only removes work from the existing-group path.

**Test coverage**
- The new test, `add_dev_preserves_inline_group_comments`, covers the main regression with both a trailing and a leading comment. It follows the style of nearby tests: `uv_snapshot!` plus an inline `assert_snapshot!` of the file.
- It is reasonable that `uv_snapshot!` uses `--frozen` with an empty-output snapshot.
- There is no test for the unchanged new-group path, such as adding `--group foo` to an inline table that has comments. Existing tests probably cover sorting and formatting for new groups, but I didn't check.
- There is no test for the second function, the one that creates an empty group, for example `uv init` or `uv add --group` with no dependencies. Its changed code path (early return) isn't exercised by the new test.
- I didn't check whether the test needs a `#[cfg(feature = "test-...")]` gate. Its `ok==1.0.0` dependency with `--frozen` suggests it doesn't need network access, but confirm this per AGENTS.md.

**Verdict:** The change is good and the logic is correct. The main follow-up is the unindented array formatting in the output. I'd also add a test that an existing group is left untouched when the group-creation function runs.

# REVIEW B

**Review of PR 23017: Preserve inline comments when updating an existing dependency group**

I read the diff only. I did not build the PR or run its tests. It is already merged.

**What it does**
- In `add_dependency_group`, the sort and `fmt()` of the inline `dependency-groups` table now run only when a new group key is inserted. They are skipped when a dependency is added to an existing group.
- The second function, which looks like `ensure_dependency_group` (the diff doesn't show its name), now returns early if the group exists. This removes the `group_exists` flag and some nesting. It is a behavior-preserving cleanup.

**Correctness**
- The logic is sound. Sorting and formatting only matter when the key set changes, and the early return in the second function does the same job.
- If the group exists, `existing_group` is `Some`. In that case `new_group` is false, so the `was_sorted` check is correctly skipped.
- Skipping `fmt()` leaves the array's own decor to whatever `add_dependency` produces. That is why the snapshot shows the odd layout below. If `add_dependency` doesn't normalize inline arrays, this is the main risk.

```toml
dev = [
"ok==1.0.0",
], # Local development
```

   - A follow-up could re-indent only the edited array (for example, by setting the array's decor and per-element prefixes) so the output stays tidy.
   - At minimum, say in the PR that the odd indentation is a known tradeoff.
