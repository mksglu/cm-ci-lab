# REVIEW A

## Review of PR #100935: store `ChunkGroupInfo::chunk_groups` as a `Vec`

This PR is already merged. I reviewed it from the diff alone and did not check out the code or run the tests.

**Summary:** `ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. `IndexSet` compares as a set, so a recomputation that only renumbered the chunk groups compared equal. Turbo-tasks cell updates treat equal values as unchanged and keep the old value. In that case `chunk_groups` would keep the old order. Meanwhile `module_chunk_groups` (the bitsets) and `chunk_group_indices` would take the new numbering. Modules could then map to another entry's chunk groups. `Vec` equality is order-sensitive, so the new value now replaces the old one.

### Correctness
- The diagnosis is sound and the fix is minimal. Positional data in `module_chunk_groups` is now stored together with a container that compares positionally.
- Only call sites that used `get_index` changed (`module_batches.rs` and the test helper), now using `get`. Other uses of `.len()`, `.iter()` and indexing should work unchanged on `Vec`.
- `Vec` drops the uniqueness guarantee of `IndexSet`. This is fine if the construction site collects from an already-deduplicated structure, which I couldn't see in the diff. A short comment or `debug_assert` at the construction site would document that.
- The `#[bincode(with = "turbo_bincode::indexset")]` attribute is correctly removed, since `Vec` has native bincode support.

### Remaining risk (the author mentions this)
- `chunk_group_keys: FxIndexSet<ChunkGroupKey>` stays as an `IndexSet`. It is marked `unsafe_ignore`, so it doesn't take part in equality, but the same stale-order problem could arise if any query reads it by index. The author says they are looking at other places with this risk. That is worth tracking as a follow-up.
- `ModuleToChunkGroups` and the other index-dependent structures should be audited for the same set-vs-order issue.

### Performance
- Positive or neutral. `Vec` equality and cloning are cheaper than `IndexSet`, which has to hash. No hot-path lookups by value appear to be lost, because the code accesses entries by index.
- Equality now compares element by element. A reordering produces a new value, which can invalidate downstream tasks that previously stayed cached. That is the correct behavior.

### Tests
- `test_chunk_group_info_reordered_entries` is a good regression test. It builds the same graph with entries `[page1, page2]` and then `[page2, page1]`, flipping a `State<bool>`. It asserts that `get_chunk_groups_for_module` still returns the right groups for each module after the incremental recompute. It would fail on the old `IndexSet` implementation.
- This follows the repository's guidance to prefer behavioral tests over tests of the implementation.
- Minor: the `"other"` fallback in the `kind` match could hide new `ChunkGroup` variants. That is acceptable for a test with only entry and async groups.
- Minor: `read_strongly_consistent` after `State::set` correctly exercises the re-execution path.

### Security and style
- No security concerns.
- The doc comment on the field explains the "why" well.
- The code follows Rust conventions. I would run `cargo fmt` and clippy as usual, and CI presumably did.

**Verdict:** LGTM. It is a small, well-motivated fix with a targeted regression test. The suggestions are to document the uniqueness invariant at the construction site and to follow up on the other index-dependent structures.

# REVIEW B

## Review of PR #100935: store `ChunkGroupInfo::chunk_groups` as a `Vec`

The PR is already merged, with approvals from mischnic and sokra. I read the diff and spot-checked the usage sites. I did not build it or run the tests.

### Summary
`ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. The reason is correct. `IndexSet` equality ignores order. If the graph entries are reordered, the chunk groups are the same set under a different numbering. The new `ChunkGroupInfo` then compares equal to the old one, and turbo-tasks keeps the old cell contents. The old cell would still have the old order. Meanwhile `module_chunk_groups` (bitsets) and `chunk_group_indices` would use the new numbering. Modules would end up mapped to the wrong chunk groups. `Vec` equality is order-sensitive, so the cell updates.

### Code quality
- The doc comment on the field explains the invariant and the failure mode. This is the kind of comment that stops someone from changing it back to an `IndexSet` later.
- The `get_index(i)` calls in `module_batches.rs` and the test helper became `.get(i)`. These are the only API changes needed, and they are correct. Indexing sites such as `self.chunk_groups[index as usize]` work on both types.
- The `#[bincode(with = "turbo_bincode::indexset")]` attribute was removed. Vec's default serialization is fine. The persisted cache format changes, but that should be handled by the normal cache versioning.

### Potential issues
1. **Lost dedup guarantee.** `IndexSet::insert` deduplicated and returned the index. I only saw the diff and a grep, so I could not confirm that the construction site never pushes the same group twice. Construction goes through `chunk_group_keys` (still an `IndexSet`), which gives each key a unique index. That suggests uniqueness is still enforced by the key set. A `debug_assert` that `chunk_groups.len() == chunk_group_keys.len()` would document it.
2. **`chunk_group_keys` is marked `unsafe_ignore`.** It is excluded from equality but still depends on ordering. This is probably fine, because any key reordering also changes `chunk_groups` or the bitsets. The author says they are still looking for similar risks elsewhere. Other `IndexSet`/`IndexMap` fields in cell values that are indexed positionally are worth auditing for the same bug.
3. **Linear lookups.** If any caller used `get_index_of(&group)` or `contains` on `chunk_groups`, it would now be O(n). My grep found none, and the compiler would have flagged them, so this is fine.

### Performance
There is no real concern. A `Vec` is smaller and faster to build and iterate than an `IndexSet`, because it has no hash table. Equality is now a linear comparison. Previously it was a set comparison, which hashes. Neither should matter here.

### Security
Nothing relevant.

### Test coverage
- `test_chunk_group_info_reordered_entries` is a good regression test. It builds two entries, each with an async child, then swaps the entry order. It reads through `read_strongly_consistent` and asserts that `page1.js` and `lazy1.js` still resolve to their own chunk groups. This exercises the incremental-recompute path where the bug occurs.
- The test relies on `State` invalidation to force recomputation, which is what is needed.
- Suggestion: confirm the test fails on the pre-change code. The PR doesn't say whether this was checked. Since the previous commit (`4eae8876ff`) is titled "test ChunkGroupInfo after reordering graph entries", it likely was.
- Minor: the `_ => "other"` arm would hide new `ChunkGroup` variants. That is acceptable in a test.
- Per AGENTS.md, a Turbopack execution test is preferred for Turbopack features. A Rust unit test is reasonable here because the bug is internal to cell equality.

### Verdict
Correct, minimal, well documented and well tested. The only follow-up I would suggest is the audit of similar set-equality fields that the author already mentioned.
