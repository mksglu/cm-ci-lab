## Review of #100935: Turbopack: store `ChunkGroupInfo::chunk_groups` as a Vec

The PR is already merged, with approvals from mischnic and sokra. It's a small, correct fix for a real incremental-build bug, and it comes with a regression test. I found nothing blocking. The notes below are mostly follow-ups.

### Correctness
**The fix is right.** `FxIndexSet`'s `PartialEq` compares contents as a set and ignores order. `ChunkGroupInfo` is a `#[turbo_tasks::value]`, so its cell is compared before it is updated. When chunk groups only get renumbered:
- `chunk_groups` compared equal even though the order changed.
- `module_chunk_groups` and `chunk_group_indices` are `ResolvedVc`s to cells in the same task, so their IDs don't change.
- `chunking_heuristics` could also be unchanged, for example with defaults.

So the whole struct compared equal and the old cell stayed in place. Meanwhile the bitsets in `module_chunk_groups` and the `chunk_group_indices` cell picked up the new numbering. The result was modules mapping to another entry's chunk groups. That's a nasty bug that only appears in watch mode and is hard to diagnose. With a `Vec`, equality depends on order, so the mismatch can't happen any more.

**No call site loses anything.** I grepped every use of `chunk_groups` in `module_batches.rs`, `merged_modules.rs`, `style_groups_*`, `chunk_group_info.rs` and the tests. They all index, iterate or call `.len()`. None used `get_index_of` or `contains`, so the set semantics weren't doing anything beyond the (wrong) equality.

**No duplicates can appear.** The Vec is built from the `chunk_groups_map` keys, which are unique. Each key maps to exactly one `ChunkGroup`, so giving up set semantics doesn't make duplicate entries possible.

### Suggestions
1. **`chunk_group_keys` now depends on an unstated rule.** It is still an `FxIndexSet` marked `#[turbo_tasks(unsafe_ignore)]`. It's correct only because it comes from the same `chunk_groups_map` as `chunk_groups`, so any reordering of the keys also changes `chunk_groups` and makes the struct unequal. That's true today but nothing documents it. I'd add a comment on `chunk_group_keys` (or next to the new doc comment) saying it must stay in the same order as `chunk_groups`, because the equality check relies on `chunk_groups` to catch reordering.
2. **Look for the same bug in other cell values.** The description says you're already checking other places. Any `#[turbo_tasks::value]` that stores an `FxIndexSet` or `FxIndexMap` and whose positions are referenced elsewhere has the same risk, especially positions referenced from a sibling cell, as here, or from a bitset. It would help to track this in an issue, or to add a lint or wrapper type (such as an `OrderedIndexSet` whose `Eq` checks order) so it doesn't come back.
3. **Persistent-cache encoding changed.** Dropping `#[bincode(with = "turbo_bincode::indexset")]` changes how this field is encoded. I assume the persistent cache is versioned so old entries are thrown away. It's worth confirming that a cache written before this change can't be decoded with the new layout.

### Test coverage
`test_chunk_group_info_reordered_entries` is a good regression test. It builds the graph inside an `operation` task, flips a `State`, reads strongly consistent, and checks what `get_chunk_groups_for_module` returns, which is the behaviour users see. Following the equality logic above, it should fail on the old `IndexSet` version and pass with this change. I didn't run it either way. Minor notes:
- The `_ => "other"` arm can hide surprises. For this two-entry graph only `Entry` and `Async` should appear, so `unreachable!()` or the variant's debug name would make a regression fail more clearly.
- The test only checks `page1.js` and `lazy1.js`. Also checking `lazy2.js` would cover both directions of the swap at no real cost.
- `turbo_tasks::State` inside a test value appears nowhere else in `turbopack-core` tests. It's fine, but a one-line comment on why `State` is used (to invalidate the operation between the two reads) would help readers.

### Performance
No concern. A `Vec` uses less memory and is faster to index and compare than an `IndexSet`, and nothing needed hash lookups on this field. Comparing in order is O(n), the same as before.

### Security
Nothing relevant. This is internal build-graph state with no user input or headers involved.

**Verdict:** I'd approve it. Of the suggestions, the comment documenting the `chunk_group_keys` ordering rule is the one I'd do soon.

# Review: PR #100935, "Turbopack: store `ChunkGroupInfo::chunk_groups` as a Vec"

**Status:** already merged, approved by mischnic and sokra. These notes are follow-up suggestions.

## Summary
`ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. `IndexSet`'s `PartialEq` ignores order. So if a recomputation only renumbered the chunk groups (for example, after the graph entries were reordered), turbo-tasks treated the new cell value as equal to the old one and kept the old order. Meanwhile the separate `module_chunk_groups` bitsets and the keyed `chunk_group_indices` cell did update to the new numbering. Index-based lookups such as `get_chunk_groups_for_module` (`chunk_group_info.rs:114`) then returned another entry's chunk groups. With a `Vec`, equality depends on order, so the struct is correctly seen as changed.

The fix is correct and as small as it can be. The regression test reproduces the exact failure.

## Correctness
- **The core fix is sound.** `chunk_groups` is only ever indexed by position or iterated (`.get(idx)`, `[idx]`, `.iter().enumerate()`, `.len()`). Nothing calls `contains` or `get_index_of` on it, so the set semantics bought nothing.
- **No loss of deduplication.** The `Vec` is built from `chunk_groups_map.into_iter()` (`chunk_group_info.rs:968`), whose keys are already unique. Each `ChunkGroupKey` maps to exactly one `ChunkGroup`, so collecting into a `Vec` cannot introduce duplicates.
- **`chunk_group_keys` is still an `FxIndexSet` marked `#[turbo_tasks(unsafe_ignore)]`** (`chunk_group_info.rs:56-58`). It is also positional: `get_shared_merged_chunk_group` uses `get_index_of` to produce an index. This is safe now, but only indirectly. It comes from the same `chunk_groups_map` as `chunk_groups`, so whenever the now order-sensitive `chunk_groups` compares equal, `chunk_group_keys` has the same order too. That invariant isn't written down anywhere. A short comment on the `unsafe_ignore` would help, e.g. "safe to ignore for equality: derived 1:1 and in the same order as `chunk_groups`". Otherwise a future change that breaks the 1:1 mapping could bring the same bug back.
- **The nested indices are consistent.** `ChunkGroup::IsolatedMerged { parent: usize, .. }` and `SharedMerged { parent, .. }` refer to positions in this `Vec`, and `ChunkingHeuristicsInfo` (`Vec<Vec<u16>>` plus a `Bitset`) is indexed by chunk group too. All of these already compared in order, so the struct is now consistent from end to end.

## Test coverage
- `test_chunk_group_info_reordered_entries` is a good regression test. It uses a `State<bool>` to flip the entry order inside a single `TurboTasks` instance, which exercises the real cell-update path rather than a fresh computation. Without the fix, the second read would map `page1.js` to the `page2.js` entry group, so the test really does catch the bug.
- **Nit:** the test only reads `page1` and `lazy1`. Also checking `page2`/`lazy2` would cost almost nothing and would catch a partial misnumbering, e.g. if only the async groups got renumbered.
- **Nit:** the `_ => "other"` arm in the `kind` match quietly accepts unexpected variants. That's fine here because the expected strings would fail anyway, but naming the variant (e.g. with `{:?}`) would make failures easier to diagnose.
- **Placement:** the test lives in `module_graph/mod.rs` next to the other `ChunkGroupInfo` tests, which matches local convention. The test-only `EntryOrder` / `ChunkGroupDescriptions` types are scoped inside `mod tests`, which is good.

## Performance
- No meaningful impact. `Vec` equality is O(n), like `IndexSet` equality, and probably cheaper since it skips the hash lookups. Memory also drops a little because the hash index is gone.
- One behavioural change, which is intended: when the order changes, the `ChunkGroupInfo` cell now invalidates its dependents where it previously didn't. That is the correct behaviour, but it will cause more recomputation in watch mode when entries get reordered.

## Serialization / persistent cache
- Removing `#[bincode(with = "turbo_bincode::indexset")]` changes how this type is encoded on disk. If persistent-cache invalidation is keyed on the binary or crate version (as I believe it is), this is harmless. Worth confirming that an old on-disk cache can't be decoded into the new layout.

## Follow-ups (as the PR description mentions)
Other places where `IndexSet` equality might hide a reorder. I skimmed `turbopack-core`:
- `ChunkGroupContentInner.async_modules` / `collecting_modules` (`chunk/mod.rs:526-530`) are `FxIndexSet`, but the type is `cell = "new"`, so as far as I know it skips the equality check on update.
- `EntriesList` in `module_batches.rs:57` lives inside `ModuleBatchesGraph`, which is `eq = "manual"` and `cell = "new"`, so it's probably fine too.
- `OutputAssets`-style `FxIndexSet` wrappers (`output.rs:115`) deserve a look wherever consumers depend on iteration order (e.g. emitted chunk order).

A broader safeguard could make sense: a lint, a doc note, or a derive-level warning whenever a `#[turbo_tasks::value]` with default equality contains an `IndexSet`/`IndexMap` whose order is meaningful.

## Security
Nothing relevant: this is internal bundler data with no new inputs or headers.

## Verdict
👍 A correct, well-documented, well-tested fix. The main suggestion is a comment on `chunk_group_keys`'s `unsafe_ignore` stating the same-order invariant that keeps it safe. The others are minor test improvements.
