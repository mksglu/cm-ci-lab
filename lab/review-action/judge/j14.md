# REVIEW A

## Review of PR #36944 (merged): assert message functions and printf-style messages

Overall this is a clean change. Moving message handling into one shared `innerFail()` removes duplicated logic and brings `assert` closer to Node's behavior. I found some things to fix and some gaps.

### Issues

1. **Leftover commented-out code in `internalMatch`** (`assert.ts`). The diff comments out the old `ObjectPrototypeIsPrototypeOf(ErrorPrototype, message)` check, the old `generatedMessage` line, the `const err = new AssertionError({` line, and the old `err.generatedMessage` and `throw err` lines. These should be deleted. `ObjectPrototypeIsPrototypeOf` and `ErrorPrototype` may now be unused imports in `assert.ts`, which could trip lint. Please check.

2. **`internalMatch` mutates the caller's rest array.** `message[0] ||= ...` writes into the `message` array. That array is local to `match` and `doesNotMatch`, so it is safe today. It is still fragile.
   - `generatedMessage` is `message.length === 0`. If a user passes `match(s, re, "")` or `match(s, re, undefined)`, `message[0]` gets a generated string but `generatedMessage` is `false`. The old code used `!message`, which would have given `true`.
   - A non-falsy non-string value, such as a function or an Error, now goes to `innerFail` as intended. A falsy value of another type, such as `0`, is silently replaced by the default message. Node behaves differently here, so it's worth checking.

3. **`internalMatch` with a non-string `string`.** The default message there is a "must be of type string" text. This is the only path where `generatedMessage` is computed outside `innerFail`. It works, but the logic is split across two places. It would be cleaner to let `innerFail` or the caller own it.

4. **`innerOk` fall-through condition.** `args.length === 1 || args[1] == null` treats `assert(false, undefined, "x")` as a generated message and drops the trailing args. Node does the same (`message == null`), so this is probably fine.

5. **Behavior change in `innerFail` message handling.** Previously `message: undefined` meant a default message. Callers now pass `[]` or `[msg]`, so any caller outside this file that still passes a raw string will hit the `ERR_INVALID_ARG_TYPE` branch. Please check other users, for example `ext/node/polyfills/assert/strict.ts` and `internal/assert/*`. Since `innerFail` is newly exported, a quick grep for other callers would help.

6. **Error type check.** `isError(message[0])` is checked before `typeof === "function"`. That ordering is fine. The `ERR_AMBIGUOUS_ARGUMENT` text should be compared exactly with Node 26's. `test-assert.js` apparently passes, which suggests it matches.

7. **Minor typing.** `ArrayPrototypeSlice(args, 1) as MessageTuple` is an unchecked cast. It is acceptable because `innerFail` validates at runtime.

### Performance
Switching to rest parameters (`...message`) allocates an array on every call to `equal`, `strictEqual` and `deepStrictEqual`, including successful calls. That is small, but these are hot paths in test suites. Node avoids the allocation by only collecting args on failure. Using `arguments` or slicing lazily in the failure branch would avoid it. This is a minor point.

### Security
No concerns. User-supplied message functions are called inside `try/catch`, and their errors are swallowed as specified.

### Tests
- The only test change is un-ignoring `parallel/test-assert.js` in `tests/node_compat/config.jsonc`. That is a reasonable way to cover Node's own behavior.
- There is no Deno-specific spec or unit test for these cases:
  - `generatedMessage` on `match` with an empty or falsy message.
  - Trailing args after an Error or function.
  - A message function that throws or returns a non-string value.
  - printf formatting in `assert.ok`.

  Adding a small spec test would guard against regressions that the upstream test might not catch.

### Summary
The logic looks correct and matches Node. Please remove the commented-out code and check the `generatedMessage` edge cases in `internalMatch`. The remaining points are optional polish. I only read the diff and did not run the code or tests.

# REVIEW B

**Review of PR #36944: assert message functions and format arguments** (the PR is already merged, so these are follow-ups)

**Overall:** This is a good change. Moving message handling into `innerFail` removes duplicated logic. The tuple-based message representation is clear. Re-enabling `parallel/test-assert.js` in the node_compat config is the right kind of coverage.

**Issues and suggestions**

1. **Leftover commented-out code** in `internalMatch` (`ext/node/polyfills/assert.ts`, about lines 763–800). Several commented lines remain: the old `ObjectPrototypeIsPrototypeOf` throw, `const generatedMessage = !message`, `// message ||= ...`, `// const err = ...` and `// err.generatedMessage ...`. They should be deleted. `ObjectPrototypeIsPrototypeOf` and `ErrorPrototype` may now be unused in `assert.ts`, which would trip lint with unused-variable errors. Please run `tools/lint.js --js` to check.

2. **`internalMatch` mutates the caller's array.** `message[0] ||= ...` mutates the rest array. That's harmless here because it is freshly created. It has a subtle bug, though: if the user passes a falsy first argument (for example `""` or `0`) with extra arguments, `message[0]` is overwritten and the trailing arguments are then used as format args. Also, `generatedMessage = message.length === 0` is false when the user passes `""`, yet the message is generated. The old code used `!message`. Node's behaviour for `assert.match(s, re, "")` is worth comparing. Also check that a non-string first argument such as `0` or `false` hits the `ERR_INVALID_ARG_TYPE` path, as Node does, and isn't silently replaced.

3. **Possible `undefined`/`null` message regression.** The `equal`/`strictEqual` family now passes `...message` straight through. `assert.strictEqual(1, 2, undefined)` gives `message = [undefined]`. `innerFail` then throws `ERR_INVALID_ARG_TYPE`, whereas it formerly produced the default message. Node handles `undefined` as "no message". Please confirm this against upstream. Only `innerOk` handles `args[1] == null` explicitly. The same applies to `null`.

4. **Message functions that throw.** `innerFail` silently swallows exceptions from message functions (`catch {}`). The PR description says this matches Node, so that is fine, but a comment citing the Node behaviour would help.

5. **Error-object check order.** `typeof message[0] === "string"` runs before `isError`, which is fine. However, `isError` is Node's internal check and also accepts cross-realm errors. This is fine and arguably better than the previous `ObjectPrototypeIsPrototypeOf(ErrorPrototype, ...)`.

6. **Internal call sites wrapping messages in arrays** (`compareExceptionKey`, `expectsError`, `expectsNoError`). These pass `[message]`. In `compareExceptionKey`, `message` may be `undefined`, which gives `[undefined]` and an `ERR_INVALID_ARG_TYPE` throw. Check whether the callers can pass an undefined message there. Wrapping conditionally (`message === undefined ? [] : [message]`) would be safer. Also, a user-provided message containing `%s`/`%d` and passed through the internal single-element path is not formatted (length is 1), which is correct.

7. **`format(...new SafeArrayIterator(message))`.** This is fine for primordial safety. `ArrayPrototypeSlice(args, 1) as MessageTuple` uses a cast that hides type errors, but that is acceptable.

8. **Tests.** The only added coverage is the upstream Node compat test. That is reasonable for node compat work. A small spec or unit test would still help, covering `assert.ok(false, "x %s", "y")`, a message function, trailing arguments after an `Error` or function (`ERR_AMBIGUOUS_ARGUMENT`), and `undefined` as the message.

9. **Performance.** Every assertion call now allocates a rest array, even on the success path (`equal`, `strictEqual`, and so on). It is small, but these are hot paths in test suites. The cost is minor and acceptable.

**Security:** No concerns. Message functions run user code, but only user-supplied code.

**Process notes (CLAUDE.md):** The leftover comments suggest `tools/format.js` and `tools/lint.js --js` may not have been fully applied. Please verify.

**Verdict:** Approve, with follow-ups for items 1–3. Items 2 and 3 are the most likely sources of behavioural regressions.
