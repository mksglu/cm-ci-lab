# REVIEW A

I found no blocking problems, and the PR has already been merged. The changes are auto-generated profile data. They are worth a follow-up because several values look like they come from a fallback rule rather than real limits, and those values keep changing between refreshes.

## PR #41520 review: `chore(model-profiles): refresh model profile data`

**What it does:** a bot ran `langchain-profiles refresh`, which rewrote `_profiles.py` for HuggingFace and OpenRouter. It adds 3 models, removes 2 and changes 10 `max_output_tokens` values. No hand-written code changed.

### Code quality and conventions
- The title follows the repo's commit style (`chore(model-profiles): ...`), and the PR description summarizes the changes clearly.
- New entries use the same key layout as their neighbors. The two OpenRouter `openai/gpt-6.1-terra*` entries include `pdf_inputs` and `structured_output`, like the other `openai/*` entries.

### Potential data problems (please check)

1. **Output limits seem to be filled in as "90% of the context window", and they keep flipping.** Several values are exactly 90% of the input limit:
   - 943,717 or 943,718 ≈ 0.9 × 1,048,576
   - 235,929 ≈ 0.9 × 262,144
   - 117,964 ≈ 0.9 × 131,072

   This looks like a guessed default in the upstream data, not a published limit. In this PR the guess moves back and forth:
   - **Swapped values:** `deepseek/deepseek-v4-flash` goes 943,717 → 131,072, while `deepseek/deepseek-v4-flash-0731` goes 131,072 → 943,718. The two models effectively traded values. This looks like the upstream source mismatching models, not a real change.
   - **Value that doesn't fit the model:** `xiaomi/mimo-v2.5-pro` goes 945,000 → 235,929. That is 90% of a 262,144 context, but this model's input limit is 1,050,000.
   - **Real-looking corrections:** `google/gemma-3-4b-it`, `google/gemma-4-31b-it`, `deepseek-v4.1-flash` and `~z-ai/glm-latest` lose their guessed values and get believable ones.

   This matters because users and middleware read `max_output_tokens` from these profiles. A guessed ~944k limit for a model that actually allows ~131k will cause provider errors or wrong token budgets.

   **Suggestion:** pin the uncertain models in `profile_augmentations.toml`, at least the deepseek-v4-flash pair and `mimo-v2.5-pro`. It would also help if the refresh script flagged any `max_output_tokens` that equals about 90% of `max_input_tokens`, so reviewers notice it.

2. **`MiniMaxAI/MiniMax-M3.1-Flash` is marked `open_weights: False`.** It is the only HuggingFace entry with that value. Every other MiniMax entry, including `MiniMax-M3`, is `True`.
   - That might be correct, for example if the model is only served through an API, but it is unusual for a model hosted on the HF Hub. Please confirm it before people rely on it.
   - The entry also has no `structured_output` key, while `MiniMax-M2.7` and `MiniMax-M3` have one. A missing key just means "unknown", so this is a gap in the data, not an error.
   - The 512,000 output limit with a 1,000,000 input limit is unusually high. It is worth checking against the provider's model card.

3. **Removed models:** `arcee-ai/trinity-large-thinking` and `ibm-granite/granite-4.0-h-micro` are not referenced anywhere else under `libs/` (searched), so nothing breaks inside the repo. Anyone who reads `model.profile` for these IDs will now get no profile instead of the old data. That is normal for a refresh, but the release notes could mention it.

### Performance
No concerns. The changes are small additions and removals in a static dict.

### Security
No concerns. The file holds only literal data with no executable logic. The data comes from an external source, so its accuracy matters (see item 1), but there is no injection risk.

### Test coverage

## PR review #41520: chore(model-profiles): refresh model profile data

This PR is already merged; it is the current `HEAD` (`0b7a4eecb`). It is a bot-generated, data-only refresh of the two `_profiles.py` files. No hand-written code changed, so the usual code-quality and type-hint checks don't apply. Data like this can't be checked against the code, so the review below is about whether the numbers look plausible and whether anything downstream depends on them.

### Summary
- **huggingface:** one model added (`MiniMaxAI/MiniMax-M3.1-Flash`).
- **openrouter:** two models added (`openai/gpt-6.1-terra`, `openai/gpt-6.1-terra-pro`), two removed, and `max_output_tokens` changed on 10 models.
- Nothing outside the generated files mentions the removed or changed model IDs: a search of `libs/**/*.py` and `*.toml` found no tests, docs or augmentations that use them.

### Potential issues (data quality)

1. **The `max_output_tokens` values look like they're flipping between runs.** Several of the old and new values are exactly 90% of a context size, which suggests a guess from the upstream source rather than a published limit:
   - 943,718 ≈ 0.9 × 1,048,576
   - 235,929 ≈ 0.9 × 262,144
   - 117,964 ≈ 0.9 × 131,072

   Signs this is happening:
   - `deepseek/deepseek-v4-flash` and `deepseek/deepseek-v4-flash-0731` **swapped** values (943,717 ↔ 131,072 / 943,718). It's very unlikely the dated snapshot and the alias really traded limits.
   - `xiaomi/mimo-v2.5-pro` went from 945,000 to 235,929. That is 90% of a 262K window, but the model says it has a 1.05M input window. So the new value is probably still a guess, just a different one.
   - `google/gemma-4-31b-it` and `google/gemma-3-4b-it` dropped from the 90% guess to 16,384, which looks like a real provider limit. That is an improvement.

   **Why it matters:** anything that sizes requests from `profile["max_output_tokens"]` may change behavior between releases. Examples are middleware that summarizes or trims context, and token budgeting. If a provider rejects too-large requests, a bad high value can cause request errors. A bad low value cuts output short without warning.

   **Suggestion:** for high-traffic models whose upstream value keeps changing, set the limit in `profile_augmentations.toml`. Consider having the refresh workflow flag changes larger than about 5× in the summary so a reviewer looks closely. The deepseek swap is a good example to check by hand against OpenRouter's `/models` endpoint.

2. **The new HuggingFace entry doesn't match its neighbors.** In `MiniMaxAI/MiniMax-M3.1-Flash`:
   - **No `structured_output` key.** The other HuggingFace entries have one (50 occurrences in the file). Code that reads `profile.get("structured_output")` will treat it as unknown/false.
   - **`open_weights: False`.** This is the only HuggingFace entry with that value. A model hosted through HF Inference Providers is usually open-weights, so this may be an upstream mistake.
   - **512,000 max output on a 1M context.** That is unusually high and worth checking.

   **Suggestion:** confirm these against the model card and add an augmentation if needed.

3. **Removed models fall back silently.** After an upgrade, users of `arcee-ai/trinity-large-thinking` or `ibm-granite/granite-4.0-h-micro` with `ChatOpenRouter` will get an empty profile. Features that depend on profiles (for example, deciding whether tool calling is supported) will quietly change behavior. That's acceptable for models that have left OpenRouter's catalog, but it's worth a line in the next `langchain-openrouter` release notes. Another option is to keep them with `"status": "deprecated"`, which the file already does for `bytedance-seed/seed-1.6`, instead of deleting them.

### Security / performance
- No concerns. These are static dict literals, with no `eval` or I/O. The file grows by about 23 lines, which has no meaningful effect on import time.

### Tests
- Data refreshes don't need new unit tests. A cheap check worth adding to the generator or a unit test: every entry in a provider's `_PROFILES` should have the same set of keys, plus `max_output_tokens <= max_input_tokens` where it applies. That would have caught issue 2 automatically.

### Verdict
The format and structure are fine, but the upstream data is noisy. The deepseek swap and the 90%-of-context values suggest the source flips between runs. I'd add augmentations for the affected deepseek, xiaomi and MiniMax models, and add a key-consistency check to the refresh pipeline.
