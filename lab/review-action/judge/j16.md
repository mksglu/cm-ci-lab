# REVIEW A

**Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`**

**Summary:** This is a small, correct fix. The old code used `object_name[..1]`, which slices by byte. If the name starts with a multi-byte character, that slice isn't on a char boundary and panics. The new code calls `object_name.chars().next()` directly, which is safe for any UTF-8 input.

**Correctness**
- The fix matches the TS behavior. The TS regex is roughly `/^[a-zA-Z$_].*Ref$/`, so a non-ASCII first character should return `false`. `is_ascii_alphabetic() || '$' || '_'` does that.
- `object_name.len() > 3` compares bytes, not chars. For this check that's harmless: the name must end in `Ref`, which is 3 bytes, and a non-empty prefix is required. A multi-byte first char only makes the byte length larger, and the first-char test rejects it anyway. It's the same as the old behavior.
- `ends_with("Ref")` is safe on non-ASCII strings. It's a suffix byte comparison and doesn't slice.

**Code quality**
- The change is minimal and idiomatic. I'd drop the now-redundant `.len() > 3` in favor of something clearer, but that's optional. For example, `strip_suffix("Ref")` followed by a first-char check on the remainder would make the intent more obvious. It's a nit and shouldn't block the PR.
- It might be worth grepping the crates for other `[..n]` or `[n..]` byte slices on identifier names. The same bug class could exist elsewhere, such as in `is_hook_name` or similar helpers. I haven't checked.

**Performance / security**
- No performance concerns. The change is O(1) and slightly cheaper than before.
- On the security side, this removes a panic that could be triggered by user-controlled source code (a denial of service in the compiler). That's a robustness improvement.

**Test coverage**
- The new fixture `repro-ref-like-name-non-ascii.js` reproduces the panic and covers the `.current` access path through InferTypes. The `.expect.md` output looks sensible: the compiled code is memoized, with `.current` mutation inside the closure.
- The PR reports passing `yarn snap`, `yarn snap --rust`, and the Rust port script.
- Possible improvement: a Rust unit test for `is_ref_like_name` would cover the cases directly and cheaply, without the full pipeline. Suggested cases: `"한글Ref"` → false, `"fooRef"` → true, `"$Ref"`/`"_Ref"` → true, `"Ref"` → false, and `"ref"` → true. It would also guard against regressions in the boundary cases.
- The fixture covers a non-ASCII first character only. A name like `aé Ref` or `fooé` with non-ASCII in later positions is already safe, so this isn't a gap.

**Verdict:** LGTM. The fix is correct and well tested, and the suggestions above are optional. The PR has already been merged with an approval.

## Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`

**Verdict:** Approve. The change is correct, minimal, and well targeted. I read the diff only and did not run the tests.

### The fix
`object_name[..1]` slices by byte. When the name starts with a multi-byte character such as `한`, the slice lands inside the character and Rust panics. Using `.chars().next()` reads the first full `char`. The existing `is_ascii_alphabetic() || '$' || '_'` check then returns `false` for non-ASCII starts. This matches the TS regex, which only accepts `[a-zA-Z$_]` as the first character. The `.is_some_and` handles the empty-string case, though `len() > 3` already rules that out.

### Other places to check
- `object_name.len() > 3` counts bytes, not characters. This is harmless here, because a name too short in characters is also too short in bytes, and non-ASCII starts are rejected anyway.
- The same `[..n]` byte-slicing pattern may exist elsewhere in `compiler/crates/`, for example in other name heuristics like `is_hook_name` or `is_set_state_name`. A quick `grep -rn '\[\.\.[0-9]\]' compiler/crates` would show whether the same panic can happen elsewhere. This is optional and could be a follow-up.
- The Rust check only looks at the first character. The TS regex also constrains the remaining characters. That mismatch is not new and is outside this PR.
