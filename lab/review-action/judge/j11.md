# REVIEW A

I reviewed PR #100956 (it is already merged). I found no bugs. The fix is narrowly scoped, and the suggestions below are minor.

## Summary

Before this change, `prerenderToStream` returned the work store's shared `reactServerErrorsByDigest` as `digestErrorsMap`. The prerender caller treats any entry in that map as a render failure (`app-render.tsx:2749`). But the `'use cache'` wrapper's own error handler also writes into the shared map (`use-cache-wrapper.ts:1427`). It does that so the outer render can recover the original, readable error for logging (#86500). As a result, a `'use cache'` error that the page caught with `try/catch` still failed the build or on-demand prerendering.

The PR adds a separate `renderErrorsByDigest` map. Only the page's own RSC error handler fills it, and the prerender result now uses it as `digestErrorsMap`.

## Correctness

- **Uncaught `'use cache'` errors still fail the prerender.** When such an error escapes the page, React reports it again through `serverComponentsErrorHandler` with the same digest. The handler finds the original in the shared map, swaps in the original error in production, and records it in `renderErrorsByDigest` (`create-error-handler.tsx:119`).
- **Caught errors no longer count.** They only reach the cache-side handler, which doesn't receive the new map, so they never land in `renderErrorsByDigest`.
- **Every return in `prerenderToStream` was updated.** All six `digestErrorsMap:` returns now use `renderErrorsByDigest`; one path already returns `new Map()`. No `reactServerErrorsByDigest` return is left behind.
- **Lookups that need the shared map still use it.** These are the logging lookup at `:10418`, the SSR error filters at `:10520` / `:10834`, and the read-only lookup in `createHTMLErrorHandler`.
- **No SSR failures are lost.** The HTML/SSR handler only reads the shared map and reports its errors through `allCapturedErrors` / `ssrErrors`.
- **No regression from the error-page render.** It uses the same `serverComponentsErrorHandler`, so its errors also go into `renderErrorsByDigest`. That matches the old behaviour.

## Code quality

1. **Positional `undefined` argument.** The call is now `createReactServerErrorHandler(..., onHTMLRenderRSCError, undefined, renderErrorsByDigest)`. That is the sixth positional parameter, after an untyped `spanToRecordOn?: any`. A trailing options object (`{ spanToRecordOn, renderErrorsByDigest }`) would make call sites clearer and make it hard to swap the two by mistake. This is optional.
2. **Name the new parameter for what it holds.** Inside the handler, `renderErrorsByDigest` means "errors that reached this renderer's `onError`." A short JSDoc on the parameter would explain how it differs from `reactServerErrors`, i.e. that it excludes errors recorded by nested cache renders. The comment at the call site explains this well, but whoever next adds a call site will be reading the function signature.
3. **Comment above `if (!reactServerErrors.has(...))`.** The `@TODO ... we don't error the build in places we actually expect to` note now sits next to a map that no longer drives build failure in `prerenderToStream`. It may be worth rewording or moving it next to the new `set`.

## Performance

There is one extra `Map` per prerender and one extra `Map.set` per RSC error, which is negligible.

## Security

There are no concerns. No new request inputs or headers are read, and nothing new is exposed.

## Test coverage

The new e2e test is a good fit. It uses a real fixture directory and covers both build-time (`static`, from `generateStaticParams`) and on-demand (`runtime`) prerendering. Checking for `x-nextjs-cache: HIT` in start mode confirms the fallback was actually cached. Suggestions:

- **Check that the logging from #86500 is kept.** The PR description says the shared map is preserved for logging, but nothing tests that. In start mode, adding `expect(next.cliOutput).toContain('Cached function failed: static')` (or the runtime variant) would catch a regression that silently drops the original error log.
- **Cover the opposite case.** A route where the `'use cache'` error is *not* caught should still fail the prerender (in build mode, or return 500 on demand). This change touches exactly that detection path. If existing suites already cover it (e.g. other `use-cache` error tests), mention that in the PR. Otherwise, a second page in this fixture with `@gate`/`skipStart` handling for the expected build failure would guard against over-filtering.
- **Deploy mode.** `isNextStart` is false under deploy, so the HIT assertion is skipped there. Since deploy tests were the reason for the branch PR, consider checking a deploy-equivalent cache header so that path gets verified too.
- **Dev mode.** The test only checks for status 200 in dev. That's fine, but a comment saying the cache-HIT check is intentionally start-only would help readers.

## Verdict

The approach is correct and minimal: it separates "errors that reached this render's `onError`" from "all digested errors seen in this work unit." The suggestions above are about clarity and extra test assertions, not about whether the fix is right.

# Review: Fix prerendering of caught `'use cache'` errors (#100956)

## Summary
`workStore.reactServerErrorsByDigest` was doing two jobs:
1. **A lookup for logging and recovery.** The `'use cache'` wrapper writes every error thrown inside a cached function into it (`use-cache-wrapper.ts:1688`). That lets the RSC handler swap in the original, readable error later.
2. **A failure signal for prerendering.** `prerenderToStream` returned this map as `digestErrorsMap`. Around `app-render.tsx:2749`, the first entry in that map becomes the `renderError`, which fails the build or on-demand ISR.

Because of job 2, an error inside a `'use cache'` function failed the prerender even when the page caught it. The PR adds a separate `renderErrorsByDigest` map. Only `createReactServerErrorHandler` writes to it, and only when the page's RSC renderer reports an error. All seven `digestErrorsMap` return sites now use it. The shared map is still used for logging and recovery, including the `throw reactServerErrorsByDigest.get(...)` at line 10418.

## Correctness
- **Uncaught `'use cache'` errors still fail the build.** When such an error reaches the RSC handler, `err.digest` matches the shared map. In production `err` is replaced with the original error, and then `renderErrorsByDigest.set(err.digest, err)` runs. So the original error is still what gets rethrown at build time. Good.
- **The error-page render is covered.** The `errorServerResult` paths (lines ~10774 and 10848) use the same `serverComponentsErrorHandler`, so their returns stay consistent.
- **SSR-surfaced errors are unaffected.** They are still collected through `captureHTMLError` into `allCapturedErrors`, then filtered by `isUserLandError` into `ssrErrors`. A cached error that crosses into a client component through a promise and is thrown in SSR still fails the prerender.
- **A small side benefit.** The shared map can also hold entries from other handlers in the same request, such as the validation handler at line 8695. Those no longer leak into `digestErrorsMap`, so the failure signal is narrower and more accurate.
- **Harmless inconsistency.** The shared map keeps the first error per digest (`if (!reactServerErrors.has(...))`), but `renderErrorsByDigest?.set` overwrites. Map insertion order keeps the key in its first position, so `values().next()` still picks the first digest seen, though its value can change. Using the same first-wins guard would make the two maps behave alike. This is not a bug.

## Code quality
- **Positional `undefined`.** `createReactServerErrorHandler(..., onHTMLRenderRSCError, undefined, renderErrorsByDigest)` stacks a second optional positional parameter after `spanToRecordOn?: any`. That is easy to get wrong at future call sites. Consider an options object (`{ spanToRecordOn, renderErrorsByDigest }`) or a short JSDoc on the new parameter. The handler is called from about nine places, so the signature will likely grow again.
- **Stale TODO.** The `@TODO` at `create-error-handler.tsx:113` ("possible that we don't error the build in places we actually expect to") now describes the new map too. Updating it to mention that `renderErrorsByDigest` is the build-failure signal would help the next reader.
- **The comment in `prerenderToStream` is good.** It explains clearly why there are two maps.

## Performance
Negligible: one extra `Map` per prerender and one `set` per reported RSC error.

## Security
No concerns. The change reads no new headers or inputs, and error digests and messages are handled exactly as before.

## Tests
The new e2e suite fits repo conventions: it uses a fixture directory (`files: __dirname`), sets `cacheComponents: true`, and covers both the build-time path (`static`, via `generateStaticParams`) and the on-demand path (`runtime`).

Suggestions:
1. **Add a negative case.** Nothing confirms that an *uncaught* `'use cache'` error still fails prerendering. That is the main regression risk of narrowing the map. A small production-only test, using `skipStart` and `next.build()` and expecting a non-zero exit plus the original message in the output, would protect it. A separate fixture would keep the main suite building.
2. **Assert the error is still logged.** The PR says caught `'use cache'` errors should still be logged (#86500). Checking that `next.cliOutput` contains `Cached function failed: static` (production only) would cover the "preserve the shared lookup for logging" half of the change.
3. **Possible flakiness in the HIT check.** For `/runtime`, the HIT check runs immediately after the first on-demand render. If the ISR cache write ever finishes after the response, the check could flake. Wrapping it in `retry()` from `next-test-utils` would be safer.
4. **Deploy mode is fine as written.** The `x-nextjs-cache` assertion is gated on `isNextStart`, so it won't misfire under Vercel's `x-vercel-cache`.

## Verdict
Approve. Of the suggestions above, the uncaught-error test is the one that matters most. The rest are optional polish.
