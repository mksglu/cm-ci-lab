## PR #37046 review: fix(tls): distrust compromised eMudhra certificate authorities

**Overall:** The security fix is sound and needed. The new `rustls-webpki` version rejects certificate chains that use the compromised eMudhra keys, including cross-signed ones, and the root bundles drop `emSign ECC Root CA - G3`. The ML-DSA move from `unstable` to the stable API is clean. My main concern is the Cargo.lock change that now links **two copies of AWS-LC** into the binary.

### 1. Two `aws-lc-sys` versions are now linked (main issue)

Cargo.lock now contains both `aws-lc-sys 0.40.0` and `aws-lc-sys 0.46.0`:
- `aws-lc-rs 1.18.2` uses `aws-lc-sys 0.46.0`.
- The workspace still pins `aws-lc-sys = { version = "0.40.0", features = ["prebuilt-nasm"] }` (`Cargo.toml:195`). `deno_crypto_provider` (`libs/crypto`) and `deno_node_crypto` call it directly.

What this means:
- **Binary size and build time.** Two full builds of the AWS-LC C library get compiled and linked into `deno`. That's likely several MB more, plus extra CMake/C time in CI and for contributors. Size matters for `deno` and for `deno compile` output.
- **Two separate crypto states.** The duplicate symbols probably link fine, because each version's symbols get a version-specific prefix. But there are now two independent AWS-LC instances, each with its own RNG, FIPS/self-test state and error queues. `node:crypto` code that calls `aws_lc_sys::*` directly (`ext/node_crypto/cipher.rs`, `lib.rs`, `libs/crypto/ffi.rs`, `spki.rs`) runs on 0.40. `aws-lc-rs` users (rustls, WebCrypto ML-DSA) run on 0.46. Today I couldn't find any place that passes raw `EVP_PKEY`/`BIO` pointers from one to the other. If someone does that later, it's memory-unsafe across the two versions, and nothing catches it at compile time.
- **The `prebuilt-nasm` feature no longer applies to the copy rustls uses.** Before, both crates resolved to one `aws-lc-sys`, so the workspace's `prebuilt-nasm` feature covered the TLS stack. Now it only applies to the 0.40 copy. 0.46 builds with its default features. Please confirm that Windows x64 CI and release builds, and contributor setups, don't suddenly need a NASM install.

**Suggestion:** Bump the workspace `aws-lc-sys` to `0.46.0` so there's only one copy. If that's blocked by API changes in the direct FFI users, it would be good to say so in the PR and open a follow-up. Afterwards, `cargo tree -d -i aws-lc-sys` should show a single version.

### 2. The root-bundle jump is larger than the PR describes

`webpki-root-certs` goes from 0.26.6 to 1.0.10, and `webpki-roots` from 0.26.1 to 1.0.10. Those are many months of Mozilla CA changes, not just the emSign removal. Other roots were added and removed along the way. That's the right thing to do, but users will see it:
- `tls.rootCertificates` (`ext/node/ops/tls.rs:122`) will return a different list.
- `fetch` / `Deno.connectTls` may reject servers that chain to roots removed since 0.26.1.

A sentence in the PR description or release notes would help people who hit new TLS failures after upgrading.

### 3. Smaller points

- **Leftover feature flag:** `ext/crypto/Cargo.toml:21` still enables `aws-lc-rs`'s `features = ["unstable"]`. Nothing in `ext/crypto` imports `aws_lc_rs::unstable` anymore. Remove it if nothing else needs it, so the crate doesn't keep depending on the unstable surface.
- **`to_pkcs8v1()`:** Good call to keep the existing export format. The newer `to_pkcs8()` could emit a different structure, which would silently change the bytes `exportKey("pkcs8")` returns for ML-DSA. Please confirm that existing tests compare the exported PKCS#8 bytes exactly (for example, round-trip or known-answer tests). If they don't, a known-answer test would lock this in.
- **Re-exported crate changes major version:** `ext/tls/lib.rs:30` does `pub use webpki_roots;`, so moving from 0.26 to 1.0 is a breaking change for anyone using `deno_tls` as a library. That's probably fine given how Deno versions its crates, but worth noting.
- **Old `webpki-roots` still in the tree:** `reqwest` and `hyper-rustls` still use 0.26.11. Since that's a thin wrapper around 1.0.10, everything ends up on the fixed bundle, as the PR description says. Upgrading those crates later would remove the wrapper.
- **Version requirement:** Raising `rustls-webpki` from `"0.103"` to `"0.103.16"` is correct. It stops a `cargo update`, or a downstream user without Deno's lockfile, from resolving to a version without the fix.

### 4. Tests

There's no regression test, which is acceptable here. The rejection logic lives in, and is tested in, `rustls-webpki`, and building a test chain for the compromised keys inside Deno would be awkward. One cheap option is a unit test asserting that `emSign ECC Root CA - G3` isn't in `tls.rootCertificates`. That would catch a later accidental downgrade of `webpki-root-certs`.

### 5. Security

This is a positive security change. Apart from the two-crypto-instances issue in point 1, I don't see new risks.

### Summary

| Area | Assessment |
|---|---|
| Correctness of the security fix | ✅ Good |
| ML-DSA API migration | ✅ Good (`to_pkcs8v1` keeps the export format) |
| Dependency hygiene | ⚠️ Two `aws-lc-sys` copies: bigger binary, two crypto states, `prebuilt-nasm` gap |

# Review: PR #37046 — fix(tls): distrust compromised eMudhra certificate authorities

## Summary
The PR raises `rustls-webpki` to 0.103.16, which rejects the 8 compromised eMudhra keys. It moves `webpki-roots` and `webpki-root-certs` to 1.0.10, which drops the `emSign ECC Root CA - G3` root. A `webpki-roots` 0.26.11 wrapper makes reqwest and hyper-rustls use the same fixed 1.0.10 bundle. Pulling in the new verifier forces `aws-lc-rs` up to 1.18.2, so ML-DSA moves from the `unstable` module to the stable API. `deno_graph` goes to 0.111.1 to pick up the same TLS dependencies.

This is the right fix. Raising the `rustls-webpki` minimum to `0.103.16` in `Cargo.toml` is important: it means a later `cargo update` can never fall back to a version without the distrust.

## Potential bugs / issues

### 1. Two copies of `aws-lc-sys` are now linked (most important)
The lockfile now has both `aws-lc-sys 0.40.0` and `aws-lc-sys 0.46.0`:
- `aws-lc-rs 1.18.2`, used by rustls, webpki and `ext/crypto`, uses **0.46.0**.
- The workspace pin `aws-lc-sys = { version = "0.40.0", features = ["prebuilt-nasm"] }` (`Cargo.toml:195`) still makes `deno_crypto_provider` (`libs/crypto`) and `deno_node_crypto` use **0.40.0**.

What this causes:
- **Binary size and build time:** a second full AWS-LC C build gets compiled and statically linked into `deno`. That is several MB and noticeably more CI time on every platform.
- **Windows build risk:** `prebuilt-nasm` is only enabled on 0.40. Nothing in the workspace turns it on for 0.46. Whether 0.46 builds on a Windows machine without NASM depends on that crate's default behaviour. CI may pass only because NASM happens to be installed on the runners, while contributors' local builds could break.
- **Two crypto implementations in one process:** Node `crypto` (`ext/node_crypto/cipher.rs`, `lib.rs` scrypt, `libs/crypto/spki.rs`) runs on AWS-LC 0.40, while TLS and WebCrypto run on 0.46. They can differ in behaviour and security fixes, and any AWS-LC CVE now means checking two versions.
- **Is it memory-safe?** As far as I can tell, yes. I found no raw pointers (`EVP_PKEY*`, `BIO*` and so on) passed between `aws-lc-rs` objects and the 0.40 `aws_lc_sys` calls. `PKey::from_ptr` is only fed by 0.40 calls inside `libs/crypto/spki.rs`. AWS-LC also prefixes its symbols per version, so linking works. Still, this is easy to break by accident later.

**Suggestion:** bump the workspace pin to `aws-lc-sys = { version = "0.46.0", features = ["prebuilt-nasm"] }` so everything uses one copy. The raw FFI calls in `ext/node_crypto/cipher.rs` and `libs/crypto/{ffi,spki}.rs` use stable BoringSSL-style APIs and should compile unchanged. If that bump is too risky for a security hotfix, at least open a tracking issue and mention the duplication in the PR description; right now it is only described as "AWS-LC and pkg-config updates".

### 2. ML-DSA PKCS#8 export format (`ext/crypto/mldsa.rs:327`)
Switching to `to_pkcs8v1()` is a reasonable way to keep the old output under the stable API. The risk is that the format silently changes: v2 adds a public key field, and the seed may be encoded differently. That would break interop and the re-import path in `extract_seed_from_pkcs8`.
- Please confirm the existing WebCrypto ML-DSA tests do an export → import round trip **and** compare against fixed expected bytes (e.g. in `tests/unit/webcrypto_test.ts` or WPT expectations). If no fixed-bytes test exists, a small one comparing PKCS#8 output for a fixed seed would lock the format across future `aws-lc-rs` upgrades.

## Code quality
- The import changes in `mldsa.rs` are clean and alphabetized, and moving `PqdsaPrivateKey` to `aws_lc_rs::signature` is correct.
- **Leftover feature:** `ext/crypto/Cargo.toml:21` still has `aws-lc-rs = { workspace = true, features = ["unstable"] }`. A grep finds no `unstable::` uses left anywhere in `ext/`, `libs/`, `cli/` or `runtime/`. Dropping the feature would stop new code from quietly depending on unstable APIs. It's a small cleanup and could go in a follow-up to keep this PR minimal.
- The 0.26 → 1.0 move for `webpki-roots` / `webpki-root-certs` doesn't need code changes. `TLS_SERVER_ROOTS` (`ext/tls/lib.rs:266`, `cli/lib/args.rs:152`) and `TLS_SERVER_ROOT_CERTS` (`ext/node/ops/tls.rs`) have the same types. 👍

## Security
- The change does what it says. The `rustls-webpki` key-based block also covers cross-signed paths, which removing the root alone would not.
- Note that the block only applies to Deno's bundled verifier. If users run with `DENO_TLS_CA_STORE=system`, the compromised intermediates are still rejected, because `rustls-webpki` does the path checking. The release notes could say this.
- Because of issue 1, part of Deno's crypto stays on the older AWS-LC 0.40. Check whether any AWS-LC fixes between 0.40 and 0.46 matter to the Node crypto paths.

## Performance
Runtime performance is unaffected. Build time and binary size go up because of the duplicate `aws-lc-sys` (issue 1).

## Test coverage
- There is no regression test for the distrust. A spec test is hard because it needs a chain with a compromised key, and the upstream `rustls-webpki` PR (#546) covers that logic, so this is acceptable.
- A cheap check would be a Rust unit test in `ext/tls` asserting that no `TLS_SERVER_ROOTS` entry's subject matches `emSign ECC Root CA - G3`. It would catch a future accidental downgrade of `webpki-roots`.
- See issue 2 about locking the ML-DSA PKCS#8 output.

## Verdict
The security fix is correct and worth shipping fast. Before or soon after the release, I'd ask for:
1. **Merge the two `aws-lc-sys` copies** by bumping the workspace pin to 0.46 with `prebuilt-nasm`, or track that explicitly.
2. Confirm the ML-DSA PKCS#8 export bytes are unchanged.
3. Optionally, drop the now-unused `unstable` feature from `ext/crypto/Cargo.toml`.
