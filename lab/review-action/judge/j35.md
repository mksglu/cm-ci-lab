# REVIEW A

## Review of PR #100956: Fix prerendering of caught `'use cache'` errors

The PR is already merged and has one approval. I read the diff only. I did not run any tests.

### Summary
Errors thrown inside `'use cache'` functions were recorded in the shared `workStore.reactServerErrorsByDigest` map, which exists for logging (#86500). `prerenderToStream` also used that same map as `digestErrorsMap` to decide whether a prerender failed. A page that caught a cached function's error and rendered a fallback therefore still failed the build or on-demand generation.

The fix adds a separate `renderErrorsByDigest` map. Only the page's RSC renderer error handler fills it. It is returned as `digestErrorsMap` from all six return sites. The shared map is untouched, so the logging behavior stays the same.

### Code quality
- The change is small and well targeted. Splitting the logging lookup from the failure-detection set is the right separation of concerns.
- The new comment in `app-render.tsx` explains why the two maps differ.
- All six `digestErrorsMap` return sites are updated consistently: the dynamic and Fizz success paths, and the error-shell paths.
- **Nit:** `createReactServerErrorHandler` now has `spanToRecordOn?: any` followed by `renderErrorsByDigest?`. The call site has to pass a literal `undefined` positionally, which is easy to misread. Moving to an options object, or reordering the parameters, would be cleaner. This is minor, since the function has few callers.
- **Nit:** The new map is written unconditionally when the optional argument is present. Other callers of `createReactServerErrorHandler`, such as the dev, runtime and resume paths, don't pass it, so they are unaffected.

### Potential bugs and risks
- **Where `renderErrorsByDigest.set` sits:** It runs after the earlier early-return branches in the handler. I only saw the diff context. Make sure those branches are only for the response-closed case and for bailout and dynamic errors, which are intentionally not treated as failures. The `reactServerErrors.set` just above is guarded by a condition. The new `set` is unconditional. If that guard excludes errors that shouldn't fail the build, the new map is looser than the old one. Something like a `shouldSkip` check could behave differently here. This is worth a quick check, but I don't see a concrete problem.
- **Digest collisions:** The map is keyed by digest. If two distinct errors in the page's own RSC stream shared a digest, one would overwrite the other. This is the same as the previous behavior.
- **Errors that surface only via the cache:** Before, a cached function's error that was not caught by the page would be in the shared map. It also reaches the page's RSC handler when it propagates, so it is still recorded. Uncaught cache errors should still fail. A test for the uncaught case would pin this down.

### Performance
There is no meaningful impact. It is one extra `Map` per prerender and one `set` per reported error.

### Security
There are no concerns. No new headers are read and no external input is involved.

### Test coverage
- The e2e test follows the repo conventions: it uses a real fixture directory, `nextTestSetup({ files: __dirname })`, and no `setTimeout` or `check()`.
- It covers both build-time prerendering (`/static` via `generateStaticParams`) and on-demand generation (`/runtime`). It also asserts the cache `HIT` in start mode.
- Gaps:
  - There is no assertion that the error is still logged. The PR claims logging (#86500) is preserved, so a `next.cliOutput` check in dev mode would guard against regressions.
  - There is no negative case where the cached error is not caught and the build or request should still fail.
  - The test is not gated to run only with `cacheComponents`, but the fixture sets it in `next.config.ts`, so that is fine.
  - In dev mode the `HIT` assertion is skipped. That is reasonable.

### Verdict
This is a clean, minimal and correct fix. The main suggestions are follow-ups: add a logging-preserved assertion and an uncaught-error negative test, and consider an options object for the handler signature.

# REVIEW B

## Review of PR #100956: Fix prerendering of caught `'use cache'` errors

The PR is already merged and approved. This is my review of the diff.

### Summary
Before this change, prerender failure detection used the shared `workStore.reactServerErrorsByDigest` map. `'use cache'` functions also write their errors into that map so they can be logged (#86500). A page that caught such an error therefore still looked like a failed render, and the build or on-demand generation failed. The PR adds a separate per-render map, `renderErrorsByDigest`. The RSC error handler fills it only for errors the page's own renderer reports. Every `digestErrorsMap` returned from `prerenderToStream` now uses this new map. The shared map is left alone for logging.

### Code quality
- The fix is small and targeted, and the comment in `app-render.tsx` explains why there are two maps.
- All eight `digestErrorsMap` return sites changed together. I found no site that still uses the old map.
- `renderErrorsByDigest` is an optional last parameter of `createReactServerErrorHandler`, and it follows the optional `spanToRecordOn`. The call site has to pass `undefined` positionally to reach it. That is slightly awkward, but it keeps the change minimal. An options object would read better if the signature grows again.
- The write sits after the `reactServerErrors.set` block. I couldn't tell from the diff whether the earlier branches return early. If one returns before this line, some errors would never reach the new map, so check that those branches don't skip it.

### Potential issues
- **Other users of the shared map.** Prerender failure detection now ignores `reactServerErrorsByDigest`. I didn't check whether anything else in the prerender path, such as the `ssrErrors` handling or dev-only paths, depended on the old map being the one returned. The test passes and the PR was approved, so it is probably fine.
- **Errors that are not caught.** If a `'use cache'` error is not caught, it propagates through the page's RSC render and the renderer's own error handler reports it. The new map records it, so the failure is still detected. The test only covers the caught case. A companion test with an uncaught cached error that still fails the build would guard against the fix swallowing real failures.

### Performance
Each prerender allocates one extra `Map` and does one `Map.set` per reported error. That cost is negligible.

### Security
No concerns. The change reads no new request headers.

### Test coverage
- The e2e test covers both a build-time path (`generateStaticParams` with `static`) and an on-demand path (`runtime`). It also checks that the fallback is cached by looking for an `x-nextjs-cache: HIT` header under `next start`.
- The test uses `nextTestSetup` with `files: __dirname` and a real fixture directory, as the repo guidelines ask.
- The `HIT` check on `runtime` could be flaky if the first fetch and the cache write race. If it is, wrap it in `retry()`.
- The test doesn't assert that nothing was logged, or that the original error still reaches the logs. The PR says logging is preserved, so a log assertion would cover that claim.
- The test runs only with `cacheComponents: true`. The `'use cache'` path may also matter in other configurations, but this is the one the issue describes.

### Verdict
This is a correct, minimal fix with a regression test. The suggestions above are optional follow-ups: a negative test for uncaught cached errors, a log-preservation assertion, and `retry()` around the cache-hit check if it turns out to be flaky.
