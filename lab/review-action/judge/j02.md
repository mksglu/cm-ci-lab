# Review: fix(ext/node): support assert message functions and format arguments (#36944)

## Summary
The PR moves all assertion-message handling into one shared `innerFail()` in `internal/assert/utils.ts`. Messages are now passed around as a list of arguments, which lets an assertion take a message function or a printf-style message (`assert.strictEqual(a, b, "got %s", x)`). This matches the Node 26 API and lets `parallel/test-assert.js` run again. Having one code path is a real improvement over the scattered `throw message` / `new AssertionError` copies. A few correctness and cleanup issues remain.

## Potential bugs

**1. Passing `undefined` (or `null`) as the message may now throw `ERR_INVALID_ARG_TYPE`** (`utils.ts`, `innerFail`)

With `...message`, a call like `assert.strictEqual(1, 2, undefined)` gives `message = [undefined]`. The length is 1, and `undefined` is not a string, not an Error and not a function, so it reaches the last branch and throws `ERR_INVALID_ARG_TYPE("message", ...)` instead of an `AssertionError` with the default message.

Wrapper helpers commonly forward an optional message:
```js
function check(a, b, msg) { assert.strictEqual(a, b, msg); }
check(1, 2); // previously: AssertionError; now: TypeError [ERR_INVALID_ARG_TYPE]
```
`innerOk` already handles this case (`args[1] == null`), but the comparison methods and `match`/`doesNotMatch` don't. Please check what Node 26 does here. If it treats a `null`/`undefined` first message as "no message", `innerFail` should do the same, for example `if (message.length === 0 || message[0] == null)`. Either way, a regression test would help.

**2. `internalMatch` reports `generatedMessage` incorrectly when the message is falsy**

```js
const generatedMessage = message.length === 0;
message[0] ||= /* default */;
```
The old code used `!message`. So `assert.match("a", /b/, "")` and `assert.match("a", /b/, undefined)` used to get `generatedMessage: true`, and now get `false` even though the default message is used. The check should probably be `!message[0]`, computed before the `||=`.

`||=` also has two smaller side effects:
- `match(s, re, undefined, "x")` swaps in the default text as `message[0]` and keeps `"x"`, so `format()` appends `"x"` to the default message.
- If a message function throws or returns a non-string, the error falls back to the generic `AssertionError` text for `match`, not the more useful "The input did not match the regular expression…" text.

**3. `generatedMessage` is wrong when an `ok` message function falls back**

`innerOk` always passes `generatedMessage: false` when the user supplies a message. If that message is a function that throws or returns a non-string, `resolved` becomes `undefined` and `AssertionError` builds a default message. The error still says `generatedMessage: false`. One fix is for `innerFail` to set `generatedMessage = true` whenever `resolved` ends up `undefined` because of the fallback, so callers don't need to know about it.

## Code quality

**4. Leftover commented-out code in `internalMatch`.** These lines should be deleted:
```js
// if (ObjectPrototypeIsPrototypeOf(ErrorPrototype, message)) { ...
// const generatedMessage = !message;
// message ||= typeof string !== "string"
// const err = new AssertionError({
// err.generatedMessage = generatedMessage;
// throw err;
```
The leftover `// 'The input was expected to not match ...` comment is now misleading as well.

**5. Coverage is incomplete across the module.** `fail()`, `expectedException()` (used by `throws`/`rejects`), the primitive branch of `compareExceptionKey`, and `ifError()` still build `AssertionError` directly and check `ErrorPrototype` themselves. So:
- `assert.throws(fn, /re/, () => "msg")` passes a function into `AssertionError` as the message.
- `assert.fail(() => "msg")` behaves differently from the other methods.

The PR says it fixes "part of #35293", which is fair, but a TODO or a follow-up issue listing the remaining methods would help.

**6. Simpler `innerOk` call sites.** `innerOk(ok, ...new SafeArrayIterator(args))` spreads an array only to collect it again as a rest parameter. Passing `args` directly (`innerOk(fn, args)`) would skip a copy and the iterator allocation, and would read more simply.

**7. Formatting noise.** Destructuring a single name over several lines (`const {\n  getErrorSourceExpression,\n} = ...`) is an unrelated whitespace change. Minor, but CLAUDE.md asks for no drive-by changes.

## Performance
- Every comparison method (`strictEqual`, `deepEqual`, …) now allocates a rest array on every call, including when the assertion passes. These are hot paths in test suites. The cost is small and matches upstream Node, so it's acceptable, but don't add more per-call work on the success path.
- `format()` and the message function only run when an assertion fails, which is correct.

## Security
No concerns. Message functions are user-supplied and run synchronously only when an assertion fails. Errors they throw are swallowed on purpose, which matches the described Node behaviour.

## Test coverage
- Turning `parallel/test-assert.js` back on is good and covers most of the new behaviour.
- There are no Deno-side tests (`tests/unit_node/assert_test.ts`) for the edge cases above: an `undefined` message on the comparison methods, `generatedMessage` for falsy messages in `match`, a message function that throws or returns a non-string with `ok`/`match`, and the `ERR_AMBIGUOUS_ARGUMENT` paths. A few targeted cases there would protect against regressions that the upstream test doesn't check.

## Verdict
The overall direction is right. Before relying on this, I'd fix two things:
1. Confirm, and probably fix, the `undefined`-message regression (#1).
2. Clean up the commented-out code and `generatedMessage` handling in `internalMatch` (#2, #4).

The rest can go into follow-ups.

This adds Node 26's printf-style messages and lazy message functions. `parallel/test-assert.js` is no longer ignored. ## Potential bugs

1. **An explicit `undefined` message now throws `ERR_INVALID_ARG_TYPE`. This is the main concern.**
   Methods like `equal`, `strictEqual` and `deepStrictEqual` now collect the message with `...message`. A call such as `assert.strictEqual(1, 2, undefined)` produces `message = [undefined]`. The length is 1, so the "default message" branch is skipped. The first element is not a string, `Error` or function, so it reaches the `else` branch:
   ```ts
   throw new ERR_INVALID_ARG_TYPE("message", ["string", "function"], message[0]);
   ```
   Before this PR, that call threw a normal `AssertionError` with the generated diff message. Code that forwards an optional message commonly does this, e.g. `function check(a, b, msg) { assert.strictEqual(a, b, msg) }`. Those callers would now get a `TypeError` instead of an assertion failure.

   `innerOk` already handles this case (`args.length === 1 || args[1] == null` → default message), so the two paths are inconsistent. Unless Node 26 really throws here (worth checking against upstream `lib/assert.js`), the first branch should be:
   ```ts
   if (message.length === 0 || (message.length === 1 && message[0] === undefined)) {
   ```

2. **`internalMatch` gets `generatedMessage` wrong for `[undefined]`.**
   It computes `const generatedMessage = message.length === 0;`. For `assert.match("a", /b/, undefined)`, the default message is filled in by `message[0] ||= ...`, but `generatedMessage` stays `false`. The old `!message` check returned `true`. Comparing against the resolved value would fix it, e.g. `generatedMessage = message.length === 0 || message[0] == null`, computed before the `||=`.

3. **Message functions in `match` / `doesNotMatch` lose the specific default message.**
   When `message[0]` is a function, `||=` doesn't run. If the function throws or returns a non-string, `innerFail` passes `message: undefined` to `AssertionError`. The user then gets `AssertionError`'s generic text for operator `match`, not the "The input did not match the regular expression …" text. `generatedMessage` is also forced to `false` in that case. This is an edge case, but it contradicts the PR's stated goal of keeping default messages when a function fails.

4. **Non-string truthy messages in `throws` / `rejects` validation objects.**
   `compareExceptionKey` now wraps the message as `[message]`. A call like `assert.throws(fn, { code: "X" }, 42)` used to raise an `AssertionError` with message `"42"`. It now raises `ERR_INVALID_ARG_TYPE`. This is probably fine if it matches Node 26, but it changes behaviour and is worth confirming.

## Code quality

- **Commented-out code was left in `internalMatch`.** Seven lines of dead code (`// if (ObjectPrototypeIsPrototypeOf(...`, `// const generatedMessage = !message;`, `// const err = new AssertionError({`, `// err.generatedMessage = ...`, `// throw err;`) look like leftovers from development and should be deleted.
- **`internalMatch` mutates the caller's rest array** (`message[0] ||= ...`). It's harmless because the array is freshly created by `...message`, but building a local tuple would be clearer.
- **`innerFail` no longer appears in `assert.ts`'s local scope.** It is now imported, so it's worth checking that no `ErrorPrototype` / `ObjectPrototypeIsPrototypeOf` primordial imports in `assert.ts` became unused. `fail()` still uses them, so they probably remain needed.

- **Fragile tuple cast.** `ArrayPrototypeSlice(args, 1) as MessageTuple` hides the `[undefined, ...]` case from the type system. That cast is what allows bug 1 to type-check.

The cost is negligible in practice, though assertion-heavy test suites call these in hot loops. If it ever matters, one option is to keep `message` as a named parameter and build the tuple only on failure (via `arguments`).

`format()` and the message function run only on failure, which is correct and matches Node's lazy semantics.

## Security

No concerns. Message functions are user code called with values the user already supplied. Exceptions from them are swallowed and the default message is used, so a broken message callback can't hide an assertion failure.

## Test coverage

- Coverage relies entirely on enabling `parallel/test-assert.js`, which is a good, thorough upstream test.
- There are no Deno-side tests for the regressions above. A small `tests/unit_node/assert_test.ts` case would lock in the behaviour:
