# Review: PR #345293 — hide non-user-invocable agents from the Cloud picker

The PR is already merged. I read the diff only and did not run the tests.

## Summary
The change does three things:
- It filters remote agents with `user_invocable === false` out of the Cloud picker.
- It still passes the full remote list to `getLocalCustomAgentFiles`, so hidden remote agents can't come back as "missing from remote" warnings.
- It parses local-only agent files with `PromptFileParser`, so local `user-invocable: false` frontmatter is respected.

The approach is sound and the diff is small and readable.

## Code quality
- **Filtering at the picker boundary:** Using `!== false` keeps the default of visible when the field is absent. The code builds `userInvocableAgents` once and reuses it for both the visibility condition and the item mapping. That's cleaner than the old repeated `status === 'fulfilled'` checks.
- **Error handling:** The per-file `try/catch` logs a warning and continues, so one unreadable file no longer aborts discovery. The outer `catch` still covers directory-level failures.
- **Parser reuse:** Using the existing `PromptFileParser` avoids a hand-rolled frontmatter regex. The tests cover CRLF line endings, trailing comments, nested keys, and body-only text.

## Potential issues and suggestions
1. **Sequential awaits in the loop (minor performance):** Each local-only file is now read with `await readFile` one at a time. The directory is normally small, so this is fine. If it grows, `Promise.all` over the unmatched entries would help. The order would need to be preserved for the output.
2. **Deleted files are logged as warnings:** A file removed between `readDirectory` and `readFile` is a normal race, so it probably shouldn't be a `warn`. The test covers both "deleted" and "unreadable" and expects the same single warning, so this looks deliberate. You could log `FileNotFound` at `trace` or `debug` to cut noise.
3. **`new PromptFileParser()` and `new TextDecoder()` are created per iteration:** These are cheap, but they could be hoisted above the loop.
4. **Local frontmatter for matched files is ignored:** For matched agents, remote visibility is authoritative. The test "keeps remote visibility authoritative" documents this, so it's intentional. It's an asymmetry worth a code comment, because a local `user-invocable: false` on a remote-visible agent still shows the agent.
5. **Other remote agent fields are still unfiltered:** `disable_model_invocation` agents stay visible, which matches the PR description. Nothing to change here.

## Security
No concerns. The file contents come from the user's own workspace and go through a parser. Nothing is sent externally, and the URIs come from a directory listing.

## Test coverage
Coverage is strong. There are seven cases:
- Default visibility.
- All remote agents hidden, so the group is omitted.
- Case-insensitive local/remote matching.
- Local frontmatter variants, both with and without a remote fetch failure.
- Deleted and unreadable files.

Two small gaps:
- There is no test for the `repoIds.length === 1` condition when `localOnly` is non-empty and `userInvocableAgents` is empty. The "every hidden" test covers only the case where the local file matches the hidden remote agent.
- The test file mocks `vscode.FileSystemError` with a hard-coded `code`. That's fine for now, but it's brittle if the production code ever starts branching on the error type.

## Verdict
Looks good. The fix is targeted and the tests are thorough. The points above are minor polish, and the main one is downgrading the log level for the deletion race.

## What it does
- It filters remote agents with `user_invocable === false` out of the Cloud picker. Agents without the flag stay visible, and `disable_model_invocation` does not hide an agent.
- It still passes the full remote list to `getLocalCustomAgentFiles`. A hidden remote agent therefore can't reappear as a "Missing from …" local-only warning entry.
- It reads local-only agent files and parses their frontmatter with the existing `PromptFileParser`. It skips files with `userInvocable === false`.
- It logs a per-file read error and continues with the other agents.

## Code quality
- **Good:** Filtering at the picker boundary is clean. Replacing the `customAgents.status === 'fulfilled' ? … : []` ternaries with a single `remoteAgents` array is a readability win.
- **Good:** Reusing `PromptFileParser` avoids a hand-rolled frontmatter regex. The tests cover the cases such a regex would get wrong: CRLF line endings, trailing comments, a nested key, and body-only text.
- **Good:** The `try/catch` is scoped to the individual file, so one bad file doesn't abort discovery. The outer catch is unchanged.
- **Nit:** `new PromptFileParser()` and `new TextDecoder()` are created inside the loop for every file. They could be hoisted above it.
- **Nit:** The reads happen sequentially with `await` in the loop. `.github/agents` is usually small, but the new work now scales with the number of unmatched files. `Promise.all` (or the existing `Limiter`) would keep latency flat. This is optional.

## Potential issues
1. **Local-only reads happen on every options request.** Previously `getLocalCustomAgentFiles` only listed the directory. Now each unmatched file is read and parsed each time the picker options are provided. It is probably fine, but it is worth confirming the call isn't on a hot path, such as being triggered on every git or window-state change. Caching by mtime would be the fix if it is.
2. **Hidden-agent matching depends on the lowercased filename.** A local file `Foo.agent.md` can match a remote agent named `foo` only through the name-derived key, and the PR relies on that. The test with `HiDdEn.AGENT.MD` covers this case.
3. **Remote-fetch failure fallback.** When the remote fetch fails, `remoteAgents` is `[]`, so the picker shows every user-invocable local file as a "Missing" warning. This is the pre-existing behaviour and the test covers it. It could mislead users during an outage, but it is outside this PR's scope.
4. **Errors are logged at `warn` for deleted files too.** A file deleted between listing and reading is a benign race. `FileNotFound` could log at `debug`. The test deliberately asserts a warning for both cases, so this is a design choice.

## Performance
Aside from the extra file reads above, there is no concern. The remote filter is O(n).

## Security
No concerns. The change only restricts what is shown, and it doesn't broaden what is read. Reads are limited to files already enumerated under the agents directory. The UI filter is not an authorization boundary. The server still returns a 400 if a non-invocable agent is somehow selected, which is acceptable.

## Test coverage
Coverage is strong. There are seven cases:

- all-hidden omits the group
- remote visibility stays authoritative over local frontmatter
- local frontmatter variants, parameterized over fetch success and failure
- deleted and unreadable files

- Add a case for a local file with malformed or unterminated frontmatter. It should still be listed, and the parser shouldn't throw.
- Add a case for the `repoIds?.length === 1` condition. It gates the local-only entries, and multi-repo selection isn't exercised here.
- The test mock changes are reasonable. `FileSystemError`, `asRelativePath`, and `observableValue` for `activeRepository` are needed for the new paths.

This is a good fix with solid tests. The only follow-ups I'd consider are hoisting the parser and decoder, and checking that the per-request file reads are cheap enough.
