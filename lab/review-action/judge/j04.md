# Review: PR #38025 — [rust-compiler] Fix non-ASCII panic in `is_ref_like_name`

## Summary
`object_name[..1]` sliced the first **byte** of the string. Rust panics when a slice boundary falls inside a UTF-8 character, so a name like `한글Ref` crashed the compiler on `.current` access. Using `object_name.chars().next()` reads the first full character, so the panic can't happen. The fix is small, correct and well targeted.

## Correctness
- **The fix is right.** A non-ASCII first character now fails `is_ascii_alphabetic()` and the function returns `false`. That matches the TS regex `/^(?:[a-zA-Z$_][a-zA-Z$_0-9]*)Ref$|^ref$/` (`InferTypes.ts:785`).
- **The `len() > 3` check still works.** It counts bytes, not characters. It only needs to rule out a bare `"Ref"`, and any name with a non-empty prefix is longer than 3 bytes, so the byte count is fine.
- **One divergence from TS remains (it predates this PR, but it's the same area).** The comment at `infer_types.rs:243` says the code matches the TS regex, but it only checks the **first** character. The regex also requires every character between the first one and `Ref` to be in `[a-zA-Z$_0-9]`. Example: `a한Ref` or `aéRef` (both valid JS identifiers):
  - TS: no match, so it is not treated as a ref.
  - Rust: `ends_with("Ref")` passes and `'a'` passes, so it **is** treated as a ref.

  This can change type inference and ref validation, and so the output can differ between TS and Rust. Since this PR is about non-ASCII names, it would be a good moment to close the gap, for example:

  ```rust
  object_name == "ref"
      || object_name
          .strip_suffix("Ref")
          .is_some_and(|prefix| {
              let mut chars = prefix.chars();
              chars
                  .next()
                  .is_some_and(|c| c.is_ascii_alphabetic() || c == '$' || c == '_')
                  && chars.all(|c| c.is_ascii_alphanumeric() || c == '$' || c == '_')
          })
  ```

  This version also makes the separate `len() > 3` check unnecessary: an empty prefix fails on `chars.next()`. It also stays close to the TS regex, which the port guidelines ask for.

## Test coverage
- The new fixture `repro-ref-like-name-non-ascii.js` reproduces the crash, and the `.expect.md` shows the TS and Rust builds producing the same output. Good.
- Suggested additions:
  - A fixture with an ASCII first character and a non-ASCII middle (e.g. `const aé한Ref = useRef(0)`) to cover the divergence above. With the current code I'd expect TS and Rust output to differ.
  - Optionally, a small `#[cfg(test)]` unit test for `is_ref_like_name` covering `ref`, `Ref`, `fooRef`, `$Ref`, `_Ref`, `한글Ref` and `a한Ref`. That's cheaper than fixtures for boundary cases like these.

## Other notes
- **Other byte slices:** I searched `compiler/crates` for similar `[..1]`/`[0..1]` slices on strings and found none. The only hit, `items[1..]` in `disjoint_set.rs`, slices a `Vec`, not a string. So this bug doesn't seem to exist elsewhere.
- **Performance:** no impact. `chars().next()` costs the same as the old slice.
- **Security:** nothing to flag. If anything the fix removes a crash that crafted input could trigger.
- **Conventions:** the `[rust-compiler]` title prefix and the `repro-` fixture naming match the repo's conventions.

# Review of PR #38025: [rust-compiler] Fix non-ASCII panic in is_ref_like_name

**Summary:** The fix is correct and small. I'd approve it. It fixes the panic, it's covered by a fixture, and the description is clear. My notes below are about one remaining difference from the TypeScript compiler and about how much the tests actually check.

## Correctness

**The fix itself is right.** `object_name[..1]` takes the first byte of the string, not the first character. When the name starts with a character longer than one byte, such as `한`, Rust panics because the slice cuts that character in half. `object_name.chars().next()` reads the first full character instead, so the panic is gone. `한` isn't an ASCII letter, `$` or `_`, so `한글Ref` now returns `false`. That matches TS.

**The `len() > 3` check is still fine.** `len()` counts bytes, while JS counts UTF-16 code units, so the two measure differently. It doesn't matter here: `ends_with("Ref")` already guarantees the last 3 bytes are ASCII, so `len() > 3` only means "at least one more character before `Ref`" in both languages.

## The Rust version still doesn't fully match the TS regex (not caused by this PR)

The TS regex is in `packages/babel-plugin-react-compiler/src/TypeInference/InferTypes.ts:785`:

```ts
const RefLikeNameRE = /^(?:[a-zA-Z$_][a-zA-Z$_0-9]*)Ref$|^ref$/;
```

It checks every character before `Ref`. The Rust function checks only the first one. Names like `a한Ref` or `foo·Ref` therefore give different answers:

| Name     | TS      | Rust (after this PR) |
|----------|---------|----------------------|
| `한글Ref` | `false` | `false` ✅            |
| `a한Ref`  | `false` | `true` ❌             |

The comment above the function says it matches the TS regex, and the PR description says the same, so this gap is easy to miss. This PR already touches this code, so it's a good place to close the gap:

```rust
fn is_ref_like_name(object_name: &str, property_name: &PropertyNameKind) -> bool {
    // ...
    if object_name == "ref" {
        return true;
    }
    let Some(prefix) = object_name.strip_suffix("Ref") else { return false };
    let mut chars = prefix.chars();
    chars
        .next()
        .is_some_and(|c| c.is_ascii_alphabetic() || c == '$' || c == '_')
        && chars.all(|c| c.is_ascii_alphanumeric() || c == '$' || c == '_')
}
```

This version also does without the byte-length check, which makes the empty-prefix case (bare `Ref`) clearer. If you'd rather keep this PR small, a follow-up issue or a `// TODO` noting the gap would also work.

As far as I can tell, the compiled output for this component would look the same whether or not `한글Ref` is treated as ref-like.
