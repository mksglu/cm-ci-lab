# Review: PR #345293, hide non-user-invocable agents from the Cloud picker

The PR is already merged. I reviewed the diff only. I did not check out the code or run the tests.

## Summary
The PR filters remote agents with `user_invocable === false` out of the Cloud picker. It keeps the full remote name set when matching local files, so hidden remote agents don't reappear as "missing from remote" warnings. It also parses local-only agent frontmatter with `PromptFileParser` to honor `user-invocable: false`.

## Strengths
- **Filtering happens at the picker boundary.** `getLocalCustomAgentFiles` still receives the unfiltered `remoteAgents`, so a hidden remote agent still matches its local file by name. This is the subtle part, and the PR gets it right.
- **Default visibility is preserved.** Using `!== false` means agents with `undefined` stay visible. `disable_model_invocation` is correctly treated as a separate concern.
- **Per-file errors are handled well.** Each file read sits in its own `try/catch` that logs a warning and continues, so one bad file no longer aborts discovery of the rest.
- **Parsing reuses `PromptFileParser`.** It doesn't add an ad-hoc regex, and the tests cover CRLF, trailing comments, nested keys and body-only mentions.
- **The tests are thorough.** They cover visibility defaults, case-insensitive matching, the case where every remote agent is hidden, remote fetch failure, and deleted or unreadable files.

## Issues and suggestions
1. **Sequential `await` in a loop.**
   - The new `readFile` runs once per local-only file inside the loop, so reads happen one after another.
   - The number of files is usually small, so this is minor.
   - `Promise.all` over the unmatched files would remove the serial latency. The picker is on the UI path, so it may be worth doing.
2. **Fresh `PromptFileParser` and `TextDecoder` on every iteration.**
   - Both are cheap, but they could be created once outside the loop.
3. **Warning-log wording.**
   - `Error reading local agent ...` is also logged for parse failures, not just read failures.
   - The `try` block mixes the two. Splitting it, or wording the message more generally, would make logs easier to diagnose.
4. **Deleted files are logged at `warn`.**
   - A file that vanishes between the directory listing and the read is a benign race.
   - The test names it as a case, but it logs the same warning as a real read failure. Consider a quieter level or special handling for `FileNotFound`.
5. **Local-versus-remote precedence is only tested one way.**
   - The test "keeps remote visibility authoritative" covers it, and the behavior looks right.
   - There is no test for a local agent with `user-invocable: false` whose name matches a visible remote agent. That is covered indirectly by the `visible.agent.md` case, so this is only a minor gap.
6. **Test mocks.**
   - The `vscode` mock gains a `FileSystemError` stub with a hard-coded `code`, and `TestGitService.activeRepository` becomes a real observable.
   - Both are reasonable, but they change shared test scaffolding. Check that other tests in the file still pass. CI presumably did.
7. **Case-sensitivity assumption in the filename-derived agent name.**
   - Matching lowercases the name on both sides, which is consistent.
   - The `id` used for local-only entries is the raw filename-derived name. This is unchanged from before and fine.

## Security and performance
- There are no security concerns. The change reads only workspace files under `.github/agents` and adds no new external input paths.
- Performance impact is limited to the extra file reads for local-only agents, as noted in point 1.

## Verdict
This is a clean, well-scoped fix with strong regression coverage. The points above are minor and non-blocking.

- **Good tests.** They cover default visibility, `disable_model_invocation` not hiding an agent, case-insensitive matching, remote-fetch failure, and deleted or unreadable files.

## Issues and suggestions

1. **Local file reads are sequential and happen on every options call (performance, minor).** Each unmatched local agent file is now read with `await readFile` inside a `for` loop. Previously only the directory listing was needed. This is probably fine for a handful of files, but `Promise.all` over the unmatched files would be cheap. It would also keep the order deterministic if the results are mapped in order. The options provider may run often, for example on auth or repo changes. Consider caching, or at least only reading files when the remote list doesn't already contain the name. That second part is already true.

2. **Read failures drop the warning entry silently (behavior question).** If a file can't be read, it is logged and omitted from `localOnly`. Hiding an unreadable file is defensible. The alternative is to fall back to showing it as a warning, since the old behavior showed it. The PR description says the omission is intended. A short code comment saying so would help.

3. **Frontmatter is trusted without a size or encoding guard (security, low).** `new TextDecoder().decode(content)` on a workspace file is fine, because files in the user's own workspace aren't an attack boundary here. A very large file would still be read fully into memory. This is negligible for agent files.

4. **Remote visibility is authoritative, and local frontmatter is ignored for matched names.** The tests assert this deliberately: `visible.agent.md` with `user-invocable: false` is still shown if the remote agent is visible. This is consistent. It would be worth stating in the method's doc comment, which currently only describes `localOnly`.

5. **Test mock changes are broad (nit).** The spec now mocks `vscode.window`, `FileSystemError` and `asRelativePath`, and adds a `getTreatmentVariable` stub. These are needed for the new tests but affect the whole file. Since the whole suite is run together, the changes are low risk.

6. **Test gap (minor).** Nothing tests a local file that has `user-invocable: false` and a remote agent that is missing the field. Nothing tests a malformed-frontmatter file, where the parser may return no header and the entry is shown. The `body-only` case partly covers the second.

## Verdict
This is a clean, well-tested bug fix with no correctness or security blockers. The suggestions are small improvements: parallelize the file reads, document the unreadable-file behavior, and extend the doc comment. LGTM.
