All of the `prerenderToStream` return sites now use that map as `digestErrorsMap`. The shared `reactServerErrorsByDigest` map stays in place for log recovery (#86500). The change is small and scoped, and it fixes the cause rather than hiding the symptom.

**Code quality**
- The explanatory comment at the declaration site is clear.
- `createReactServerErrorHandler` now ends in `spanToRecordOn?: any, renderErrorsByDigest?: Map`. Because of that, the call site has to pass an explicit `undefined` for the span. That's a minor smell. Passing an options object, or moving the new parameter ahead of `spanToRecordOn`, would read better. This is optional.
- There are about 7 near-identical `digestErrorsMap:` replacements. They look complete, but a future return path in `prerenderToStream` could easily use the wrong map again. A short note, or one shared variable, would reduce that risk. I did not check whether other `reactServerErrorsByDigest` consumers remain, for example in the dynamic/resume paths. It's worth a grep to confirm none of them also drive failure detection.

If that guard exists to skip certain error types, the new map now receives errors the old one did not. This should be fine here, because the map is only used to detect failures. Please confirm the guard doesn't filter out something that should not fail the build, such as postpone or dynamic-usage errors. Those usually return earlier in the handler, so this is likely OK.
- Nothing else in this diff worries me.

# REVIEW B

## Review of PR #100956: Fix prerendering of caught `'use cache'` errors

The PR is already merged and approved. I read the diff but didn't run the tests.

### Summary
The shared `reactServerErrorsByDigest` map records every error from `'use cache'` functions. It does this so the page renderer can recover the original errors for logging (#86500). Prerendering also used that map to decide whether the render failed. A `'use cache'` error that the page caught and handled therefore still failed the build or on-demand generation.

The fix adds a separate `renderErrorsByDigest` map. The page's RSC error handler fills it, and the prerender result's `digestErrorsMap` now reads from it. The shared map is left alone for logging. I think this is the right approach. It's a small change and the root cause is clear.

### Code quality
- **Scope:** Only the error handler plumbing changed. All 7 `digestErrorsMap` return sites in `prerenderToStream` were switched. I found no missed site in the diff, but I didn't search the rest of the file. It's worth grepping for other readers of `reactServerErrorsByDigest` in the prerender path.
- **Handler signature:** `createReactServerErrorHandler` now takes `undefined` for `spanToRecordOn` to reach the new trailing parameter. That works, but it's awkward. An options object would be cleaner if the parameter list grows again. Other callers don't pass the new parameter, so they behave as before.
- **Where the write happens:** `renderErrorsByDigest?.set(...)` runs after the early-return paths in the handler (for example, closed response and dynamic or bailout errors). I haven't verified that this ordering is the intended filter. Errors that return early never reach `renderErrorsByDigest`, which matches the old "should fail the render" semantics only if those errors were never meant to count. The tests don't cover this.
- **Comment:** The new comment explains why the second map exists, which helps.

### Potential bugs
- **Genuine render errors:** I see no regression here. Errors the page's own RSC renderer reports still land in the new map. Errors that are thrown only inside `'use cache'` and then propagate are reported by the same handler, so they should still fail the build. No test checks that an uncaught `'use cache'` error still fails. That would be worth adding. A negative test would show that the fix hasn't made failures silent.
- **Cache-component errors in other renderers:** Cached functions might run under a separate renderer, such as the cache-specific Flight render. If an uncaught error there reaches the page only through the cache result, I'm assuming it is rethrown into the page render. In that case the page handler sees it. I haven't confirmed this.

### Performance
There is no meaningful cost. It adds one `Map` allocation per prerender and one `set` per reported error.

### Security
No new request headers are read, so the internal-header filtering guidance doesn't apply. I have no other security concerns.

### Tests
- The new e2e fixture `test/e2e/app-dir/use-cache-caught-error` covers a build-time route (`static`, from `generateStaticParams`) and an on-demand route (`runtime`). In `next start` it also asserts the fallback is cacheable (`x-nextjs-cache: HIT`). That is good coverage of the regression.
- It uses a real fixture directory and `nextTestSetup({ files: __dirname })`, which matches the repo conventions.
- **Possible gap:** In the `runtime` case, the first fetch is a cache `MISS` or `STALE`. The `HIT` assertion on the second fetch should be stable, but I'd confirm it isn't flaky under deploy mode. The PR description says deploy tests are meant to run, so that is probably covered.
- **Missing coverage:** There is no dev-mode assertion beyond a 200 response and the fallback text. There is also no assertion that the caught error is still logged, which was the purpose of keeping the shared map (#86500). A check that the log is preserved would guard against someone later merging the two maps.
- The test and fixture names are fine. Normally I'd also expect it to be generated with `pnpm new-test`, but I can't tell that from the diff.

### Verdict
This is a focused, correct fix with a good regression test. My suggestions are optional follow-ups:
1. Add a negative test showing that an uncaught `'use cache'` error still fails prerendering.
2. Add a test that the caught error is still logged.
3. Consider an options object for `createReactServerErrorHandler` the next time its signature changes.
