# REVIEW A

**Review of PR 37046: distrust compromised eMudhra CAs.** The PR is already merged. This is a security-driven dependency bump, and I found no blocking problems.

**What's good**
- The security fix is clearly scoped. `rustls-webpki` is now required at `>=0.103.16`, so a plain `cargo update` can't resolve to a vulnerable version. The old `"0.103"` requirement allowed that.
- Bumping `webpki-roots` and `webpki-root-certs` to 1.0.10 removes the `emSign ECC Root CA - G3` root. The 0.26.11 wrapper makes the transitive users (reqwest, hyper-rustls) pick up the same bundle. The lockfile confirms this: `webpki-roots 0.26.11` depends on `1.0.10`.
- The ML-DSA migration moves to the stable `aws_lc_rs::signature::*` paths. It uses `to_pkcs8v1()` to keep the existing PKCS#8 export format. That avoids a silent change in exported key bytes, which could break WebCrypto interop.

**Concerns and suggestions**
1. **Two `aws-lc-sys` versions in the lockfile.** `aws-lc-rs` 1.18.2 pulls in `aws-lc-sys 0.46.0`. `deno_crypto_provider` and `deno_crypto` still use the workspace pin `0.40.0` (`prebuilt-nasm`). Consequences:
   - Two copies of AWS-LC get compiled and linked, which increases build time and binary size.
   - There is a symbol-collision risk. `aws-lc-sys` normally uses a version-specific symbol prefix, so this should be safe, but it's worth confirming on all platforms (Windows, macOS, and Linux musl).
   - The `deno_crypto` code that calls `aws-lc-sys 0.40` directly could behave differently from `aws-lc-rs`.
   - Aligning the workspace `aws-lc-sys` pin with 0.46 would fix this. If that isn't possible, say why in a comment. Also check that `prebuilt-nasm` is still enabled for the 0.46.0 copy on Windows. The new lock entry lists `cc`, `cmake`, `dunce`, `fs_extra` and `pkg-config` as dependencies, with no prebuilt-nasm artifacts. That suggests Windows builds of that copy may need NASM or the prebuilt objects.
2. **`webpki-root-certs` 0.26 → 1.0 is a semver-major jump.** The PR says `cargo check` passed for `deno_tls` and `deno_node`. Confirm that other consumers (for example `deno_native_certs` and the `deno_node` TLS root-cert APIs such as `tls.rootCertificates`) still produce the same output format. A spec or unit test asserting that `tls.rootCertificates` no longer contains the eMudhra root would be a good guard.
3. **No regression test.** Nothing checks the actual security behavior: a chain through a distrusted eMudhra key being rejected, or the root being absent from the bundle. A small unit test in `ext/tls` or `tests/unit_node` could check that the bundle doesn't contain `emSign ECC Root CA - G3`. That would catch a future downgrade or a lockfile regression.
4. **Scope.** The PR mixes the TLS fix, the ML-DSA API migration, and the `deno_graph` bump. The ML-DSA change is justified, since newer `aws-lc-rs` makes the old API produce deprecation errors under `-D warnings`. Even so, CLAUDE.md asks for minimal, focused changes, so splitting them would have been cleaner. The PR description also has a stray "Bump `deno_graph`…" paragraph, which looks like it came from the squash of a separate commit.
5. **Minor.** The `to_pkcs8v1()` call is formatted across multiple lines. Confirm that `tools/format.js` produced this. The PR says rustfmt was checked, so it is probably fine.

**Performance and security**
- There is no runtime performance impact apart from the build and binary-size effect of the duplicate `aws-lc-sys`.
- The security effect is positive. Cross-signed paths through the eight compromised keys are now rejected by the verifier, and the root is no longer in the bundle.

**Verdict:** Approve. The main follow-ups are to reconcile the duplicate `aws-lc-sys` versions and to add a regression test for the distrusted root.

# Review of PR 37046: distrust compromised eMudhra CAs

The PR is already merged. The change is mostly a dependency bump with one small code migration, and I found no blocking problems.

## What changed
- `rustls-webpki` goes to a minimum of 0.103.16, which rejects the eight compromised keys.
- `webpki-roots` and `webpki-root-certs` go to 1.0.10, and the 0.26 line is pinned to the 0.26.11 shim.
- `aws-lc-rs` goes to 1.18.2.
- `deno_graph` goes to 0.111.1.
- `ext/crypto/mldsa.rs` moves from `aws_lc_rs::unstable::signature` to the stable `aws_lc_rs::signature` paths. It also switches `to_pkcs8()` to `to_pkcs8v1()`.

## Observations

**1. Two `aws-lc-sys` versions in the lockfile (medium).**
- `aws-lc-rs` now pulls `aws-lc-sys 0.46.0`.
- The workspace pins `aws-lc-sys = "0.40.0"` with `prebuilt-nasm`, and that version is used by `deno_crypto_provider` and `deno_node`.
- This means two copies of AWS-LC are compiled and linked: one through `aws-lc-rs`, one used directly.
- It increases build time and binary size.
- It could cause symbol-prefix or version confusion if the C symbols aren't prefixed. `aws-lc-sys` does prefix them by version, so linking should work.
- It also leaves `rustls-webpki` and `rustls` verification on a different AWS-LC than the direct FFI code in `deno_crypto_provider` and `deno_node`.
- I'd follow up by bumping the workspace `aws-lc-sys` to 0.46 so the lockfile has one copy.
- The `prebuilt-nasm` feature needs to be checked on the new version. On Windows, `aws-lc-sys 0.46.0` in the lockfile may not get that feature enabled.

**2. The PKCS#8 export format (low, worth a test).**
- `to_pkcs8v1()` is meant to preserve the old output.
- The ML-DSA PKCS#8 and seed export is spec-sensitive: WebCrypto expects the seed-only form.
- A round-trip or known-answer test for `exportKey("pkcs8")` on ML-DSA-44, ML-DSA-65 and ML-DSA-87 would guard against a silent format change in future aws-lc-rs bumps.
- I couldn't tell from the diff whether such a test exists. The existing WPT and unit tests may cover it.
- The PR description says only `cargo clippy` and `cargo check` were run locally, with the rest left to CI.

**3. No regression test for the distrust (low).**
- Nothing in the diff checks that the `emSign ECC Root CA - G3` root and the compromised-key paths are actually rejected.
- A unit test in `deno_tls` could assert that the root is absent from the bundled store.
- That would also catch a future dependency downgrade or an accidental `webpki-roots` pin.
- Dependency-only security fixes often skip this, so it's a nice-to-have.

**4. `webpki-root-certs` crossing 0.26 → 1.x (low).**
- This is a semver-major jump.
- The `deno_tls` and `deno_node` call sites weren't touched, so the API is evidently compatible.
- The `cargo check` for those two crates in the PR description covers this.

**5. Scope and hygiene (nit).**
- The `deno_graph` bump to 0.111.1 is bundled in. Per CLAUDE.md, changes should stay minimal.
- It's justified here because the same security update flows through it, and the description says so.
- The `rustls-webpki = "0.103.16"` floor is the right way to force the fix.
- The `webpki-roots 0.26.11` shim is cleverly used to push `reqwest` and `hyper-rustls` onto the 1.0.10 bundle, so there's only one root list in the build.

## Security
- The change is a positive security fix. It rejects both the roots and the cross-signed paths.
- I'd confirm that the `deno_native_certs` and system-store paths (`--tls-ca-store=system`) aren't affected. The bundled Mozilla store is the only thing updated here, so users on the system store depend on their OS vendor for the same distrust.
- It would be worth mentioning that in the release notes.

## Verdict
This is a reasonable and correct fix. The follow-ups I'd suggest are consolidating `aws-lc-sys` to one version, and adding a small test for the distrusted root and the ML-DSA PKCS#8 export.
