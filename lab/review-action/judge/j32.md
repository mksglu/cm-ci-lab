# REVIEW A

# Review of PR #345283: run `--runList` in parallel workers

This PR is already merged. I read the diff and the description but did not run anything. Overall the change looks sound, and I found no blocking bugs.

## What looks good

- **The worker-count rule is small and documented.** `getWorkerCountForFiles` in `test/unit/parallel.ts` uses `max(1, min(count, files, max(2, floor(files/75))))`. It is a pure function with a named constant, and its comment explains why the minimum is 2. The thresholds match the measurements (1 file gives 1 worker, 2–224 give 2, and 300 or more give 4).
- **The "Running N test files…" message prints once.** The process that starts the workers prints it, and `!worker`, `!opts.workerDir` and `!args.worker` guard the worker processes. Each runner keeps its own guard.
- **`findTestFiles` is shared between Electron's main process and the renderer.** The old logic moved from `renderer.js` into `test/unit/electron/testFiles.ts`, so the two paths cannot drift apart.
- **The browser runner keeps its browsers sequential.** `workersApply` keeps them one at a time even when the cap or a short list leaves only one worker. The concurrent path passes `1`, which matches the behaviour without `--workers`.
- **Excluding `--runGlob` is justified.** The PR explains that the node.js integration tests are selected with `--runGlob`.
- **The docs are updated everywhere.** That covers the three help texts, `test/unit/README.md` and the unit-tests skill.

## Potential issues

1. **Electron single-worker path (`test/unit/electron/index.js`, `firstRunArgs = { ...args, run: files }`).** This is clever but a little fragile.
   - It passes compiled paths such as `vs/a.test.js` through `--run`. The renderer strips `src/` and `.js`/`.ts`, so it works today.
   - It also silently depends on nothing else reading `args.run`. I grepped the main process and only the bare-file handling and `workersApply` use it, so it is fine for now. A comment on that coupling would help.
   - `args.run` is a truthy empty array when `files.length === 0`. `loadModules([])` handles that, but the "0 files" case is not tested explicitly. The node and browser runners exit early in that case, so Electron behaves differently.
2. **Duplicate globbing.** Every Electron worker and every node.js worker re-globs the output tree, and the main process globs it once more. This is small next to process startup, and the PR accounts for the startup cost.
3. **Node `findTestModules` swallows the glob error differently than before.** It now rejects, and the caller prints the error and exits 1. Previously `files` was undefined and the loop threw. The new behaviour is better, but it is a behaviour change.
4. **The `FILES_PER_WORKER = 75` threshold is heuristic.** Per-worker cost on the 5-core macOS and 8-core Windows CI runners is unmeasured. The PR says so under "Not covered", and the repo's own PR checks run all tests, so they do not exercise `--runList` with workers. Watching selected-run durations on the first PRs after merge is the right follow-up.
5. **Electron's `listedTestFiles?.catch(() => {})` pattern.** It prevents an unhandled-rejection warning and the real error is reported at `ready`. That is correct, but a one-line comment on the "awaited later" intent is already there, and that is enough.

## Performance

The measurements are convincing. At 300 files, node.js went from 61 s to 43 s, Electron from 27 s to 16.5 s, and Chromium from 29 s to 17 s. The overhead for 10 files is up to about 1–3 s, which the "at least 2 workers" rule accepts to protect against one slow file. The PR also notes that `agentService.test.ts` alone sets a floor of about 38 s for the node.js case.

No concerns. The change only affects local test tooling. The `--runList` contents are read as file paths and matched against globbed output, not executed.

- The PR has extensive manual validation: 363 of 364 runs, reruns, `.only` and `--tfs`.
- There is no automated test for `getWorkerCountForFiles`. It is a pure function with edge cases (0, 1, 2, 149, 150, 224, 225 and 300 files, and `count` of 2 or 3), so a small unit test would be cheap.
