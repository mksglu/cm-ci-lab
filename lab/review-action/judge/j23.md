# REVIEW A

## Review of PR #100956: Fix prerendering of caught `'use cache'` errors

The PR is already merged and approved. I found no blocking issues.

### Summary
Errors from `'use cache'` functions are recorded in the shared `workStore.reactServerErrorsByDigest` map, which exists so errors can be logged (#86500). `prerenderToStream` also used that map as `digestErrorsMap` to decide whether the render failed. A page that caught a cached function's error therefore still failed the build or on-demand generation.

The fix adds a render-local `renderErrorsByDigest` map. `createReactServerErrorHandler` populates it, and the prerender result uses it as `digestErrorsMap`. The shared map is unchanged, so logging still works.

### Code quality
- The change is small and targeted. The comment in `app-render.tsx` explains why there are two maps.
- All seven `digestErrorsMap:` return sites are switched, including the error-shell paths (`errorHtmlStream`, `errorServerResult`). I counted the sites in the diff and didn't see one left on the old map.
- The new `renderErrorsByDigest` parameter is optional and comes after `spanToRecordOn`. The call site has to pass `undefined` positionally to reach it. An options object would read better if this signature grows again, but the churn isn't worth it here.
- `renderErrorsByDigest?.set(...)` runs after the same early-return filters as the shared map. Errors that were already skipped, such as postpone and bailout errors, are still skipped.

### Potential issues to consider
- **Placement of the `set`:** the new map is written after the `reactServerErrors.set` branch. I haven't checked whether that branch has an early `return` or a condition that could skip the new `set` for some error types, such as the dev-only or digest-present cases. The diff context suggests it doesn't, but it's worth confirming.
- **Cached function errors that are not caught:** if the page doesn't catch the error, it still propagates through the page's RSC renderer and reaches `onError` there. The failure detection should still work. The test only covers the caught case, so an uncaught-error regression test would show that the build still fails. Existing `use-cache` suites may already cover this.
- **Other consumers of `reactServerErrorsByDigest`:** other places might read the shared map to detect failures, for example the dynamic or runtime prerender paths, or the `'use cache'` fill and resume-data-cache paths. A quick grep for those would confirm that nothing else has the same bug.

### Performance
The cost is one extra `Map` per prerender and one `Map.set` per error. This is negligible.

### Security
No new request headers are read, and nothing touches `INTERNAL_HEADERS`. There are no concerns.

### Tests
- The fixture follows the repo conventions: a real fixture directory, `nextTestSetup({ files: __dirname })`, and `cacheComponents: true`.
- It covers both build-time prerendering (`static`, via `generateStaticParams`) and on-demand generation (`runtime`).
- Checking for `x-nextjs-cache: HIT` under `isNextStart` verifies that the fallback is actually cacheable, not just rendered.
- Gaps:
  - The `HIT` assertion on `runtime` depends on the first fetch having populated the cache, which should hold for ISR. It could be flaky in deploy mode, where the cache header can differ. The PR says deploy tests were run, so this is probably fine.
  - In dev mode there is no cache assertion, which is expected.
  - The test doesn't assert that the error is still logged (the #86500 behavior this change preserves). An `expect(next.cliOutput)` check for the error message in dev or build output would guard against regressing the logging path.
  - The fixture isn't checked under `cacheComponents: false`. This is probably fine, since `'use cache'` requires it.

### Verdict
This is a clean, minimal fix with a good regression test. The optional follow-ups are a logging assertion in the test and an uncaught-error test.

# REVIEW B

## Review of PR #100956: Fix prerendering of caught `'use cache'` errors

The PR is already merged. The change looks correct and well scoped.

### What it does
`reactServerErrorsByDigest` on the work store is shared. It is used for logging (#86500), and it now also records errors thrown inside `'use cache'` functions. Prerendering was reusing the same map to decide whether the render failed. A page that caught a cache error and rendered a fallback therefore still failed the build or on-demand generation. The PR adds a per-render `renderErrorsByDigest` map. `createReactServerErrorHandler` fills it in, and the prerender result's `digestErrorsMap` now reads from it. The shared map is left alone for logging.

### Code quality
- The fix is small and targeted, and the comment on the new map explains why it exists.
- All 7 `digestErrorsMap` return sites in `prerenderToStream` were switched. I checked the diff and none were missed. Each of those sites also needs the new map for the `ssrErrors` and `digestErrorsMap` consumers to stay consistent.
- Nit: the handler now takes `undefined` as a positional placeholder for `spanToRecordOn`. That is slightly awkward, and the signature is growing long. Moving to an options object would be cleaner if more parameters get added. It's not worth blocking on.
- Nit: the new parameter is optional, so a future caller could forget it and silently fall back to the old behavior. This is fine because only the prerender path needs it. The doc comment on the parameter could say "used for prerender failure detection".

### Potential bugs
- The shared map is only written under a condition (`reactServerErrors.set(...)` just before the new line). The new map is written unconditionally. The condition isn't visible in the diff. If it excludes some errors (for example digest-bearing Next.js control-flow errors), the new map may now contain entries the old one skipped, and those would count as render failures. I'd check that the unconditional `set` matches the old semantics for redirect, not-found and postpone errors. These likely never reach this point, since the handler returns early for them, but I couldn't confirm that from the diff.
- Errors from `'use cache'` that are not caught and propagate into the page's RSC render are still reported through the handler. They are recorded in `renderErrorsByDigest` and still fail the build, which is the right behavior.

### Performance
Negligible. It is one extra `Map` per prerender, and `set` is called once per error.

### Security
No concerns. No new request headers are read.

### Test coverage
- The test covers build-time prerendering (`static`, via `generateStaticParams`) and on-demand generation (`runtime`). It also checks that the fallback is cached (`x-nextjs-cache: HIT`) in start mode. This covers the regression well.
- It uses a real fixture directory and `nextTestSetup({ files: __dirname })`, as AGENTS.md asks.
- Possible gaps:
  - Nothing covers PPR / `cacheComponents` with a dynamic shell. `cacheComponents: true` is set, so the PPR path is partly exercised, but the error-recovery branches (`errorHtmlStream`, around lines 10700 and 10880) are not clearly hit.
  - Nothing checks that an uncaught `'use cache'` error still fails the build. A negative test would guard against the fix being too permissive.
  - The `isNextStart` cache assertion on the first `/runtime` fetch assumes the response is a HIT after one request. Wrap it in `retry()` if that proves flaky. A prerender that finishes in the background could race with the second fetch.

### Verdict
Approve. The fix is correct and low risk. The only follow-ups I'd suggest are a negative test for uncaught cache errors and checking the unconditional `set` against the old conditional one.
