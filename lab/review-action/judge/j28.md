# REVIEW A

## Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`

**Verdict:** Approve. The fix is correct and minimal. I only read the diff and did not run the tests. The PR is already merged.

### The fix (`infer_types.rs`)
- `object_name[..1]` slices by byte. It panics when byte 1 is not a char boundary, which is the case for any name starting with a multi-byte character such as `한글Ref`.
- `object_name.chars().next()` reads the first Unicode scalar safely. A non-ASCII first char fails `is_ascii_alphabetic() || '$' || '_'` and returns `false`.
- `false` matches the TS behavior. The TS regex is roughly `/^[a-zA-Z$_].*Ref$/`, which also rejects non-ASCII first characters.
- `object_name.len() > 3` is a byte length. That is harmless here: a name that is too short in bytes is also too short in chars, and the first-char check handles the rest.
- The `ends_with("Ref")` check is char-boundary safe.

### Test coverage
- The fixture reproduces the reported panic: a `*Ref` name starting with Hangul, accessed via `.current`.
- The `.expect.md` shows clean compilation and the eval output is OK.
- The PR says both `yarn snap` and `yarn snap --rust` pass. It also says the Rust-port script passes and `cargo fmt` is clean.

**Suggestions (non-blocking):**
1. Add a Rust unit test for `is_ref_like_name`, covering `"ref"`, `"fooRef"`, `"$Ref"`, `"_Ref"`, `"한글Ref"`, `"Ref"` and an emoji-prefixed name. It would test the function directly. The fixture goes through the whole pipeline, and a variable initialized by `useRef` may get its ref type from other inference before this heuristic matters. It would also guard against regressions in this one function.
2. Do a quick audit for similar byte-slicing patterns in the Rust crates, such as `[..1]`, `[..n]` or `.as_bytes()[0]` on identifier strings. Panics on non-ASCII identifiers are likely to show up elsewhere in the port. For example: `grep -rnE '\[\.\.[0-9]+\]|\[[0-9]+\.\.' compiler/crates`.
3. Optionally add a second fixture where the name starts with an ASCII letter and contains non-ASCII characters later (e.g. `aé Ref`-style names like `éRef` vs `aéRef`). This confirms the positive path still works.

### Other concerns
- **Performance:** negligible. `chars().next()` is O(1).
- **Security:** a panic on user-controlled identifiers is a robustness and DoS-style issue for build tooling, and this fix removes it. There are no new concerns.
- **Style:** it follows the surrounding code, and the diff is small and focused.

## Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`

**Verdict: looks good.** The PR is already merged and approved. I found no blocking issues.

### The fix
- The old `object_name[..1]` slices by byte. If the name starts with a multi-byte character such as `한`, the slice lands inside the character and panics. The change to `object_name.chars().next()` reads the first Unicode scalar instead, so it can't panic.
- Behavior now matches the TS regex. Names that start with a non-ASCII character fail the `is_ascii_alphabetic() || '$' || '_'` check and return `false`.
- The change is minimal and idiomatic. There is no extra allocation, and `chars().next()` is O(1).
- I grepped `compiler/crates` for other `[..1]` or `[0..1]` byte slices and found none. This bug doesn't appear to be repeated elsewhere in this form.

### Minor suggestions (non-blocking)
1. **Length check:** `object_name.len() > 3` counts bytes, not characters. This is harmless here because `ends_with("Ref")` plus a first-character check make the result the same as the TS regex. For `한Ref`, which is 6 bytes, the length check passes and the first-character check then rejects it correctly. A short comment saying the byte length is deliberate would help later readers.
2. **Test coverage:** The fixture covers the panic path, a non-ASCII leading character with `.current` access. A Rust unit test for `is_ref_like_name` would be cheaper and more targeted. It could cover `"한글Ref"` → false, `"myRef"` → true, `"$Ref"` and `"_Ref"` → true, `"ref"` → true, and `"Ref"` → false (length). A fixture where the non-ASCII character is not first, such as `aé Ref`, or an identifier like `éRef` would also exercise the boundary.

4. **Fixture naming:** `repro-ref-like-name-non-ascii` follows the existing `repro-*` convention.

### Performance and security
