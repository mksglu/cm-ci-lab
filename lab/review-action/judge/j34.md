# REVIEW A

**Review of PR #100935: store `ChunkGroupInfo::chunk_groups` as a `Vec`**

This PR is already merged and approved. I found no blocking issues and have a few small suggestions.

**What it does**
- `chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`.
- `IndexSet` compares as a set, so a recomputation that only renumbered the chunk groups compared equal to the old value. Turbo-tasks then kept the old cell contents. That left `module_chunk_groups` (bitsets) and `chunk_group_indices` on the new numbering while `chunk_groups` stayed on the old one, so modules could resolve to another entry's chunk groups.
- Using a `Vec` makes equality order-sensitive, which is correct because the index is semantically meaningful.

**Code quality**
- The construction site in `chunk_group_info.rs` (~line 968) already ends in `.collect()`, so the target type is inferred and needs no change. Making the field type the only change keeps the diff small.
- The `get_index(idx)` calls become `get(idx)` in `module_batches.rs` and the test helper, and the indexing at the other usage sites already worked on a `Vec`.
- Dropping `#[bincode(with = "turbo_bincode::indexset")]` is right, since a `Vec` uses the default encoding. I haven't checked whether anything depends on the old serialized layout. A persisted-cache format change should be covered by the usual cache versioning.
- The doc comment states the invariant and the reason. That should stop someone from "optimizing" it back to a set.

**Remaining risk**
- `chunk_group_keys` is still an `FxIndexSet<ChunkGroupKey>` marked `#[turbo_tasks(unsafe_ignore)]`, so it is excluded from equality. It has the same numbering-sensitivity problem. It is safe only while some other order-sensitive field changes whenever the order changes, and `chunk_groups` now does that. The PR description says the author is auditing other places, so this is probably covered. A comment on the field noting the dependency would help.
- `IsolatedMerged` and `SharedMerged` store `entries: merged_entries.into_iter().collect()`. If that is a set-like collection, it may have the same equality issue. It is worth checking as part of the audit.
- `Vec` loses the O(1) lookup by value that `IndexSet` gave. `chunk_group_indices` and `chunk_group_keys` cover the key-to-index direction, and no call sites appear to use `get_index_of` on `chunk_groups`.

**Performance**
- A `Vec` is lighter than an `IndexSet`: no hashing and less memory per entry.
- Equality is now O(n) with element comparison. That is the same order as before, and it is the cost of correct semantics.

**Security**
- No concerns.

**Tests**
- `test_chunk_group_info_reordered_entries` is a good regression test. It builds two entries with async children, reverses the entry order, and checks that the chunk groups reported per module are unchanged. Without the fix, the second read would map modules to the wrong groups.
- It uses `read_strongly_consistent` and `State` to force recomputation, which is the right way to exercise cell-equality behaviour.
- It checks only `page1.js` and `lazy1.js`. Including `page2.js` and `lazy2.js` would cover the swap symmetrically, though one side is enough to catch the bug.
- It is an inline unit test rather than an execution test. That is reasonable here, because the behaviour depends on turbo-tasks incremental recomputation.

**Verdict:** a correct, minimal fix with a well-targeted regression test.

# REVIEW B

# Review of PR #100935: store `ChunkGroupInfo::chunk_groups` as a `Vec`

This PR is already merged and has two approvals. I reviewed the diff only. I did not check out the branch or run the tests.

## Summary
`ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. `IndexSet` equality ignores order. If a recomputation only renumbered the chunk groups, the new value compared equal to the old one. The cell then kept the old order, while `module_chunk_groups` (bitsets) and `chunk_group_indices` used the new numbering. Modules could then resolve to another entry's chunk groups. A `Vec` compares in order, so the cell updates whenever the numbering changes.

## Code quality
- The fix is minimal and targets the cause. The doc comment explains why it must be a `Vec`, and that comment will help the next person who is tempted to switch back.
- Dropping `#[bincode(with = "turbo_bincode::indexset")]` is correct. `Vec<ChunkGroup>` uses the default bincode encoding, so no custom serializer is needed.
- The call sites change from `get_index(idx)` to `get(idx)` in `module_batches.rs` and in the test helper. They behave the same.

## Potential issues
- **Lost deduplication.** `IndexSet` prevented duplicate chunk groups, and a `Vec` does not. I'm assuming the builder still dedups through a separate map or set before it produces the `Vec`. It would be worth confirming that `chunk_group_indices` and `chunk_group_keys` are the only dedup path. The preceding commit, `62bf191bef`, probably covers this.
- **`chunk_group_keys` is still an `IndexSet`.** It is marked `unsafe_ignore`, so it doesn't take part in equality. That is fine. But the PR description says other places may have the same risk, so any other set-typed fields that feed index-based lookups deserve an audit. The author says they are already looking.

## Performance
Neutral to slightly positive. Index lookups and iteration on a `Vec` are cheaper than on an `IndexSet`. Equality is now an ordered element-wise comparison, which is about the same cost.

## Security
No concerns.

## Test coverage
The new `test_chunk_group_info_reordered_entries` is a good regression test:
- It builds two entries that each have an async child, then flips the entry order with a `State<bool>` and recomputes.
- It asserts that the chunk groups reported for `page1.js` and `lazy1.js` stay correct after the reorder.
- It uses `read_strongly_consistent`, which exercises the invalidation path, so it should fail without the fix.

Minor nits:
- The `_ => "other"` arm would hide new `ChunkGroup` variants. An exhaustive match, or a panic on unexpected variants, would be stricter.
- The test checks the `Entry` and `Async` kinds only. The repo guidance prefers integration-style tests, and this one is close to that because it goes through the real graph and `chunk_group_info()`, so it fits.

## Verdict
LGTM. The change is correct, small, and well tested. The one follow-up is to confirm that nothing relied on `IndexSet` deduplication at the construction site.
