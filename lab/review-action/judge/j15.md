# REVIEW A

# Review of PR #37046: distrust compromised eMudhra CAs

The PR is already merged, so this review is retrospective. I only read the diff and the PR description. I did not build the code or run any tests.

## Summary
The PR does four things:
- It bumps `rustls-webpki` to 0.103.16, `webpki-roots` and `webpki-root-certs` to 1.0.10, and `aws-lc-rs` to 1.18.2.
- It moves the ML-DSA code from `aws_lc_rs::unstable::signature` to the stable `aws_lc_rs::signature` paths.
- It switches PKCS#8 export to `to_pkcs8v1()`.
- It bumps `deno_graph` to 0.111.1.

The change is small and focused, and the security motivation is sound.

## Observations

**Dependency and lockfile changes**
- The `rustls-webpki` floor of `0.103.16` in `Cargo.toml` is a good choice. The fix can't be silently lost to a lockfile regeneration.
- `webpki-roots` 0.26.11 is a thin wrapper over 1.0.10. That means reqwest and hyper-rustls, which are still on 0.26, also get the trimmed root set.
- The lockfile now has `aws-lc-sys` at both 0.40.0 and 0.46.0.
  - The workspace pins `aws-lc-sys = "0.40.0"` with `prebuilt-nasm`, and that pin feeds `deno_crypto_provider` and `deno_node`.
  - `aws-lc-rs` 1.18.2 pulls in 0.46.0.
  - Two copies of AWS-LC will be compiled and linked, which adds build time and binary size.
  - Two copies also risk duplicate-symbol problems. The `aws-lc-sys` crates use versioned symbol prefixes, so that is probably safe, but it deserves a check.
  - There is also a quiet inconsistency. `deno_crypto_provider` and `deno_node` call into 0.40.0 directly, while everything going through `aws-lc-rs` uses 0.46.0. The 0.46.0 copy also lacks the `prebuilt-nasm` feature on Windows, unless feature unification enables it.
  - I'd suggest a follow-up that bumps the workspace `aws-lc-sys` pin to 0.46 so there is one copy, if the APIs allow it.
- The `webpki-root-certs` jump from 0.26 to 1.x is a major version bump. I couldn't see its call sites in this diff. The PR says `cargo check` was run on `deno_tls` and `deno_node`, which is reassuring, but I'd confirm that nothing else in the tree uses the old `CertificateDer` types.

**ML-DSA change (`ext/crypto/mldsa.rs`)**
- Moving to the stable paths is correct.
- Using `to_pkcs8v1()` to keep the existing export format is a sensible way to avoid a behavior change. The PR description says `to_pkcs8()` is deprecated. I believe the newer default may emit a different PKCS#8 version or structure, so keeping `v1` here is the safe choice.
- A one-line comment explaining why `v1` is pinned would help the next person who sees `to_pkcs8v1()` and wonders why.
- Existing WebCrypto and node tests for ML-DSA exports should cover this. I didn't see one in the diff that checks the exported PKCS#8 bytes against a known vector. If none exists, that's worth adding.

**Test coverage**
- The diff has no test for the actual security behavior, meaning that a chain through one of the eight compromised keys is rejected.
- That is understandable. A test would need fixtures for the compromised keys, and the real guarantee comes from `rustls-webpki`.
- A cheap regression guard would still help. For example, assert that the `emSign ECC Root CA - G3` root isn't in the bundled root set.
- The `Cargo.toml` version floors are the main protection against a downgrade.

**Process notes**
- The PR bundles the `deno_graph` bump with the TLS change. It's justified, because `deno_graph` also carries the TLS fix. It is arguably a separate commit, but it's acceptable for a security fix.
- The description is thorough, discloses AI assistance, and lists the validation commands run.

## Verdict
This is a good, well-scoped security fix. The things I'd follow up on are:
1. Unify `aws-lc-sys` to a single version, or confirm that two copies are intentional.
2. Add a comment on `to_pkcs8v1()`.
3. Add a small regression test for the removed root, or for the ML-DSA PKCS#8 export format.

# Review of PR 37046: distrust compromised eMudhra CAs

I read the diff only. I didn't build it or run any tests. The PR is already merged, so this is a retrospective review. Overall it looks correct and appropriately scoped.

## What it does well
- **Targeted security fix.** It bumps `rustls-webpki` to 0.103.16, which rejects the compromised keys, including cross-signed paths. It also moves `webpki-roots` and `webpki-root-certs` to 1.0.10, which drops `emSign ECC Root CA - G3`.
- **Minimum versions are pinned.** `rustls-webpki = "0.103.16"` and `webpki-roots = "1.0.10"` in `Cargo.toml` stop a future lockfile regeneration from silently resolving to a vulnerable version.
- **Transitive trust bundle is covered.** `webpki-roots` 0.26.11 is a thin wrapper over 1.0.x. As a result, reqwest and hyper-rustls (via `deno_graph`'s dependency chain) also pick up the fixed root set.
- **ML-DSA migration is minimal.** The code moves from `aws_lc_rs::unstable::signature` to the stable paths. It uses `to_pkcs8v1()`, which the PR says preserves the existing PKCS#8 export format.

## Concerns and suggestions

1. **Two `aws-lc-sys` versions in the lockfile (0.40.0 and 0.46.0).**
   - `aws-lc-rs` 1.18.2 pulls in `aws-lc-sys` 0.46.0.
   - The workspace still pins `aws-lc-sys = "0.40.0"` with `prebuilt-nasm`. `deno_crypto_provider` and `deno_node` link it directly.
   - This means two copies of AWS-LC get compiled and linked. That adds build time and binary size.
   - It could also cause duplicate-symbol problems, although the sys crates normally use a version-mangled `links` prefix, so that is probably fine.
   - Mixed versions are also a correctness risk. `aws-lc-rs` and the directly used `aws-lc-sys` FFI would then run on different AWS-LC builds.
   - It would be worth checking whether `aws-lc-sys` can be bumped to 0.46 in the workspace so the lockfile has one copy. If that isn't possible, add a comment in `Cargo.toml` explaining why.
   - The 0.46.0 entry in the diff also lacks the `prebuilt-nasm` feature, which matters on Windows builds. Verify that Windows CI covered this.

2. **Major-version bump of `webpki-root-certs` (0.26 to 1.0).**
   - The diff shows no API changes needed in callers. `cargo check -p deno_tls -p deno_node` passed per the PR description, which supports that.
   - Confirm that the type of the exported cert list is unchanged. In 1.0 it is `CertificateDer<'static>` from `rustls-pki-types`. A mismatch with the `rustls-pki-types` version used elsewhere would show up as a compile error, so CI should catch it.

3. **Test coverage.**
   - There are no tests. That is understandable for a dependency bump, but a regression test would still help. For example, a unit or spec test could assert that `emSign ECC Root CA - G3` is absent from the `tls.rootCertificates` / `deno_tls` root store.
   - There is also no test that the ML-DSA PKCS#8 export is byte-identical before and after the `to_pkcs8v1()` switch. The existing WebCrypto ML-DSA export tests probably cover this. It would be worth confirming that they ran in CI, since the PR notes only partial local validation.

4. **Scope and process.**
   - The PR combines three changes: the TLS fix, the ML-DSA API migration, and the `deno_graph` bump. The CLAUDE.md guidance prefers minimal changes with no drive-by edits.
   - The ML-DSA migration is justified here, because the `aws-lc-rs` bump deprecates the unstable API and CI uses deny-warnings. It is still worth stating explicitly in the commit message.
   - The `deno_graph` bump arrived as a late addition to the description. It is related, since it carries the same TLS fix, but it would read better as a clearly labelled section.

5. **Minor.**
   - `pkg-config` jumped from 0.3.30 to 0.3.34. This is expected as the new `aws-lc-sys` requires it, and it is low risk.
   - The `to_pkcs8v1()` call is formatted over multiple lines. `rustfmt --check` was run per the PR description, so this is fine.

## Security
- The change addresses the compromise as intended. No new attack surface is introduced.
- One follow-up to consider is `deno_native_certs` / system root stores. A user whose OS trust store still includes the compromised CAs is not protected by the bundled-root changes. The `rustls-webpki` key-blocklist check should still reject the compromised keys in that path, and this is worth confirming.

## Verdict
Approve-quality. The main thing I'd follow up on is the duplicated `aws-lc-sys` versions. A regression test for the removed root would be a worthwhile addition.
