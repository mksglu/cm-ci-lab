# REVIEW A

**Review of PR #100935: store `ChunkGroupInfo::chunk_groups` as a `Vec`** (already merged and approved; I read the diff only and didn't build or run it)

**Summary:** `ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. `IndexSet` equality ignores order, so if the graph entries were reordered, the recomputed value compared equal to the old one. Turbo-tasks then kept the stale cell. `module_chunk_groups` (bitsets) and `chunk_group_indices` were recomputed with the new numbering, so indices pointed at the wrong chunk groups. A `Vec` makes equality order-sensitive, which is what the data needs.

**Code quality**
- The change is small and correct. The doc comment explains why it must be a `Vec`, which will stop someone from "optimizing" it back to a set.
- `get_index(idx)` becomes `get(idx)` in `module_batches.rs` and in the test helper. Both are equivalent.
- `#[bincode(with = "turbo_bincode::indexset")]` is removed. A plain `Vec` serializes natively, so that's right.
- The neighbouring `chunk_group_keys: FxIndexSet<ChunkGroupKey>` is marked `unsafe_ignore`, so it doesn't take part in equality. That's fine, but the same order-sensitivity risk applies if its order ever matters to consumers. The author says they're checking other places. I'd add a short comment on that field about why ignoring it is safe.

**Potential bugs / issues**
- The diff doesn't show where the `Vec` is built. I'd expect an `IndexSet` to still be used while deduplicating during computation and then converted at the end. If lookups like `get_index_of` on the old set are still needed, they should be served by `chunk_group_keys` or `chunk_group_indices`. Since it compiled and was approved, this is probably fine.
- A `Vec` has no dedup guarantee. The construction path must keep uniqueness. I assume it does, because `chunk_group_indices` already maps to indices.
- The fix has a cost. Any reorder of entries now invalidates the `ChunkGroupInfo` cell and its dependents, where before it was (incorrectly) treated as unchanged. That's the correct trade-off, and it's the point of the PR.

**Performance**
- A `Vec` is cheaper than an `IndexSet`: no hashing and less memory. Equality is O(n) with no hash lookups. Indexed access is unchanged.

**Security:** No concerns.

**Test coverage**
- `test_chunk_group_info_reordered_entries` reproduces the bug directly. It builds the graph with entries `[page1, page2]`, then flips the order through a `State` and recomputes in the same `TurboTasks` instance. It asserts that each module still maps to its own chunk groups, which is the user-visible symptom. It's an integration-style test, as the repo guidelines prefer.
- It would be stronger if it first confirmed the test fails on the old code. The commit history suggests this was done (the test commit comes before the fix), but I couldn't confirm it.
- Only the entry-reordering case is covered. Cases such as reordered `IsolatedMerged` groups or async-loader groups aren't. That's acceptable for a focused fix.
- Minor: `swapped` is written with `.set(true)` through `order.await?`. That works, but a comment saying it triggers invalidation would help readers.

**Verdict:** Approve. It's a minimal, well-reasoned fix with a regression test. The follow-up the author mentioned is worth doing: audit other `FxIndexSet`/`IndexSet` fields in `#[turbo_tasks::value]` structs whose iteration order feeds derived data.
