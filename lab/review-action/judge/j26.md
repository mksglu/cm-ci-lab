# REVIEW A

**Review of PR #36944: assert message functions and printf-style arguments** (already merged, so these are follow-ups)

**Overall:** This is a good change. Moving message handling into one `innerFail()` removes duplicated logic, and the `MessageTuple` type documents the contract well. Re-enabling `parallel/test-assert.js` is the right test signal.

**Issues and suggestions**

1. **Dead commented-out code in `internalMatch`** (`assert.ts`). The PR leaves several commented-out lines: the old `ErrorPrototype` throw, `generatedMessage`, `message ||=`, `new AssertionError`, and `err.generatedMessage`. Delete them.

2. **`message[0] ||= ...` in `internalMatch` mutates the caller's rest array and handles falsy values wrongly.**
   - `assert.match("x", /y/, "")` gives `message = [""]`. `generatedMessage` is `false`, but `||=` then replaces the empty string with the default. The result is a default message flagged as not generated. Node has the same quirk, but check that this matches it.
   - `assert.match("x", /y/, 0)` or `null` behaves differently: `null` is replaced by the default, while `0` fails the same way. Node's `innerFail` would throw `ERR_INVALID_ARG_TYPE` for non-string, non-function values, but `||=` hides that for falsy values. Compare this against Node 26.
   - When `message` is `[]`, `message[0] ||= ...` sets index 0 on the array. This works, but it is subtle. Building a new tuple would be clearer.
   - Passing a function as the message to `match`: `message[0]` is truthy, so the function is kept and called with `(string, regexp)`. That looks right.

3. **`typeof message[0] === "string"` is checked before `isError`, and `isError` comes before `function`.** The order is fine. But `isError` from `internal/util.mjs` may return true for cross-realm or `Error`-like objects. It should be equivalent to the old `ObjectPrototypeIsPrototypeOf(ErrorPrototype, ...)` check, but I haven't verified that.

4. **`innerOk` semantics.**
   - `args.length === 1 || args[1] == null` now treats an explicit `undefined` or `null` message as "generate from source". That matches the old behavior.
   - Assertions that pass `message: undefined` explicitly, such as `assert.strictEqual(a, b, undefined)`, now give a rest array of `[undefined]`. `innerFail` then falls through to the `else` branch and throws `ERR_INVALID_ARG_TYPE`. Before, `undefined` meant "use the default". Check the equality functions. Node's `innerFail` has the same issue and may filter `undefined`, so confirm that `strictEqual(1, 2, undefined)` still yields the default `AssertionError`. If it doesn't, this is a regression. A single test would settle it.

5. **The `equal`-family functions use `arguments.length < 2` together with `...message`.** This works. Using `...message` and `arguments` in the same function is slightly awkward, and `...message` is fine as is.

6. **`compareExceptionKey`, `expectsError` and `expectsNoError` now wrap their messages in `[...]`.** These are internal call sites with generated messages. If a printf-style `%` appears inside the generated text, a single-element tuple is not formatted, so that's safe. Good.

7. **Swallowed exceptions from message functions.** The bare `catch {}` falls back to the default message, which matches Node. A comment links this to the Node behavior, which is helpful.

8. **Tests.** The PR relies only on the Node compat test (`test-assert.js`). No Deno-side spec or unit test covers these behaviors:
   - function messages
   - `%s` / `%d` formatting
   - `ERR_AMBIGUOUS_ARGUMENT` for trailing arguments
   - `ERR_INVALID_ARG_TYPE` for a bad message type
   
   The compat suite does cover them, so this is acceptable. A small spec test for the `undefined` message case above would still be worthwhile.

**Performance:** The rest parameter allocates an array on every call of `equal`, `strictEqual` and the other comparison functions, even when the assertion passes. In hot test loops this is a small cost. It is probably negligible, but passing `message` through lazily would avoid it.

**Security:** No concerns. User-supplied message functions run only on failure and are wrapped in try/catch.

**Style:** The PR reformats some imports, such as `getErrorSourceExpression` onto multiple lines, without a functional change. That is a minor drive-by change under CLAUDE.md's "minimal changes" rule.

**Verdict:** Approve. The follow-ups are to remove the commented-out code, check the `undefined` and falsy-message edge cases against Node, and add a small direct test.

# REVIEW B

## Review of PR #36944: assert message functions and format arguments

The PR is already merged and approved. Moving the message handling into a shared `innerFail()` is a good change, and it follows Node's behavior. I found a few issues. Most are minor.

### Issues

1. **Leftover commented-out code (`assert.ts`, `internalMatch`).** The old `if (ObjectPrototypeIsPrototypeOf(ErrorPrototype, message)) throw message;`, `const generatedMessage = !message;`, `message ||= …`, `const err = new AssertionError({`, and `err.generatedMessage = …; throw err;` lines are commented out instead of deleted. They look like debugging residue and should be removed. `ErrorPrototype` and `ObjectPrototypeIsPrototypeOf` may now be unused imports, which `tools/lint.js --js` would flag. Please check.

2. **`internalMatch` mutates the rest array and has an edge-case bug.**
   - `message[0] ||= …` replaces a falsy first argument with the generated text. For example, `assert.match("x", /y/, "")` and `assert.match("x", /y/, 0)` both take that path. Node only treats an absent or falsy message this way. With `message = [0]` or `[""]`, `generatedMessage` is `false`, but the message is the generated text, so the flag is wrong.
   - A message function, an `Error`, or an invalid type that is falsy, such as `null` or `undefined`, is silently replaced. Node 26 would throw `ERR_INVALID_ARG_TYPE` for some of these. This differs from `innerOk`, which treats only `null` or `undefined` as "no message".
   - `assert.match(str, re, undefined)` gives `message.length === 1`, so `generatedMessage` is `false` even though the message is generated.
   - A cleaner approach is to build the tuple explicitly, as `innerOk` does: `message.length === 0 || message[0] == null ? [generated] : message`, with `generatedMessage` computed from the same condition.

3. **Non-string first argument when the string is not a string.** `message[0] ||= …` skips the generated text when the user passes a message, so that case is fine. The mutation does change the caller's array, though. Here that array is a fresh rest array, so it is harmless, but it is fragile.

4. **`generatedMessage` is only set when `obj.generatedMessage !== undefined`.** For the other callers, such as `strictEqual`, `AssertionError` computes it itself. When a message function returns a non-string or throws, `resolved` is `undefined`, so the default message is used and `AssertionError` should set `generatedMessage = true`. That matches the PR's stated intent, but I saw no test for it.

5. **The `innerOk` message branch.**
   - `args.length === 1 || args[1] == null` covers `assert(false, undefined)`, which matches the old `message == null` behavior.
   - `assert(false, undefined, "x")` is also treated as "no message", so trailing arguments are silently ignored. Node probably does the same, but I'd verify.
   - When `getErrMessage` returns `undefined`, `[]` is used, but `generatedMessage` stays `true`. That is fine.

6. **`format` with a `%`-less first string.** `message.length > 1` calls `format(...)`. Node does the same, so a string such as `"a"` followed by extra arguments gets the extra arguments appended. That is consistent.

7. **Message functions that throw.** The empty `catch {}` swallows the error silently. Node does this too. A short comment explaining it would help.

### Performance

- Every assertion call now allocates a rest array. Successful assertions are the hot path, and they never reach `innerFail`. The cost is small. `message` is only used on failure, so a rest parameter is acceptable.
- `innerOk` now spreads `SafeArrayIterator` and then collects the arguments into another array. That is minor.

### Security

No concerns. The user-supplied message function is called only on failure, and exceptions from it are contained.

### Tests

- The PR enables the upstream `parallel/test-assert.js` and removes the ignore, which gives broad coverage.
- I didn't see any Deno-specific tests under `tests/unit_node`. Edge cases are covered only through the upstream test, for example `assert.match` with falsy messages and a function that returns a non-string. Targeted tests for those would help.
- The PR description says the test passes only on a local debug build. I have no CI results to cite.

### Style and conventions

- The MessageTuple docs have an odd blank line between the doc comment and the `type`, so the comment is detached from the type.
- Run `tools/format.js` and `tools/lint.js --js`. The mixed `{ getErrorSourceExpression }` formatting and the commented-out code suggest this may have been skipped.

### Summary

The approach is sound and matches Node. I'd ask for a follow-up PR that removes the dead commented-out code, tightens the `internalMatch` falsy-message handling to match `innerOk` and Node, and adds a few focused unit tests.
