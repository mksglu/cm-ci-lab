# Review of PR #345293: hide non-user-invocable agents from the Cloud picker

The PR is already merged. I read the diff only and did not run the tests.

## Summary
The change does what the description says. Remote agents with `user_invocable === false` are filtered out of the picker. The full remote name list is still passed to `getLocalCustomAgentFiles`, so hidden remote agents can't come back as local-only "Missing from remote" warnings. Local-only files are now parsed with `PromptFileParser`, so their `user-invocable: false` frontmatter is respected. The change is small and the tests are good.

## What's good
- **Filtering at the picker boundary.** The filter uses `!== false`, so agents with the field absent stay visible. This is the right default.
- **Remote names matched before filtering.** The comment "Match all remote names so hidden agents cannot reappear" explains a non-obvious choice.
- **Per-file error handling.** The `try/catch` is inside the loop, so one unreadable or deleted file is logged with `warn` and the rest are still discovered.
- **Existing parser reused.** `PromptFileParser` is used instead of a hand-rolled regex. The tests cover CRLF line endings, trailing YAML comments, a nested `metadata.user-invocable` key, and a body-only mention.
- **Test coverage.** The tests cover visibility defaults, case-insensitive matching, the all-hidden case, remote fetch failure, and deleted or unreadable files. The test setup is also better than before: a real `MockFileSystemService` replaces the empty mock, and the git service's `activeRepository` is now an observable.

## Issues and suggestions

1. **Sequential file reads (minor, performance).** Each local-only file is now read with `await readFile` inside a `for` loop, so reads run one after another. Agent directories are small, so this is unlikely to matter. If it ever does, `Promise.all` over the files, or reading only the files that aren't matched, would help. The matched branch correctly skips reads already.

2. **Decoding and parsing (nit).** `new PromptFileParser()` and `new TextDecoder()` are created for every file. Hoisting them out of the loop is a small cleanup. Check first whether the parser is stateless.

3. **Swallowed errors for deleted files (nit).** A deleted file (`FileSystemError`) is logged at `warn` level, the same as a real read failure. A file deleted between the directory listing and the read is a benign race, so `debug` would suit it better. The tests treat both cases identically, so this is a judgment call.

4. **Asymmetric behavior (observation).** When a local file matches a remote agent, the remote's visibility wins and the local frontmatter is ignored. The test "keeps remote visibility authoritative" asserts this on purpose. It's reasonable, because the remote is what the API will accept, and the local file may differ from what was pushed. A short comment in the code would help the next reader, since the behavior is only documented in the test.

5. **Malformed frontmatter (unverified).** I didn't check what `PromptFileParser.parse` does with malformed YAML. If it throws, the file is skipped and logged. If it returns no header, the file is listed as visible. No test covers a malformed file. One case would pin down whichever behavior is intended.

6. **Test mock (nit).** The `vscode` mock now defines a `FileSystemError` class with a hardcoded `code = 'FileNotFound'`. This is fine for the current tests. Be careful if other specs in the file start depending on `FileSystemError` semantics.

## Security
I found no concerns. The change only filters what the UI shows. It doesn't expand access, and file contents are only parsed, never executed. The server presumably still enforces `user_invocable` itself, since the 400 error in the linked issue comes from the API. The client-side filter prevents the bad selection but is not the enforcement point.

## Verdict
Approve. The suggestions above are optional follow-ups. The most useful one is a test for malformed frontmatter (item 5).
