# REVIEW A

**Review of PR #36944: assert message functions and format arguments** (already merged)

**Overall:** This is a sound change. Moving message handling into `innerFail` removes duplicated logic, and un-ignoring `parallel/test-assert.js` gives real coverage. I found a few cleanup items and some behavior worth confirming. I read the diff only and did not run the code.

**Issues**
1. **Leftover commented-out code.** `internalMatch` in `assert.ts` still has several commented-out lines: the `ErrorPrototype` check, `const generatedMessage = !message`, `message ||=`, `const err = new AssertionError({`, and the `err.generatedMessage` lines. These should be deleted. Their presence also suggests the change was not fully tidied before merge.
2. **`internalMatch` mutates `message`.** `message[0] ||= ...` writes into the rest-args array. The array is local to `match`/`doesNotMatch`, so this is safe today. It is fragile, though, and it has a second effect. If the caller passes `""` as the message, `message.length` is 1, so `generatedMessage` is false. The `||=` still replaces the empty string with the default text. The result is a default message flagged as not generated. Node's behavior here is worth checking.
3. **Trailing arguments after a generated `match` message.** If `message` is `[undefined, "x"]`, `message[0] ||=` fills in the default text, and `innerFail` then runs `format(default, "x")`. That formats the default text with stray arguments. This is an edge case, but a default string that contains `%` (from `inspect` of the input) would be run through printf-style formatting, because `format` is called when `message.length > 1`. It is only reachable with trailing args.
4. **Single-string messages are not formatted.** With `length === 1` the string is used as is, so `%%` stays literal. This matches Node, but it deserves a comment.
5. **`innerOk` condition.** `args.length === 1 || args[1] == null` means `assert(false, undefined, "x")` uses the generated message and silently drops the trailing argument. This is probably fine, but I'd confirm it matches Node.
6. **Dropped `Error` instance check.** The old code used `ObjectPrototypeIsPrototypeOf(ErrorPrototype, ...)`. The new code uses `isError`, which is broader because it accepts cross-realm and duck-typed errors. That is likely the intent, but it is a behavior change. Check that `ErrorPrototype` and `ObjectPrototypeIsPrototypeOf` are still used in `assert.ts`, since unused destructured primordials would be flagged by lint.
7. **Swallowed errors from message functions.** The bare `catch {}` hides errors thrown by user message functions. This follows the PR description and Node, but a comment saying so would help.
8. **Rest-args signatures.** Changing `equal(actual, expected, message)` to `...message` changes `Function.length` for these functions. They still use `arguments.length < 2`, which works. Check that no test depends on `.length`.

**Performance:** The extra array allocation on the failure path is negligible. `innerOk` now spreads and slices on every call to `assert()`, including successful ones, because `...new SafeArrayIterator(args)` is evaluated before the truthiness check. Hot loops that call `assert(x)` will pay a small cost. A cheap guard would help: have `assert` check `args[0]` first and call `innerOk` only on failure. Otherwise a fixed `(value, ...message)` signature would work.

**Security:** There are no real concerns. Message functions run user-supplied code only on failure, inside try/catch.

**Tests:** Coverage relies solely on the upstream Node test `test-assert.js`. That is reasonable for compat work. The `match` and `doesNotMatch` edge cases from items 2 and 3 are better covered by a spec test or unit test, if the upstream test doesn't exercise them.

**Suggestions:** In a follow-up, remove the commented-out code and decide on the `""` and trailing-argument behavior in `internalMatch`. Consider a fast path in `assert()`/`ok()` so the passing case avoids the allocation.

# REVIEW B

**Review of PR #36944: assert message functions and format arguments** (already merged)

**Overall:** The approach is good. Putting message handling in one `innerFail()` removes duplicated logic, and re-enabling `parallel/test-assert.js` is the right proof of correctness. I found a few cleanup items and some edge cases to check.

**Issues and suggestions**

1. **Leftover commented-out code in `internalMatch`** (`ext/node/polyfills/assert.ts`). The old `ObjectPrototypeIsPrototypeOf(ErrorPrototype, message)` check, `const err = new AssertionError({`, and the `err.generatedMessage` lines are commented out rather than deleted. These should be removed. After this change `ErrorPrototype` and `ObjectPrototypeIsPrototypeOf` may also be unused in `assert.ts`, which `lint.js` would flag. It's worth checking that.

2. **`message[0] ||= ...` in `internalMatch` has some quirks:**
   - It mutates the caller's rest array. That is harmless here, since it is a fresh array.
   - If a user passes `""` as the message, `message.length` is 1, so `generatedMessage` is `false`. Then `||=` replaces the empty string with the default text. The result is a default message flagged as non-generated. Node's behavior here may differ, so it's worth comparing.
   - If the user passes a function or an Error as `message[0]`, both are truthy, so they pass through correctly. If the user passes extra format args with a falsy first element (e.g. `match(s, re, "", 1)`), `||=` fills the default message and then `format()` runs on it with a stray argument. This is an edge case that is unlikely to matter.

3. **`innerOk` with `args[1] == null`.** Passing an explicit `undefined` or `null` message yields the generated message, which matches the old `message == null` behavior. But `assert.ok(false, undefined, "x")` also takes the generated path and silently ignores the trailing argument. That seems fine, but it's untested.

4. **Throwing function messages.** `catch {}` swallows every error from the message function, so a bug in a user's message callback is hidden. This matches the stated Node 26 behavior, so I'm only noting it. A short comment pointing to the Node source would help future maintainers.

5. **Error check order in `innerFail`.** `typeof message[0] === "string"` comes first, then `isError`, then function. That is fine. For `ERR_AMBIGUOUS_ARGUMENT`, `ErrorPrototypeToString(message[0])` can throw if the object is a duck-typed error with a broken `name` or `message`. This is a minor edge case.

6. **`compareExceptionKey`, `expectsError` and `expectsNoError`.** These now wrap internal messages in `[message]`. If `message` is `undefined` in `compareExceptionKey` (the original parameter could be undefined), then `[undefined]` reaches `innerFail`. That falls into the final `else` and throws `ERR_INVALID_ARG_TYPE`. Please check that every caller of `compareExceptionKey` passes a defined message. A defensive `message === undefined ? [] : [message]` would be safer, in the same way `innerOk` handles `source === undefined`.

7. **Public-signature change.** The comparison functions now use `...message`, which changes `fn.length`. For example, `assert.equal.length` goes from 3 to 2. This matches Node's current behavior, but it could be visible to user code. It's fine, though worth noting.

8. **Type and style details.**
   - `as MessageTuple` casts on user input hide the fact that the input is untrusted. Runtime validation in `innerFail` covers this, so it's acceptable.
   - The doc comment says "print like substitutions". "printf-like" would be clearer.

**Performance:** Negligible. The rest args and `ArrayPrototypeSlice` only add cost on the failure path, plus a small cost per call for the `...message` rest allocation. `assert.equal` and similar functions are hot in test suites, but a rest array allocation is cheap.

**Security:** No concerns. User-provided message functions run only on failure, and their exceptions are contained.

**Test coverage:** The only test change is un-ignoring the upstream `test-assert.js`. That covers the main behaviors well. I'd still suggest a small spec test in `tests/specs/` or `tests/unit_node/` for the Deno-specific edge cases: `assert.ok(false, undefined, ...)`, `match` with an empty-string message, and `compareExceptionKey` with an undefined message. It would also catch regressions if the node_compat test is skipped later.

**Process:** The PR description says it fixes "part of #35293" and mentions AI assistance, which is good. I couldn't confirm that `tools/format.js` and `tools/lint.js` were run. The commented-out code suggests the lint pass may have been missed.

**Verdict:** Approve-worthy. A follow-up PR should delete the commented-out code and guard against `undefined` in `compareExceptionKey`.
