# Review of PR #23017: Preserve inline comments when updating an existing dependency group

## Summary
When `dev` already exists inside an inline `dependency-groups = { ... }` table, `uv add --dev` used to call `InlineTable::fmt()` on the whole table. That call removes comments between keys. Now `add_dependency_group_requirement` only sorts and formats the table when it inserts a new group. `ensure_dependency_group` is also restructured to return early when the group already exists. The change is small and the fix is correct. My main concerns are that the same problem is left in place for `optional-dependencies`, and that some new code paths have no tests.

## Potential bugs / issues

1. **`project.optional-dependencies` still has the same bug** (`crates/uv-project-edit/src/lib.rs:541-551` and `:581-590`).
   `add_optional_dependency` and `ensure_optional_dependency` still call `optional_dependencies.fmt()` every time, even when the extra already exists. They also still carry the old comment, "you can't put comments between items in an inline table anyway." This PR shows that comment is wrong, since comments between keys are now preserved (and TOML 1.1 allows them). So this input:
   ```toml
   [project]
   optional-dependencies = {
       cli = [], # CLI extras
       # Docs
       docs = [],
   }
   ```
   still loses its comments with `uv add --optional cli foo`. I'd suggest applying the same `new_group` gating there, or at least removing the wrong comment, so the two code paths behave the same.

2. **Comments are still removed when a group is inserted.** On the insert path, `fmt()` still runs and clears every comment in the table. That's a reasonable trade-off, but the new comment ("Only inserting a key changes the table layout…") doesn't say comments will be lost in that case. A sentence stating that inserting a group still normalizes the table and drops comments would help future readers. A snapshot test pinning that behavior would help too.

3. **`ensure_dependency_group` now behaves differently, with no test.** It used to call `fmt()` even when the group already existed. Now it returns early, so existing inline tables are left untouched. That's probably the right behavior, and it matches the PR's goal, but the PR description doesn't mention it and no test covers it (e.g. `uv add --group dev` against an inline table with comments, through whichever command reaches `ensure_dependency_group`).

## Code quality

- The `// To avoid churn in pyproject.toml, we only sort new group keys if the existing keys were sorted.` comment was removed from both functions. The `was_sorted` condition still isn't obvious, so I'd keep that explanation.
- `ensure_dependency_group` lost the explanation of why `fmt()` runs. A one-line comment like the one in `add_dependency_group_requirement` would keep the two consistent.
- Minor: you could get `new_group` from the same `match` that produces `group` (e.g. `let (group, new_group) = match existing_group { Some(v) => (v, false), None => (..., true) }`) instead of checking `is_none()` beforehand. This is optional; the current version reads fine.
- The early-return refactor in `ensure_dependency_group` is cleaner than the previous `group_exists` flag.

It also doesn't repeat any existing test; no other test in `edit.rs` uses an inline `dependency-groups` table.

# REVIEW B

## PR #23017 review: keep inline comments when updating an existing dependency group

**Verdict:** The fix is correct and small. The new test reproduces the bug. The same bug is still there in nearby code paths, though, and the PR now explicitly makes a comment-preservation promise, so I'd like those paths covered too.

### What the change does
In both `add_dependency_group_requirement` and `ensure_dependency_group`, `dependency_groups.sort_values()` and `InlineTable::fmt()` now run only when a new group key is inserted. When the group already exists, the array is edited in place and the surrounding inline table is left alone.

### Correctness
- **This is safe for existing groups.** If the table was already sorted, sorting it again changes nothing. And `InlineTable::fmt()` only resets the decor (spacing and comments) between keys and values; it never formatted the array contents. So for existing groups, skipping it removes only the comment-erasing side effect.
- **Inserting a new group still erases comments.** With the same fixture, `uv add --group lint ok` takes the `new_group` path, calls `fmt()`, and drops `# Local development` and `# Release tests run separately.`. `ensure_dependency_group` does the same (e.g. `uv add --group lint` with nothing to install). The old code comment said this was acceptable because "you can't put comments between items in an inline table anyway". That was true in TOML 1.0, but this PR's fixture shows multi-line inline tables with comments are supported now, and the PR removes that justification. Two options:
  - Avoid `fmt()` on insert too. For example, only format the newly inserted key/value decor, or format only when the table is on a single line.
  - Or add a short comment saying comments are still lost when a key is inserted, plus a snapshot test documenting it, so it isn't mistaken for a regression later.
- **Optional dependencies have the same bug.** `add_optional_dependency` and `ensure_optional_dependency` (`crates/uv-project-edit/src/lib.rs:~546` and `~585`) still call `optional_dependencies.fmt()` on every edit. That includes edits to an existing extra, so `uv add --optional dev ok` against an inline `optional-dependencies = { dev = [], # ... }` will still erase comments. Fixing it here, or in a follow-up, would keep the two code paths consistent.

### Code quality
- `ensure_dependency_group`: the early `return Ok(())` is clearer than the old flag. But the PR also deleted the "only sort if the existing keys were sorted, to avoid churn" comment from this function, and that rationale isn't obvious from the code. Please restore a one-line version of it, as was done in `add_dependency_group_requirement`.
- The new comment ("Only inserting a key changes the table layout. Formatting after an array edit would clear the comments between inline groups.") reads well and describes current behaviour, which matches AGENTS.md.
- `let new_group = existing_group.is_none();` is fine. Writing `let new_group = matches!(...)` / a `match` that returns `(group, new_group)` would also work, but this is readable as it is.

### Test coverage
- The test follows nearby conventions: `uv_snapshot!` for the command, then `assert_snapshot!` on `context.read("pyproject.toml")`, using `--frozen`. It also uses the local `ok` package, so it needs no network gate.
- **Ugly array indentation in the snapshot.** The array's indentation ignores the nesting:
  ```toml
  dependency-groups = {
      dev = [
      "ok==1.0.0",
  ], # Local development
  ```
  `add_dependency` formats the array as if it were top-level. This isn't a regression, since `fmt()` never touched array contents. But the snapshot now pins this output, so it's worth either a follow-up or a note in the PR that it's known.
- **Suggested extra tests,** as separate named tests per AGENTS.md:
  1. Adding to a *new* group in a commented multi-line inline table. This documents (or, if fixed, checks) what happens to the comments.
  2. The inline `optional-dependencies` case, if it gets fixed in this PR.
- Please confirm that no existing snapshot exercises a single-line inline `dependency-groups = { dev = [...] }` with an existing group. I didn't find one in `crates/uv/tests`. Before this PR, that case had its spacing normalised by `fmt()` and now it won't be. That's probably better (less churn), but it is an untested change in behaviour.

### Performance / security
Nothing to flag. The change only removes work: it skips sorting and formatting on the common path.
