# REVIEW A

**Review of #100956: Fix prerendering of caught `'use cache'` errors**

The PR is already merged and approved. I read the diff only. I didn't run the tests.

**Summary:** `reactServerErrorsByDigest` on the work store also records errors thrown inside `'use cache'` functions, so the page's logging can recover them. Prerendering also read that map as its failure signal. A page that caught a cache error still failed the build or on-demand generation. The fix adds a per-render `renderErrorsByDigest` map. `createReactServerErrorHandler` fills it only from the page's RSC renderer. Every `digestErrorsMap` returned from `prerenderToStream` now uses the new map. The shared map stays in place for logging (#86500).

**Code quality**
- The change is small and targeted, and the comment explains why there are two maps.
- Adding a trailing optional parameter to `createReactServerErrorHandler` is minimally invasive. It forces the call site to pass `undefined` for `spanToRecordOn`, which is a little awkward. An options object would read better, but that's a style point and not worth blocking on.
- `renderErrorsByDigest?.set(...)` runs after the early-return paths for the following cases:
  - prerender bailouts
  - dynamic-usage errors
  - closed responses
  
  Those errors are therefore never added to the map, as before. The new map is not populated from any early-return path that previously skipped the shared map.

**Potential issues**
- I checked that all seven `digestErrorsMap` return sites were switched, covering the dynamic, Fizz, and error-fallback paths. I didn't check whether other `prerenderToStream` code reads `reactServerErrorsByDigest` for failure detection. Worth a grep to confirm none remain.
- If other callers of `createReactServerErrorHandler` need the same separation (for example the dev or runtime render path or the `prerender` function), they still use only the shared map. For those paths a caught cache error is only logged, so this looks fine.
- The error handler only receives the new map in the page's RSC renderer. If the same cache error is also thrown uncaught, it flows through the handler and does land in the new map, so real failures are still detected. The test doesn't cover that negative case.

**Performance:** The cost is one extra `Map` per prerender and one `set` per error. That is negligible.

**Security:** No new request headers are read, and nothing is exposed to users.

**Test coverage**
- The e2e fixture covers a build-time static param and an on-demand runtime param under `cacheComponents`. It follows the repo conventions: `nextTestSetup` with `files: __dirname`, and a fixture directory instead of inline files.
- The `x-nextjs-cache: HIT` assertion on a second fetch checks that the fallback stays cacheable. It is guarded by `isNextStart`.
- Possible additions:
  - A negative test showing that an uncaught `'use cache'` error still fails the build. It would guard against the fix swallowing real failures.
  - A check that the caught error is still logged, which would protect the #86500 behavior this change explicitly preserves.
  - The `HIT` assertion on the `runtime` route may be timing-sensitive. The first request generates it on demand, and the cache write can race the second fetch. Wrapping it in `retry()` would be safer.
- The test name says "should cache the fallback", but the first fetch status and body check is the main regression signal. This is fine as written.

**Verdict:** The fix is correct and well-scoped, and I found no blockers. The follow-ups I'd suggest are an uncaught-error regression test and `retry()` around the cache-hit assertion.

# REVIEW B

**Review of PR #100956: Fix prerendering of caught `'use cache'` errors**

I read the diff and the surrounding code in `create-error-handler.tsx` and `app-render.tsx`. I did not run the tests.

**Summary:** The fix is small and well targeted. `'use cache'` errors are recorded in the shared `workStore.reactServerErrorsByDigest` map so the page renderer can recover the original error for logging (#86500). Prerendering also read that same map as `digestErrorsMap`. At `app-render.tsx:2749`, `firstReactServerError` is taken from `digestErrorsMap`, so a cached-function error that the page caught still failed the build. The PR gives prerender its own `renderErrorsByDigest` map. That map only receives errors that reach the page's RSC `onError`, meaning errors that surfaced uncaught. The logging lookup is unchanged.

**What looks right**
- All the `digestErrorsMap: reactServerErrorsByDigest` returns in `prerenderToStream` are switched, including the error-render fallback paths. The `digestErrorsMap: new Map()` at line 10097 is unaffected.
- `digestErrorsMap` is only read at `app-render.tsx:2749`, so no other consumer is affected.
- `renderErrorsByDigest` is populated after the `reactServerErrors.has()` check, so it still records an error when the shared map already holds one with the same digest. That is the right behavior.
- The well-known-digest early returns (`notFound`, `redirect`, bailout) and abort errors never enter either map, so that behavior is unchanged.
- The new map is created per `prerenderToStream` call, so there is no cross-request leakage.

**Concerns and suggestions**
1. **API ergonomics.** `createReactServerErrorHandler` now has a positional optional `renderErrorsByDigest` after `spanToRecordOn`. The call site has to pass `undefined, renderErrorsByDigest`. An options object would be cleaner, though this is minor, with only one caller needing the new argument.
2. **Remaining reads of the shared map in `prerenderToStream`.** These still use `reactServerErrorsByDigest`:
   - Line 10418: `throw reactServerErrorsByDigest.get(err.digest) ?? err`.
   - Lines 10520 and 10834: `reactServerErrorsByDigest.has(digest) ? undefined : err`.

   They treat "digest is known" as meaning the error was already handled. A caught cache error could in principle share a digest with an error that later surfaces. That is probably fine and arguably intended, because the original error is recovered for the digest. It is worth a comment or a check that none of these paths depend on the old "surfaced" semantics.
3. **Test coverage.**
   - The fixture covers both a `generateStaticParams` route (`static`) and an on-demand route (`runtime`). It checks the 200 status, the fallback markup, and an `x-nextjs-cache: HIT` on a second request in start mode.
   - There is no assertion that the build log is free of the cached error. The error is still logged, which is intended for #86500, so that is acceptable.
   - There is no negative test showing that an *uncaught* `'use cache'` error still fails the build. This is the most valuable missing case because it guards against the fix hiding real failures. A second route that doesn't catch the error, run in a separate build test or as a `next build` failure check, would help.
   - `next.config.ts` uses `cacheComponents: true` only. Consider whether the non-cacheComponents path, where `'use cache'` is enabled via `useCache`, shares this bug.
   - The `HIT` check could be flaky for `runtime` on a first fetch in start mode. The first request generates and the second hits, which is fine, but the dynamic-params case depends on `dynamicParams` defaults.
4. **Style.** The test uses `it.each` with a template-less title, which is fine. It follows the repo conventions: a fixture directory, `nextTestSetup({ files: __dirname })`, and no `check()` or `setTimeout`. I can't confirm from the diff alone that it was generated with `pnpm new-test`. The comment block above `renderErrorsByDigest` is clear.

**Security and performance:** No security concerns, since no new request headers are read. The performance cost is one extra `Map` per prerender and one extra `set` per error, which is negligible.

**Verdict:** Looks good. I'd add the negative test (an uncaught cached error still fails prerendering) and double-check the three remaining `reactServerErrorsByDigest` reads in the error-render paths before merging.
