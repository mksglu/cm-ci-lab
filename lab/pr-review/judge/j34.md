# REVIEW A

I'd approve this PR. The fix is correct, small and well targeted, and it comes with a regression test that reproduces the actual bug. (It's already merged, with approvals from mischnic and sokra.)

## What it changes
`ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. Equality on `FxIndexSet` ignores order. So when a recompute only renumbered the chunk groups, for example after reordering graph entries, the new `ChunkGroupInfo` compared equal to the old one and the cell kept the **old** order. Meanwhile the separately celled `module_chunk_groups` bitsets and `chunk_group_indices` were updated to the **new** numbering. The result was modules silently mapping to another entry's chunk groups.

## Correctness
- **The root-cause fix is right.** Every reader of `chunk_groups` looks it up by index: `get_chunk_groups_for_module`, `get_shared_merged_chunk_group`, `module_batches.rs`, and the debug output in `get_index_of`. None of them uses set lookup, so a `Vec` is the accurate type, and `.get_index(i)` → `.get(i)` / `[i]` is a mechanical change.
- **`chunk_group_keys` is still an `FxIndexSet` marked `#[turbo_tasks(unsafe_ignore)]`.** That is now safe, but only because of an unstated invariant: `chunk_groups` is built 1:1 and in the same order from `chunk_groups_map` (`chunk_group_info.rs:956` and `:968`). Any reordering of keys therefore also reorders `chunk_groups`, which breaks equality and replaces the whole value. `get_shared_merged_chunk_group` depends on the two staying aligned: it gets an index from `chunk_group_keys.get_index_of` and uses it to index `chunk_groups`.
  - **Suggestion:** state this in the field docs, e.g. "`chunk_group_keys` must stay index-aligned with `chunk_groups`; its order-insensitive equality is only safe because `chunk_groups` catches any reordering." If someone later makes `chunk_groups` derived or lazily computed, this hazard returns quietly.
- **The new doc comment is accurate.** If the outer cell compared equal, readers would see the old `chunk_groups` paired with the updated `module_chunk_groups` and `chunk_group_indices` cells, because cells are position-indexed within the task. The `ChunkGroupKeyToIndex` docs (lines 37–42) already explain the same pitfall for keyed cells, so the two comments are consistent.

## Similar risk elsewhere
The description says you're auditing other spots, which is worth doing. A useful check: any `FxIndexSet` or `FxIndexMap` field inside a `#[turbo_tasks::value]` that something else refers to **by position** (bitsets, `u32` indices, `get_index`) has this same bug. Fields that are only iterated or looked up by key are fine. A short note in `turbopack/AGENTS.md` under "turbo_tasks caching and invalidation" would help prevent it coming back. Something like: "IndexSet/IndexMap equality is order-insensitive; use `Vec` when positions are referenced elsewhere."

## Tests
`test_chunk_group_info_reordered_entries` is a good regression test:
- It uses `State<bool>` and `read_strongly_consistent` to force a real recompute, rather than comparing two fresh builds. That is the only way to hit the "cell compares equal, so the old value is kept" path.
- I traced the old code: with `IndexSet`, the swapped run would have mapped `page1.js` to `entry page2.js`, so the test does fail without the fix.

Small nits, none blocking:
- The `_ => "other"` arm would hide an unexpected group kind. `unreachable!()` or the variant's `Debug` output would make a failure clearer.
- Asserting on `page2.js` / `lazy2.js` as well would cover both sides of the swap. As written it only checks one entry.
- The test is named and documented after one trigger (entry order). The underlying property is broader: any renumbering of chunk groups must invalidate. A sentence in the doc comment saying so would make its intent outlive this particular reproduction.

## Performance
- The change is neutral to slightly positive. `Vec` drops the hash table from `IndexSet`, so less memory and no per-element hashing on build or decode. Equality on `Vec` is a cheap element-by-element comparison.
- The extra invalidation is intended: a renumbering now propagates, where before it was wrongly swallowed. A pure reorder is rare in practice, so this shouldn't cause noticeable churn.
- Removing `#[bincode(with = "turbo_bincode::indexset")]` changes the on-disk format of this value. That should be fine as long as the persistent cache is versioned by build or binary hash, which I believe it is. Worth confirming nothing pins a format version by hand.

# REVIEW B

## Review: PR #100935, "Turbopack: store `ChunkGroupInfo::chunk_groups` as a Vec"

**Verdict:** The fix is correct and small, and the test is a real regression test. I'd approve it. The PR is already merged with approvals from @mischnic and @sokra, so the items below are suggestions for follow-ups.

### What it fixes

`ChunkGroupInfo` is a `turbo_tasks::value`, so when it is recomputed, the new value is compared with the cached one using `PartialEq`. If they compare equal, the old cell stays. `indexmap`'s `IndexSet` compares like a set and ignores order. So if a recomputation only renumbered the chunk groups (for example, because graph entries were reordered), the old `chunk_groups` order stayed in the cell. Meanwhile the bitsets in `module_chunk_groups` and the indices in `chunk_group_indices` are separate cells, and they did change to the new numbering. As a result, `chunk_groups[index]` could return a different entry's chunk group. That's a real correctness bug for persistent and incremental builds, and switching to a `Vec` makes equality order-sensitive.

### Correctness

- **Every caller already treated it as indexed storage.** All uses are `[]`, `.get(idx)`, `.iter()`, `.iter().enumerate()` and `.len()` (`chunk_group_info.rs`, `module_batches.rs`, `merged_modules.rs`, `style_groups_*`, tests). None used set-only operations like `contains`, `get_index_of` or `insert`. Key-to-index lookup goes through `chunk_group_keys` / `chunk_group_indices`, so losing set semantics changes nothing else.
- **No duplicates are possible.** `chunk_groups` is built 1:1 from `chunk_groups_map` (`chunk_group_info.rs:968`), which is keyed, so the `Vec` can't gain duplicates.
- **`chunk_group_keys` is still an `FxIndexSet` marked `#[turbo_tasks(unsafe_ignore)]`, and that's fine.** It's derived 1:1 and in the same order as `chunk_groups`. Any reordering now makes the whole struct compare unequal, so the keys get replaced along with it. It would still help to add a short comment there saying it relies on `chunk_groups` for change detection, so nobody later turns `chunk_groups` back into a set without noticing.
- **The nested collections inside `ChunkGroup` are all `Vec`s already** (`Entry`, `SharedMultiple`, the `*Merged { entries }` variants), so they don't have the same problem.
- **Serialization:** dropping `#[bincode(with = "turbo_bincode::indexset")]` changes the encoding of the persisted cache. That should be covered by cache versioning, but it's worth confirming that persisted caches get invalidated across this change.

### Test coverage

`test_chunk_group_info_reordered_entries` reproduces the bug well:
- It changes a `State` to reverse the entry order and reads the result again with `read_strongly_consistent`.
- It goes through the public `get_chunk_groups_for_module` path.
- Without the fix, the second read would give `page1.js: entry page2.js`, because the index is new but the `chunk_groups` order is stale. So the test fails before the fix and passes after it.

Small suggestions:
- **Add `lazy2.js` / `page2.js` to the asserted modules.** Right now only `page1` and `lazy1` are checked. Covering both sides makes it clearer that the two indices swapped, rather than one of them happening to line up.
- **Name the helper struct more clearly.** `EntryOrder { swapped: State<bool> }` is fine; something like `EntryOrderState` might read better next to the other test values. This is purely cosmetic.
- **Add a guard in debug builds (optional).** A `debug_assert_eq!(chunk_groups.len(), chunk_group_keys.len())` where the struct is built would catch the two collections getting out of sync in future.

### Performance

No concern. Indexing into a `Vec` is as cheap as `IndexSet::get_index` or cheaper, and it drops the hash table, so memory goes down a little. Equality now compares elements in order, which costs about the same as before (or less, since there's no hash lookup per element).

### Security

Nothing relevant. The change is internal to the bundler's data structures.

### Follow-up idea

The PR description says other places have the same risk, so a systematic check would be worthwhile. Look for `IndexSet`/`IndexMap` fields inside `turbo_tasks::value` types whose callers depend on position (`get_index`, `enumerate()` used as an id, or parallel arrays indexed by position). Each such field can silently keep a stale order. Two ways to rule out the whole class:
- Use a wrapper type with order-sensitive `PartialEq`.
- Add a clippy-style lint against plain `IndexSet` in value structs.
