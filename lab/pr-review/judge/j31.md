## Review: PR #41520, `chore(model-profiles): refresh model profile data`

**Verdict: ready to merge.** This is a bot-generated data refresh. It only touches two generated `_profiles.py` files, with no logic, signature or dependency changes. Two data-quality issues are worth following up upstream, but neither blocks this PR.

### Code quality and conventions
- The title follows Conventional Commits and includes a scope.
- The diff is limited to `libs/partners/huggingface/.../data/_profiles.py` and `libs/partners/openrouter/.../data/_profiles.py`, which is what `langchain-profiles refresh` should produce.

### Potential issues

1. **Some `max_output_tokens` values flip back and forth between refreshes (worth investigating).** The values 943,717 and 943,718 are 90% of a 1,048,576-token context window. That looks like an upstream rule of "use 90% of context" when no real limit is known, not a published limit. The git history shows these models changing direction on every run:
   - `deepseek/deepseek-v4-flash-0731` went from 943,718 to 131,072 in an earlier refresh. This PR changes it back to 943,718.
   - At the same time, its siblings `deepseek-v4-flash`, `deepseek-v4.1-flash` and `~z-ai/glm-latest` move the other way, to 131,072.
   - `xiaomi/mimo-v2.5-pro` goes from 945,000 to 235,929, which is again 90% of a context size (262,144).

   Code that uses `profile["max_output_tokens"]` to size `max_tokens` or to budget context can receive a value around 7x too large, and that value changes from one refresh to the next. The models.dev / OpenRouter source data should be fixed. Another option is an override in `profile_augmentations.toml` that pins known limits for these DeepSeek and Xiaomi models, so the refresh stops toggling them.

2. **The new Hugging Face entry has no `structured_output` key.** `MiniMaxAI/MiniMax-M3.1-Flash` lists `tool_calling: True` but leaves out `structured_output`. Only about 50 of 82 entries in the Hugging Face file include that key, so this matches existing behavior. Still, any consumer that reads `profile.get("structured_output")` will get `None` and treat it as "unsupported". This is minor, but an augmentation could fill it in if the model supports it.

3. **The new Hugging Face entry has an unusually large output limit.** `MiniMax-M3.1-Flash` lists 512,000 max output tokens against a 1M context. That is unusual but plausible. A quick check against the provider's model card would confirm it is not another estimate like the ones above.

### Removed models

Users who pass those model IDs will now get an empty or default profile instead of the old data, which is the expected result when a provider delists a model.

### Performance and security

- **Security:** no concerns. There is no executable logic, and the data comes from the existing refresh pipeline.

# REVIEW B

**Review of PR #41520: chore(model-profiles): refresh model profile data**

This bot PR refreshes generated profile data only: 1 Hugging Face model added, 2 OpenRouter models added, 2 removed and 10 changed. There is no hand-written code, so the review is about whether the data is right. The file structure and formatting match the generator. Nothing in `libs/` outside the `_profiles.py` files mentions the added or removed model IDs, so no tests or examples break. The PR is already merged, so the items below could go into an upstream data fix or a follow-up refresh.

### Possible data-quality issues

**1. Some `max_output_tokens` values look like placeholders, not real limits.**
Several values, both old and new, are exactly 90% of a common context size:
- 943,717 / 943,718 ≈ 0.9 × 1,048,576
- 235,929 ≈ 0.9 × 262,144
- 117,964 ≈ 0.9 × 131,072
- 945,000 = 0.9 × 1,050,000

These look like a fallback in the upstream source when the provider doesn't publish an output limit. This PR replaces several of them with realistic values: `gemma-3-4b-it` and `gemma-4-31b-it` go to 16,384, `mimo-v2.5` to 65,536, and `deepseek-v4-flash` and `~z-ai/glm-latest` to 131,072. That's an improvement.

It also adds new ones:
- **`deepseek/deepseek-v4-flash-0731`**: 131,072 → **943,718**. This happens in the same run where `deepseek-v4-flash` and `deepseek-v4.1-flash` go from 943,717/943,718 down to 131,072. A dated snapshot almost certainly doesn't have a ~7× larger output limit than its alias. It looks like the values flip back and forth between refreshes.
- **`xiaomi/mimo-v2.5-pro`**: 945,000 → **235,929**. That is 90% of a 262,144 context, but this model's `max_input_tokens` is 1,050,000. The value doesn't fit its own context and looks like it came from a different entry.

This matters because downstream code uses `max_output_tokens` to budget output, for example in summarization or trimming middleware. A placeholder value can lead callers to request far more output tokens than the provider allows, and the request then fails. Two suggestions:
- Pin these in `profile_augmentations.toml` for OpenRouter until the upstream source is fixed.
- Have the refresh tool warn when a value is about 0.9 × `max_input_tokens`, or when it doesn't fit the model's context (as with `mimo-v2.5-pro`).

**2. `MiniMaxAI/MiniMax-M3.1-Flash` (Hugging Face)**
- It has no `structured_output` key, while `MiniMax-M2.7` and `MiniMax-M3` both have `"structured_output": True`. Users will see "unknown" rather than `True`. Worth checking whether the upstream source just leaves this field out.
- It has `"open_weights": False`, while every earlier MiniMax entry on the Hub is `True`. That could be right for a Flash or API-only variant, but it's unusual for a Hugging Face model ID. Worth confirming.

**3. Removed models**
After `arcee-ai/trinity-large-thinking` and `ibm-granite/granite-4.0-h-micro` are removed, `ChatOpenRouter(model=...).profile` for those IDs returns an empty profile without any warning. Removing models the provider has delisted is expected for generated data. Still, the summary could separate "delisted by the provider" from "removed from the upstream dataset", so reviewers can tell a real delisting from a data glitch.

### Smaller points
- **Review process:** a diff like this, with values swapping between closely related models, is easy to approve without noticing. The "Summary of changes" block could flag changes to `max_output_tokens` above roughly 3× in either direction for a human to check.
- **Tests and security:** no new tests are needed for generated data, and there are no security concerns. It's static dict data with no code paths.

### Verdict
The data is mostly an improvement: several placeholder values are replaced with realistic limits and three new models are added. Two values (`deepseek-v4-flash-0731` and `mimo-v2.5-pro`) look like placeholder or mismatched data and should be checked or overridden. The new MiniMax entry's `structured_output` and `open_weights` fields should also be checked.
