# REVIEW A

**Review of PR 345293: hide non-user-invocable agents from the Cloud picker**

The PR is already merged. It's a small, focused change and I found no blocking problems.

**What it does well**
- It filters at the picker boundary with `agent.user_invocable !== false`. That keeps the default of visible and leaves `disable_model_invocation` alone, which is correct.
- `getLocalCustomAgentFiles` still receives the full `remoteAgents` list, not the filtered one. A hidden remote agent therefore still matches its local file and can't come back as a "Missing from microsoft/vscode" warning. A test covers this.
- It reuses the existing `PromptFileParser` for frontmatter. That handles CRLF line endings, inline comments, nested keys and body text that merely mentions the key, and the tests cover all four.
- A failed read of one file is logged and skipped. The outer try/catch no longer abandons the whole scan because of one bad file.
- The new test cases are thorough: default visibility, case-insensitive matching, a failed remote fetch, and deleted or unreadable files. The test infrastructure changes (`MockFileSystemService`, an observable `activeRepository`) look sound.

**Minor observations (non-blocking)**
1. **Sequential reads.** Local-only files are read one at a time with `await` inside the loop. `.github/agents` is usually small, so this is fine. If it ever matters, `Promise.all` would parallelize the reads. The reads only happen for files with no remote match, so the cost is already limited.
2. **Frontmatter parse failures.** `PromptFileParser.parse` is lenient. A file with malformed frontmatter ends up with `header` undefined and is shown as visible. That seems like a reasonable fallback, but no test covers malformed YAML.
3. **Visibility rule in two places.** The `!== false` rule now sits in the remote filter and in the local check. A tiny helper such as `isUserInvocable(x)` would stop the two from drifting apart. This is optional.
4. **Log level.** `warn` for a deleted file is a bit noisy, because a file deleted between `readDirectory` and `readFile` is a benign race. The tests deliberately assert the warning for both the deleted and unreadable cases, so this was a conscious choice.
5. **Test mock shape.** The `FileSystemError` mock has a fixed `code = 'FileNotFound'` that ignores its constructor argument. That's fine for now, but it could surprise someone who extends the tests.
6. **Selection guard.** The PR fixes the HTTP 400 by hiding agents from the picker. A previously stored selection of a now-hidden agent id, such as one persisted from an earlier session, isn't validated here. If the selection is restored from state, it could still send the hidden id. I didn't check how restoration works, so it's worth confirming.

**Security and performance**
- I see no security concerns. The code only reads workspace files under `.github/agents`, and the parser doesn't execute anything.
- There's no meaningful performance impact beyond the sequential reads noted above.

**Verdict:** the change is sound and well tested. The only follow-up I'd suggest is checking item 6.

**Suggestions and minor issues**

It's probably fine, since `.github/agents` is small. If it ever matters, collect the non-matching files and read them with `Promise.all`. Only the local-only ones are read, which keeps it cheap.
2. **Parser reuse:** `new PromptFileParser()` and `new TextDecoder()` are constructed on every iteration. Hoisting them above the loop is trivial and tidier.
3. **Parse errors:** `PromptFileParser.parse` appears to tolerate malformed frontmatter, so a bad file likely yields a visible warning entry. That seems the right fail-open default. A test with invalid YAML would pin it down.
4. **Log level:** Skipping a file that was deleted between `readDirectory` and `readFile` is a normal race. Logging it at `warn` is acceptable, but `debug` would be quieter for that case. The test asserts `warn` for both causes, so keep them consistent if you change it.

6. **Server-side 400:** The PR fixes the picker so users can't select these agents. It doesn't handle a 400 when an agent's visibility changes between the list fetch and the session start. That is an edge case and out of scope here.
