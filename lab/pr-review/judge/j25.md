# REVIEW A

I didn't find any correctness bugs in this PR. It's already merged, so these notes are mostly follow-ups.

**Summary of the change:** in `add_dependency_group_requirement`, the inline `dependency-groups` table is now sorted and reformatted with `fmt()` only when a new group key is inserted. Adding to an existing group no longer runs `fmt()`, so comments between the keys survive. `ensure_dependency_group` was also rewritten with an early return; its behaviour is unchanged.

### Correctness

- **Skipping the sort for existing groups is safe.** If the keys were already sorted and no key was added, `sort_values()` would have changed nothing. If they weren't sorted, it was never called.
- **Inline tables are normalised less often now.** A compact table like `dependency-groups = {dev=[]}` used to be rewritten as `{ dev = [...] }` on every add to an existing group. Now it is only rewritten when a new group is inserted. That means less churn, which is good. Since no other snapshot changed, no existing test depended on the old behaviour.
- **The old comment was based on TOML 1.0.** It said "you can't put comments between items in an inline table anyway", which was true there. The new fixture uses a multi-line inline table with comments and a trailing comma, which is only valid in TOML 1.1. Removing that comment was right. The new comment could say outright that TOML 1.1 allows comments inside inline tables, so later readers understand why `fmt()` is avoided.

### The fix is incomplete
The same comment loss still happens in other places:

1. **Adding a new group:** `uv add --group new-group x` against the fixture still goes through `fmt()`. That drops `# Local development` and `# Release tests run separately.`, and so does `ensure_dependency_group`, which also always calls `fmt()` on insert. The PR description admits this ("We now format the outer inline table only when inserting a group"), but users will still hit it. One option is to skip `fmt()` when the table is already multi-line or has decor containing `#`. Another is to only set decor on the newly inserted key and value.
2. **`project.optional-dependencies`** (`crates/uv-project-edit/src/lib.rs:580-590`) still calls `fmt()` unconditionally, and its comment still says comments can't appear inside inline tables. So `uv add --optional <extra> ...` on a multi-line inline `optional-dependencies` table erases comments in exactly the same way. Fixing both in the same way would keep `--group` and `--optional` behaving consistently.

### Code quality

- The comment "To avoid churn in pyproject.toml, we only sort new group keys if the existing keys were sorted" was deleted in both functions. It explained why sorting depends on `was_sorted`, which still isn't obvious from the code. I'd put it back.
- The early return in `ensure_dependency_group` reads well. The comments "If the group doesn't exist, create it" and "If `dependency-groups` is an inline table, reformat it" were dropped there too. They weren't essential, but the first one is a useful signpost.
- `let new_group = existing_group.is_none();` is fine. You could also get it from the `match` arms, but the current form is clear.

### Tests

- The test is in the right module, uses `uv_snapshot!` and `assert_snapshot!` like nearby tests, and uses `--frozen` with a local package name (`ok==1.0.0`), so it needs no network or `test-*` feature gate. Good.

- **Missing coverage:** nothing tests adding a *new* group to a commented multi-line inline table, which is the path that still drops comments. # REVIEW B

# Review of PR #23017: Preserve inline comments when updating an existing dependency group

This PR fixes the bug it targets: adding to an existing group no longer reformats the inline `dependency-groups` table, so comments on the other keys survive. The logic is right. Skipping `sort_values()` when no key was inserted also changes nothing in practice, because sorting already-sorted keys did nothing. There are a few gaps and follow-ups.

## Potential bugs / remaining gaps

1. **Adding a new group still deletes the comments.** The fix only covers existing groups. On the PR's own fixture, `uv add --group new ok` still reaches `dependency_groups.fmt()` (`crates/uv-project-edit/src/lib.rs:650-657`), which resets the decor on every key and drops `# Local development` and `# Release tests run separately.` The new comment says "Only inserting a key changes the table layout", which reads as if formatting is harmless there. It isn't, now that multi-line inline tables with comments are possible. Options:
   - Insert the new key without calling `fmt()`, and set decor only on the new key and value.
   - At minimum, reword the comment to say the remaining comment loss is a known limitation when adding a group.

2. **`optional-dependencies` has the same bug.** `add_optional_dependency` still calls `fmt()` unconditionally (`lib.rs:584-590`). Its comment still says "you can't put comments between items in an inline table anyway", and this PR's test shows that is no longer true. `ensure_optional_dependency` likely has the same problem. Either apply the same change there or open a follow-up, so groups and extras don't behave differently.

3. **The array indentation in the snapshot is wrong.**
   ```toml
   dependency-groups = {
       dev = [
       "ok==1.0.0",
   ], # Local development
   ```
   `reformat_array_multiline` falls back to a fixed 4-space indent from column 0 and ignores how deep the key is nested. This predates the PR, but the snapshot now locks it in as expected output. Consider fixing the indentation (use the key's indentation plus 4 spaces), or at least add a note that the output is a known imperfection, so nobody mistakes it for intended formatting.

## Code quality

- **Useful rationale comments were removed.** In `ensure_dependency_group` (`lib.rs:668-699`) and in the add path, the PR drops "To avoid churn in pyproject.toml, we only sort new group keys if the existing keys were sorted." It also leaves the `insert` / `sort` / `fmt` lines with no blank lines or comments between them, which is harder to read than before.
- **Possible shared helper.** The "insert a group, sort it if it was sorted, format it if inline" sequence now appears in both `add_dependency_group_requirement` and `ensure_dependency_group`. A small shared helper would stop the two paths from drifting apart again. That matters especially if you fix item 1 in one place.
