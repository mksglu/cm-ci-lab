### 2. Possible bugs and behavior changes

**a) An explicit `undefined` message now throws `ERR_INVALID_ARG_TYPE`.**
The comparison functions now take `...message`, so `assert.strictEqual(1, 2, undefined)` produces `message = [undefined]`. That has length 1, so it skips the "use default" branch. `typeof undefined` is not string, Error or function, so the call ends in:
```ts
throw new ERR_INVALID_ARG_TYPE("message", ["string", "function"], message[0]);
```
Before this PR, the user got a normal `AssertionError` with the generated message. Wrappers that pass their own optional message through are common, e.g. `function check(a, b, msg) { assert.strictEqual(a, b, msg) }`. That means:
- users see a `TypeError` instead of an `AssertionError`, and
- tests that expect `AssertionError` / `generatedMessage === true` break.

`innerOk` handles this case (`args[1] == null`), but `innerFail` does not. I couldn't check Node 26 from this environment. If Node 26 really throws here, this is faithful compat and could use a comment. If not, treat a single `null`/`undefined` like `[]`:
```ts
if (message.length === 0 || (message.length === 1 && message[0] == null)) {
  resolved = undefined;
}
```
Either way, a unit test should pin down this behavior.

**b) `internalMatch` with falsy or non-string first arguments.**
```ts
const generatedMessage = message.length === 0;
message[0] ||= <default regex message>;
```
- `assert.match("a", /b/, undefined)`: `generatedMessage` is `false`, but the message is the generated default. `error.generatedMessage` is wrong.
- `assert.match("a", /b/, 0)` or `""`: the falsy value is silently replaced by the default. For `0`, the other paths would raise `ERR_INVALID_ARG_TYPE`. Note this conflicts with (a): `match(..., undefined)` works, while `strictEqual(..., undefined)` throws.
- `assert.match("a", /b/, "", 1)`: `""` is replaced, and the default message is then passed to `format()` with a stray extra argument.

Setting the default only when `message.length === 0`, and computing `generatedMessage` from the same condition, would be cleaner.

**c) A message function that falls back loses the context-specific default.**
In `internalMatch`, if a message function throws or returns a non-string, `innerFail` passes `message: undefined` to `AssertionError`. You then get the generic operator message (`match`), not the "The input did not match the regular expression …" text. Meanwhile `generatedMessage` stays `false` because `message.length !== 0`.
`innerOk` has the same problem: a message function returning a non-string gives a default message but `generatedMessage = false`. Consider having `innerFail` set `generatedMessage = true` whenever it falls back to `resolved = undefined`, and let callers pass a fallback default message.

**d) `isError` replaces `ObjectPrototypeIsPrototypeOf(ErrorPrototype, …)`.**
`isError` is probably the more correct check, and matches upstream. Still, objects created with `Object.create(Error.prototype)` (and some cross-realm errors) may now be classified differently than in `fail()`, which still uses the prototype check. It's a small inconsistency inside the same module.

**e) Some paths still bypass the shared handler.**
`fail()`, `expectedException` (`throws` / `rejects` with a message), the primitive branch of `expectedException`, and the `compareExceptionKey` no-message path still build `AssertionError` directly. For example, `assert.throws(fn, /x/, (a, e) => "msg")` won't call the function. The PR says it fixes only *part* of #35293, so this is fine, but a TODO or a tracking note in the issue would help.

---

### 3. Performance
- Every comparison call now allocates a rest array (`...message`), including on the success path of hot calls like `strictEqual` / `deepStrictEqual`. V8 optimizes rest params well and upstream Node does the same, so this is acceptable. A micro-benchmark would only matter if assert-heavy test suites are a concern.
- The message function and `format()` run only on failure, which is correct.
- `innerOk(fn, ...new SafeArrayIterator(args))` followed by `ArrayPrototypeSlice(args, 1)` copies arrays twice, but only on the failure path. That's fine.

---

### 4. Security
No concerns. User message functions run inside a `try/catch` that swallows their errors. That matches the intended Node semantics, though it can hide bugs in user-supplied message functions (expected behavior).

This pattern is very common in user code and test helpers:

```js

```

Before this PR it worked: `message: undefined` meant "use the default". `innerOk` already handles this case (`args[1] == null` means a generated message), but the comparison methods and `match`/`doesNotMatch` don't. **2. `generatedMessage` is wrong for `match`/`doesNotMatch` with an explicit `undefined`**

```js
const generatedMessage = message.length === 0;
message[0] ||= ...default...
```

`assert.match("a", /b/, undefined)` sets `message[0]` to the default text, but `generatedMessage` is `false`. The old code used `!message`, which reported `true`. The check should look at whether `message[0]` is falsy, not at the array length.

**3. `internalMatch` uses `||=`, which is looser than `innerFail`**

`message[0] ||= …` silently replaces any falsy first argument, such as `""`, `0`, `null` or `false`, with the default. `strictEqual` throws `ERR_INVALID_ARG_TYPE` for a non-string like `0`, so the two disagree. Also, with `assert.match(s, re, "", extra)`, the default message plus the trailing argument goes through `format()`, so `extra` gets appended to the generated message. Using `??=`, or an explicit "no message given" check, would match the other assertions.

**4. `compareExceptionKey` passes `[message]` without normalising it**

A truthy non-string, non-function message, for example `assert.throws(fn, { code: 'X' }, 42)`, used to be converted to a string by `AssertionError`. It now throws `ERR_INVALID_ARG_TYPE`. That may match Node, but please confirm, because it's a user-visible change.

**5. Message functions that throw or return a non-string**

Both cases fall back to `AssertionError`'s generic default message. For `match` that means the regex-specific default message is lost: `message[0]` is the function, so the `||=` default never applies. `generatedMessage` is also left `false` even though the text was generated. Compare this with Node's behaviour.
