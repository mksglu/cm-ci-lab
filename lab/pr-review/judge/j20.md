# REVIEW A

**Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`** (already merged, with an approval from javache)

**Summary:** The fix is correct and minimal. `object_name[..1]` slices by byte, so it panics when the first character is multi-byte, such as `한`. Replacing it with `object_name.chars().next()` avoids that. The following `is_some_and` check already tests the first char for ASCII alphabetic, `$` or `_`. Non-ASCII names therefore return `false`, which matches the TS regex `^[a-zA-Z$_].*Ref$` that I assume the port mirrors.

**Code quality**
- The change is a one-line removal of the slice, and the surrounding logic stays the same.
- The `.len() > 3` check counts bytes, not characters. This is harmless here. It only decides whether the name is longer than `"Ref"`, and a multi-byte name is always at least as long in bytes. It would be worth confirming that the TS side's `length > 3` has the same semantics for short names. For example, a name like `$Ref` has 4 bytes and 4 chars, so there is no difference for ASCII-first names. This is not a bug.
- You could grep for other `[..1]` or `[..n]` byte slices on identifier names in `compiler/crates/`. The same bug class may exist elsewhere, for example in `is_ref_name` or hook-name checks like `is_hook_name`. I did not check this.

**Potential bugs**
- I found none in the change. The `false` result for non-ASCII names is consistent with the TS behavior. The fixture's expected output shows `한글Ref.current` is not treated as a ref-like access during type inference. It still compiles and memoizes cleanly, because `useRef` already types the variable.

**Performance:** There is no concern. `.chars().next()` is O(1).

**Security:** There are no concerns. The fix removes a compiler panic that user-controlled identifiers could trigger, which is a small robustness gain.

**Test coverage**
- The fixture reproduces the panic and covers the `.current` access path.
- It would be stronger to add a Rust unit test for `is_ref_like_name` with a few inputs: `"한글Ref"`, `"éRef"`, `"fooRef"`, `"$Ref"` and `"ref"`. That would pin the behavior without going through the full pipeline. A fixture whose name starts with a multi-byte character, in a case where the ref-like heuristic actually matters, would be better still. In this fixture `useRef` already gives the type, so the heuristic may not affect the output. That is probably fine as a crash regression test.
- The PR reports that `yarn snap`, `yarn snap --rust`, `scripts/test-rust-port.sh` and `cargo fmt --check` all pass.

**Verdict:** Looks good. The only suggestions are optional: audit for similar byte-slicing and add a small unit test.

# REVIEW B

**Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`**

**Verdict: looks good.** The PR is already merged with an approval from javache.

**The fix**
- `object_name[..1]` slices one byte. On a name that starts with a multi-byte character such as `한`, that byte index isn't a char boundary, so Rust panics.
- The replacement is `object_name.chars().next().is_some_and(...)`. It is boundary-safe, and the surrounding `is_some_and` check was already written for a `char`.
- Behavior now matches the TS regex, which is roughly `^[a-zA-Z_$].*Ref$`. A name starting with a non-ASCII character returns `false`.
- The change is minimal and idiomatic. It adds no allocation and costs nothing measurable.

**Possible issues, all minor**
1. **Length check.** `object_name.len() > 3` counts bytes, not chars. It is only a cheap prefilter, and `ends_with("Ref")` plus the first-char check carry the real logic. For ASCII-first names, a name like `aRef` has 4 bytes and passes, which matches the TS `.+Ref`-style intent. I see no correctness problem. A short comment would help the next reader who wonders about bytes versus chars.
2. **Other byte slicing.** The same class of bug could exist elsewhere in the Rust port, in patterns like `[..n]`, `[1..]` or `.as_bytes()[0]` on identifier names. Identifiers can legally contain Unicode. I'd grep `compiler/crates/` for string slicing on user-controlled names. I haven't done that audit.
3. **Behavioral parity.** The new test shows the compiler no longer panics on the input. The output treats `한글Ref.current` as a normal property access, not a ref access. This matches TS because the regex's first-char class is ASCII-only. The fixture's expected output is consistent with that. It memoizes the `div` with a sentinel check even though the callback mutates a non-ref-typed object. That is fine here because the `useRef` result is typed through the hook's return value.

**Test coverage**
- The regression fixture `repro-ref-like-name-non-ascii.js` and its `.expect.md` reproduce the panic and cover the exact failing path.
- The description reports that `yarn snap`, `yarn snap --rust`, `test-rust-port.sh` and `cargo fmt --check` all pass.
- A Rust unit test for `is_ref_like_name` would be a cheap addition. It could cover `"한글Ref"`, `"ref"`, `"fooRef"`, `"$Ref"`, `"_xRef"` and `"Ref"`. It would pin the behavior without a full compile.
- A name that merely contains a non-ASCII character, such as `fooé`Ref`, would exercise a different path. Its first char is ASCII, so it takes the true branch. That would be a useful extra case.

**Security and performance**
- There are no security concerns. The change removes a panic, which was a potential denial-of-service for the build tooling on valid input.
- There is no performance impact.

**Summary:** the fix is correct and well tested for the reported case. Follow-ups worth considering are a small unit test and a sweep of the Rust port for similar byte-index slicing on identifiers.
