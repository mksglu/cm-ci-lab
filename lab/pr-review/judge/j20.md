# REVIEW A

**Review of #100935: Turbopack: store `ChunkGroupInfo::chunk_groups` as a Vec**

I only read the diff. I did not build it or run the new test. The PR is already merged with approvals from mischnic and sokra.

**Summary**

`ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. `IndexSet` equality ignores order. If the graph entries were reordered, the chunk groups would be renumbered but the new `ChunkGroupInfo` would still compare equal to the old one. The cell would then keep the old `chunk_groups` order. Meanwhile `module_chunk_groups` (the bitsets) and `chunk_group_indices` would use the new numbering, so modules could map to the wrong chunk groups. A `Vec` makes equality order-sensitive, which fixes this.

**Code quality**
- The fix is minimal and correct, and the doc comment explains why it must be a `Vec`.
- Dropping `#[bincode(with = "turbo_bincode::indexset")]` is right, since `Vec` has native bincode support.
- The `.get_index(idx)` to `.get(idx)` updates in `module_batches.rs` and the test helper are straightforward.
- The set-style lookups were presumably already done through `chunk_group_indices` or `chunk_group_keys`. I didn't confirm that every use of `chunk_groups` avoids `get_index_of` or `contains`. Since the change compiled in CI, no such use remains.

**Potential issues**
- **Uniqueness:** an `IndexSet` guaranteed unique chunk groups by construction. A `Vec` does not. This is fine as long as the construction site dedups through `chunk_group_keys`, which is still an `IndexSet`, and pushes only on first insertion. This is worth a quick check, but I saw nothing that suggests a problem.
- **Same bug elsewhere:** the author says they are checking other places where an `IndexSet` or `HashSet` in a cell has the same order-sensitivity problem. `chunk_group_keys` is still an `IndexSet`, but it is marked `unsafe_ignore`, so it isn't compared. That looks consistent. Other `FxIndexSet` fields in turbo-tasks values that are index-addressed would be worth auditing.

**Performance**
- A `Vec` makes equality O(n) in order with no hashing, and `get(idx)` is cheaper than `get_index`. The cost is a slightly larger invalidation surface, because reorderings now propagate. That is the correct behavior.

**Security**
- No concerns.

**Test coverage**
- `test_chunk_group_info_reordered_entries` is a good regression test. It builds two entries, swaps their order through a `State`, recomputes strongly consistently, and asserts that the per-module chunk-group descriptions stay the same. It fails without the fix, because the stale order would map `page1`/`lazy1` to the wrong groups.
- The test is a unit test of Turbopack internals. That is acceptable because no Next.js e2e test could easily reproduce a reordering of entries across a warm cache.
- Minor: the test asserts only on `page1.js` and `lazy1.js`. Including `page2.js` and `lazy2.js` would also catch a swap of the second pair, though checking the first pair is already enough to detect it.

**Verdict**

Looks good. This is a correct, well-documented fix with a targeted regression test. The only follow-up is the broader audit of order-insensitive collections in cell values that the author already mentioned.

Turbo-tasks then kept the old cell contents. Meanwhile `module_chunk_groups` and `chunk_group_indices` carried the new numbering, so indices pointed at the wrong groups. A `Vec` makes equality order-sensitive, which is what you want when the position is the identity.

**Code quality**
- The doc comment on the field explains exactly why it must be a `Vec`. This will stop someone from "tidying" it back to an `IndexSet` later.
- The `get_index(i)` to `get(i)` changes in `module_batches.rs` and in the test helper are mechanical and correct.

Worth confirming that no lookup by value, such as `get_index_of` or `contains`, still relies on the set's O(1) behavior. A `Vec` would make that O(n). The diff shows none, and the separate `chunk_group_indices` map presumably covers that need.
- Dropping `#[bincode(with = "turbo_bincode::indexset")]` is right, because `Vec` encodes natively. It does change the serialized format of persistent-cache entries. That is fine as long as the cache version or schema hash is bumped by the usual mechanism, which I didn't check.

**Potential issues**
- `chunk_group_keys` is still an `FxIndexSet` marked `unsafe_ignore`. It is excluded from equality, so it doesn't cause the same bug. But if its order can change independently of `chunk_groups`, a stale order could survive in the cell. The PR description says other places are still being audited, so this looks like one to check.
- A `Vec` no longer deduplicates. If the builder relied on `IndexSet::insert` returning an existing index to dedupe, duplicates would now appear. I assume the builder keeps its own set for that and only converts at the end, but I couldn't see that in the diff.

**Performance**
- Equality now compares element by element in order. That is cheaper than set comparison, which does hashing and lookups. There is a slight upside, with no meaningful downside.
- When the order changes, the cell now invalidates, so downstream tasks re-run. That is the intended trade-off for correctness.

**Security:** No concerns.
