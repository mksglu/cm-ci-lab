**Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`** (already merged, approved by javache)

**Summary:** The fix is correct and minimal. `object_name[..1]` slices by byte, so it panics when the first character is multi-byte, such as `한`. Using `.chars().next()` takes the first Unicode scalar, so no slicing happens. The `is_ascii_alphabetic() || '$' || '_'` check then returns `false` for non-ASCII starts. The PR says this matches the TS regex `^(?:[a-zA-Z$_][a-zA-Z$_0-9]*)Ref$`. I didn't check that against the TS source.

**Code quality**
- The change is a one-line fix and is idiomatic.
- `object_name.len() > 3` counts bytes, not chars. This is harmless here: for ASCII names it matches the TS behavior, and for non-ASCII names the first-char check rejects them anyway. A short comment on that would help the next reader.

**Potential bugs**
- I found none in the changed line.
- Other places in the Rust port may do byte-slicing like `s[..n]` or `s[n..]` on identifier names. These would have the same panic class. It's worth grepping `compiler/crates` for `[..1]`, `[..n]`, and `&name[` patterns. The earlier `is_ref_like_name` fix in the recent commit history hints this may recur.

**Performance:** No concern. `chars().next()` is O(1).

**Security:** The fix removes a compiler panic that attacker-influenced identifiers could trigger. It's a robustness issue, not a vulnerability.

**Test coverage**
