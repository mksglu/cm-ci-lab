# REVIEW A

## Review of PR #100935: store `ChunkGroupInfo::chunk_groups` as a `Vec`

This PR is already merged with two approvals. I read the diff only. I did not build the code or run the tests.

### Summary
`ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. `IndexSet` compares as a set, which ignores order. So if the graph entries were reordered, the chunk groups were renumbered but the new value still compared equal to the old one. Turbo-tasks would then keep the old cell contents. `module_chunk_groups` (bitsets) and `chunk_group_indices` would already use the new numbering, so modules would resolve to another entry's chunk groups. Switching to `Vec` makes equality order-sensitive, which fixes this at the source.

### Code quality
- **Fix:** It is minimal and targeted. The doc comment explains why it must be a `Vec`, which will stop someone from "restoring" the `IndexSet` later.
- **Call sites:** `get_index(idx)` becomes `get(idx)` in `module_batches.rs` and in the test helper. Both are equivalent for an index lookup.
- **Serialization:** The `#[bincode(with = "turbo_bincode::indexset")]` attribute is dropped. `Vec` uses the default bincode encoding, so no custom code is needed.
- **Uniqueness:** The `IndexSet` also guaranteed uniqueness and gave O(1) `ChunkGroup` to index lookup. I didn't check whether anything relied on either. `chunk_group_indices` and `chunk_group_keys` appear to cover the lookup. Please confirm that nothing calls `get_index_of` or `contains` on the old field. A grep would show it, and it compiled, so this is probably fine.
- **Related risk:** `chunk_group_keys` still uses `FxIndexSet` and is marked `#[turbo_tasks(unsafe_ignore)]`, so it is excluded from equality. That is probably intentional. The PR description says other similar places are still being checked, so it is worth a follow-up audit of the other `IndexSet`/`IndexMap` fields in this struct. Any index-addressed collection has the same hazard.

### Potential bugs
I found none in the diff. The only behavioural change is that a reorder now invalidates dependents. Before, they were wrongly kept.

### Performance
- **Cost:** The change can cause some extra invalidation when only the order changed. That is the correct behaviour, because the numbering did change.
- **Memory:** A `Vec` is slightly lighter than an `IndexSet`, since it has no hash table.

### Security
No concerns. No request headers or external input are involved.

### Test coverage
- **Regression test:** `test_chunk_group_info_reordered_entries` is a good integration-style test. It builds two entries with async children, flips the entry order through `turbo_tasks::State`, and asserts that `get_chunk_groups_for_module` still returns the right groups for `page1.js` and `lazy1.js`. This is the failure the PR describes, and it follows the repo's preference for integration tests over implementation-mirroring unit tests.
- **Fixture:** The test uses a `State` cell, `read_strongly_consistent`, and `TurboTasksBackend` with `noop_backing_storage`, like the neighbouring tests.
- **Nit:** The `_ => "other"` fallback in the test hides new `ChunkGroup` variants. Asserting on the variants that can occur here would make that case fail loudly.
- **Nit:** The test only covers entry reordering. A second case with a different number of entries, or one using `IsolatedMerged`, would exercise the remaining variants. That is optional.

### Verdict
This is a correct, well-documented fix with a targeted regression test. The follow-up I would suggest is the audit of other set-semantics collections in `ChunkGroupInfo` and nearby cells, which the author already mentioned.
