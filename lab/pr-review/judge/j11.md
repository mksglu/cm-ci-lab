# REVIEW A

**Review of PR #38034: View Transitions: update error message classification for Chrome 153** (already merged, approved by rickhanlonii)

**Summary:** The PR replaces the exact-match `if` chain in `customizeViewTransitionError` with a `switch`. It suppresses the unactionable Chrome 153+ `InvalidStateError` messages (`Document hidden`, `Viewport size changed`, and the reason-less forms). It also adds the Firefox messages. In DEV, it wraps the `Snapshot capture failed` and `Animation start failed` cases with a hint about duplicate `view-transition-name`.

**Code quality**
- The switch reads better than the long `||` chain. The per-browser comments (`// Chrome 153+`, `// Firefox`, `// Safari`) make the list easy to maintain.
- Matching exact strings, not `startsWith`, is the right call. It keeps actionable reasons such as `Unsupported layout or style` visible, and the PR description explains this.
- Falling through to `break` in production for the Snapshot/Animation cases leaves the original error intact. DEV adds the hint and keeps the original as `cause`. That is a sensible split.
- The `eslint-disable-next-line react-internal/prod-error-codes` comment is appropriate because the message is DEV-only. The PR also doesn't need an entry in `scripts/error-codes/codes.json`.
- Nit: the comment `Chrome 152 and earlier use a generic error message` sits above the cases that include the Chrome 153+ ones. It is slightly misleading. Moving the 153+ cases under their own comment would be clearer.
- Nit: `{cause: error}` in the `Error` constructor depends on ES2022 support. React already uses this elsewhere, but check that every supported target handles it. The options argument is simply ignored where it isn't supported.

**Potential bugs / risks**
- Exact string matching is brittle by design. A future Chrome change to wording or punctuation will make these errors surface again. The trailing-period variant (`...invalid state.`) already shows that. Adding the test for the "other reasons are reported" path was a good idea. A comment pointing to the Chromium source file, or to the tracking issue #37669, would help the next person who has to update this.
- The DEV hint says it "usually means that two elements have the same view-transition-name". The PR notes that the failures are only observed this way. Because the message says "usually", it is acceptable. It could still mislead for other causes of snapshot capture failure. The `cause` and the "Check the console" line mitigate that.
- The Firefox strings (`Skipped ViewTransition due to document being hidden`, `Skipped view transition due to viewport resize`) are hard to check from the diff alone. Verify them against Gecko's source. I haven't done that here.

**Performance**
- There is no meaningful impact. This is an error path, and a `switch` on strings is trivial.

**Security**
- There are no concerns. The change only classifies error messages and builds a static string. The original error is preserved as `cause`.

**Test coverage**
- The tests cover three paths: a suppressed message, an unknown message that is still reported, and the DEV hint with the `cause` check, including the production branch. They follow the pattern of the other tests in the file and use `@gate enableViewTransition`.
- Gaps (minor):
  - Only one suppressed message (`Document hidden`) is tested. A `test.each` over all the suppressed strings, including the Firefox and Safari ones and the legacy no-suffix form, would guard against typos in the list. One cheap option is to export the list and test it.
  - The `Animation start failed` case isn't tested separately, though it shares code with `Snapshot capture failed`.
  - The test mocks a rejected `ready` promise. It doesn't cover the same error arriving through `finished`. I haven't checked whether the code handles both the same way.

**Verdict:** The change is good and well-scoped, and the tests are solid. The remaining points are small: the misplaced comment, a parameterized test over every suppressed message, and a pointer to the Chromium source or issue for future maintainers.

# Review of PR #38034: View Transitions error message classification for Chrome 153

The PR is already merged and approved. I read the diff only and did not run the tests.

## Summary
Chrome 153 appended reasons to the `InvalidStateError` messages, for example `...invalid state. Document hidden`. The old exact-match suppression stopped matching, so these errors started reaching `onRecoverableError`. The PR:
- Converts the `if` chain to a `switch`.
- Whitelists the unactionable messages for Chrome 153+, Firefox and Safari.
- Adds a DEV-only wrapped error with a hint for `Snapshot capture failed` and `Animation start failed`.
- Adds tests.

## What's good
- **Allow-list approach.** The PR deliberately avoids `startsWith`, so new or actionable reasons such as unsupported layout or style still surface. A test covers this.
- **Preserved error.** `{cause: error}` keeps the original error, and the test asserts on it.
- **Readable layout.** The per-browser comments make the long list of cases easy to follow.
- **Production behavior.** In production the two snapshot and animation cases `break` and fall through to the original error. The test asserts this for the non-DEV branch.

## Potential issues and suggestions
1. **Brittle exact-string matching.** This is inherent to the approach and is what broke here. The next Chromium message tweak will reintroduce the noise. Consider a short comment pointing at the Chromium source or the issue (#37669), so that whoever updates it next knows where to look.
2. **Test coverage is narrow.**
   - Only one suppressed message, `Document hidden`, is tested end to end. The other roughly nine suppressed strings are untested. A `test.each` over the list would cheaply guard against typos, such as a missing trailing period.
   - `Animation start failed` has no test, only `Snapshot capture failed`.
   - The generic Chrome 153 `...invalid state.` message with a trailing period is untested.
3. **Test helper.** `renderWithSkippedTransition` rejects `ready` but resolves `finished`. That is fine for these cases, but it doesn't check that `finished` rejection paths are handled the same way. This is minor.
4. **`@gate` and `__DEV__` branching in tests.** The `if (__DEV__)` branch in the last test is acceptable. The repo sometimes prefers `// @gate __DEV__` or separate tests, so this is only a style point.
5. **Error message wording.** "This usually means that two elements have the same view-transition-name" is helpful. The PR description says these failures can also come from other causes, so "usually" is reasonable. You could name the likely culprit, such as duplicate `name` props on `<ViewTransition>` or CSS `view-transition-name`, to make it more actionable.
6. **Lint suppression.** `eslint-disable-next-line react-internal/prod-error-codes` is justified because the error is DEV-only. Add a brief comment saying so if one isn't already nearby.

## Performance and security
- **Performance.** There is no concern. The `switch` runs only on the error path.
- **Security.** There is no concern. The code matches static strings and does not interpolate untrusted input. The original error is carried in `cause` rather than concatenated into the message.

## Verdict
This is a solid, targeted fix. The main follow-up is broader test coverage of the suppressed strings and of `Animation start failed`. It is not blocking.
