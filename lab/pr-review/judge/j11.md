# REVIEW A

I'd approve this PR. The fix is narrow and correct: errors from `'use cache'` functions that the page catches no longer fail prerendering, and the shared digest map that logging relies on still works. My suggestions are small and none of them block merging.

## What the PR changes

`prerenderToStream` used to pass `workStore.reactServerErrorsByDigest` back as `digestErrorsMap`. The caller then reads it at `app-render.tsx:2749` to decide whether the prerender failed. That shared map is also written by:
- the `'use cache'` "Cache" environment handler (`use-cache-wrapper.ts:1424`);
- the dev abort path (`use-cache-wrapper.ts:1688`);
- the validation renderer (`app-render.tsx:8695`).

So an error thrown inside a cached function landed in the map even when the page caught it, and the build failed. The PR adds a separate `renderErrorsByDigest` map that only the page's own RSC handler writes to, and uses it for failure detection.

## Correctness

- **The new map gets every error the old map got from the page's handler.** It's filled at the same point in `createReactServerErrorHandler` as before, after digest recovery, so nothing that used to fail the build silently passes now.
  - **Uncaught cached error in production:** the obfuscated error arrives with a digest, `err` is swapped for `originalError`, and that original goes into `renderErrorsByDigest`. The build still fails with the readable error.
  - **Rejected promise passed to a client component:** Flight calls `onError` while serialising the rejection, so it still goes through `serverComponentsErrorHandler` and is recorded.
  - **Prospective and other custom `onError` callbacks** (e.g. lines 9761 and 10539) delegate to `serverComponentsErrorHandler`, so the map is filled the same way it was before.
- **Lookups that need the full map still use it.** The SSR filtering at `:10520` and `:10834`, the rethrow at `:10418`, and `createHTMLErrorHandler` all keep reading `reactServerErrorsByDigest`. That's right: they need to recover the original error or skip duplicate logging, including for errors that came from cached functions.
- **One small difference in what gets stored.** The shared map has an `if (!has)` guard, so the first error per digest wins. The new map has no guard, so the last one wins. In production both end up holding `originalError`. In dev a later duplicate could replace an earlier object with the same digest. Only the first value is used for failure detection, so this has no practical effect. Still, using the same `!has` guard in both places would keep them consistent.

## Code quality

- **Positional `undefined` argument.** In `createReactServerErrorHandler(..., onHTMLRenderRSCError, undefined, renderErrorsByDigest)`, the `undefined` exists only to skip `spanToRecordOn`. The function now has two optional trailing parameters, and one of them is typed `any`. An options object (`{ spanToRecordOn?, renderErrors? }`) would read better at the call site and be harder to misuse later.
- **The `@TODO` above the guard is now partly out of date.** The comment at `create-error-handler.tsx:113` ("by putting this here and not at the top it is possible that we don't error the build…") now describes `renderErrorsByDigest` more than `reactServerErrors`, which is no longer used for failure detection here. Updating it would help the next reader.
- **The new comment at `app-render.tsx:9050` is good.** It explains clearly why there are two maps.

## Tests

The new e2e suite is small and focused, uses a real fixture directory, and covers both build-time (`static`) and on-demand (`runtime`) prerendering. If the bug came back, the build would fail during setup, so the regression is caught. Suggestions:

1. **Possible flakiness in the HIT check.** With `cacheComponents`, the first request to `/runtime` may serve a shell and finish generating in the background. If so, an immediate second fetch may not be a `HIT` yet. Consider wrapping the second fetch in `retry()` from `next-test-utils`:
   ```ts
   await retry(async () => {
     const res = await next.fetch(`/${id}`)
     expect(res.headers.get('x-nextjs-cache')).toBe('HIT')
   })
   ```
2. **Logging isn't checked.** The PR says it "preserves the shared lookup for logging" (#86500), but no test confirms the caught error is still logged. An assertion that `next.cliOutput` contains `Cached function failed: static` (in start mode, after the build) would protect that.
3. **No check that an uncaught error still fails.** It's worth confirming that an existing suite covers an uncaught `'use cache'` error failing `next build` with the de-obfuscated message. If none does, add a small case here, since this PR changes exactly that decision.
4. **Deploy mode only checks status and body.** `isNextStart` is false in deploy mode, so only those two assertions run there. That's reasonable because `x-nextjs-cache` isn't reliable on Vercel, but it means the cacheability check only runs locally.

## Performance and security

- **Performance:** each prerender now allocates one extra `Map` and does one extra `set` per reported error. That cost is negligible.
- **Security:** no new headers, inputs or outputs are introduced. Production failure detection still uses `originalError`, but only on the server, so nothing new reaches the client.

# REVIEW B

I reviewed PR #100956, "Fix prerendering of caught `'use cache'` errors", by unstubbable. It's already merged, so these notes are for follow-up only. I traced the change through `app-render.tsx`, `create-error-handler.tsx` and `use-cache-wrapper.ts`; I didn't build it or run the tests.

**Verdict:** the fix is correct and well scoped. I found no bugs, only small API and test-coverage suggestions.

## What the PR fixes

Two error handlers write to the same `workStore.reactServerErrorsByDigest` map:
- the `'use cache'` handler (`use-cache-wrapper.ts:1424`), which records every error thrown inside a cached function, so logging can recover the original error (#86500);
- the page's RSC handler.

`prerenderToStream` returned that shared map as `digestErrorsMap`. `app-render.tsx:2749` then treats the first entry as a render failure. So a page that catches an error from a `'use cache'` function still failed the build, or was marked as an error during on-demand prerendering, and its fallback was not cached.

The PR adds a local `renderErrorsByDigest` map. Only the page's RSC handler (`serverComponentsErrorHandler`) writes to it, and every `digestErrorsMap` return in `prerenderToStream` now uses it. The shared map is still used for recovering original errors, for the thrown error at `app-render.tsx:10418`, and for `createHTMLErrorHandler`'s check for duplicate RSC/SSR errors. This is the right split.

## Correctness

- **All failure paths still record errors.** Each render whose result can reach `digestErrorsMap` sends errors to `serverComponentsErrorHandler`:
  - the final prerender (`onError` at ~9761);
  - the dynamic and static renders (10211, 10262);
  - the error-shell renders (10538, 10774, 10848).

  The prospective render (~9360) uses its own handler and never wrote to the map before, so it behaves the same.
- **Errors that escape the page are still reported.** When a cached function's error is not caught, it reaches the page's handler with its digest. The handler then writes it to `renderErrorsByDigest` (in production as the recovered `originalError`), so build failures for uncaught errors are kept.
- **Dev-only timeout/deadlock errors are unaffected.** `use-cache-wrapper.ts:1688` writes those straight into the shared map. If one escapes the page, the page handler records it in the new map as usual.
- **The early-return path is fine.** The return at ~10097 already used `new Map()`.

## Code quality

1. **Positional parameter (`create-error-handler.tsx:61`).** The PR adds a sixth optional parameter after the untyped `spanToRecordOn?: any`, so the caller has to pass a bare `undefined`:
   ```ts
   onHTMLRenderRSCError,
   undefined,
   renderErrorsByDigest
   ```
   Six parameters, three of them maps or callbacks, is getting hard to read. An options object (`{ spanToRecordOn, renderErrors }`) would make call sites self-describing and avoid placeholder `undefined`s. Not a blocker, but worth doing before another parameter is added.

2. **Inconsistent write rule (`create-error-handler.tsx:115-119`).** The shared map only writes if the digest is missing (`if (!reactServerErrors.has(...))`), but the new map always overwrites (`?.set`). This makes no difference today: only the first value is read, and overwriting a key keeps its position in the map. Still, either matching the `has` check or adding a comment explaining why overwriting is fine would make the code easier to follow.

3. **Outdated comment.** The `@TODO` above the shared-map write ("we don't error the build in places we actually expect to") sits right next to the new line and now arguably applies more to `renderErrorsByDigest`. Consider updating or moving it.

4. **Naming.** `reactServerErrorsByDigest` (from the work store, used for logging) and `renderErrorsByDigest` (local, used for failure detection) are easy to mix up. The comment at 9050–9053 explains the difference well. A name like `pageRenderErrorsByDigest` would make it obvious without the comment.

## Test coverage

The new e2e suite is small and uses a real fixture directory, as the repo guidelines prefer. It covers:
- a build-time prerendered param (`/static`, from `generateStaticParams`);
- an on-demand param (`/runtime`), whose fallback is checked to be cached (`x-nextjs-cache: HIT`) under `next start`.

A build failure would break `nextTestSetup`, so build-time regressions are caught indirectly. Suggestions:

- **Test the other half of the contract.** The PR deliberately keeps original-error logging for caught `'use cache'` errors (#86500). An assertion that `next.cliOutput` still contains `Cached function failed: static` in start mode would stop a future fix that wrongly hides the error entirely.
- **Assert there's no prerender error message.** In start mode, check that `next.cliOutput` doesn't contain `Error occurred prerendering`. That makes the build-time check explicit instead of relying on setup failing.
- **Add an uncaught-error test.** A route where a `'use cache'` function's error is not caught, checked at on-demand time (`/[id]` with a param outside `generateStaticParams`), would confirm genuine failures still return 500 and aren't cached. It runs on demand so the build doesn't fail. That is the main risk of this change, and nothing currently guards it.
- **Deploy mode.** The `HIT` check is correctly limited to `isNextStart`. The fixture doesn't revalidate anything, so the shared-project caveat in AGENTS.md doesn't apply.

## Performance and security

- **Performance:** one small `Map` per prerender and one optional `set` per reported error. Negligible.
- **Security:** no new request inputs or headers are read. A caught error's message was already not exposed to the client and is still logged on the server, as intended.
