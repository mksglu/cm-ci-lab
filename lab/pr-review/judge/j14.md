# REVIEW A

**Review of #23017: Preserve inline comments when updating an existing dependency group** (already merged)

**Summary:** The fix is correct and small. `fmt()` and `sort_values()` now run only when a key is inserted into the inline `dependency-groups` table. Adding to an existing group's array no longer clears the comments on the surrounding keys. I read the diff only and did not build it or run the tests.

**Code quality**
- The `new_group` flag in `add_dependency_group` is clear. Moving `was_sorted` inside it is right, because sorting only matters when a key is added.
- The second function (the "ensure group exists" helper) now returns early when the group exists, which is easier to read than the old `if !group_exists` block. The old duplicated comment about reformatting was misleading, since inline tables can hold comments, and its removal is welcome.
- The `get_mut("dependency-groups").and_then(Item::as_inline_table_mut)` then `fmt()` block now appears in two places. A small private helper would remove the duplication, but this is minor.

**Potential issues**
- Inserting a new group into an inline table still calls `fmt()`, so comments on the existing keys are still lost in that case. For example, `uv add --group lint` on the table from the test would drop `# Local development`. The PR description says this is intended ("only when inserting a group"). A test pinning that behavior, or a code comment saying it is a known limitation, would make the scope explicit.
- Newly added keys are not covered by the "comments preserved" guarantee. I'd expect that to be acceptable, but the PR doesn't say so.

**Test coverage**
- `add_dev_preserves_inline_group_comments` covers the regression directly and matches the style of nearby tests (`uv_snapshot!`, `assert_snapshot!`, `context.read`).
- The snapshot locks in ugly output. The expanded `dev = [\n    "ok==1.0.0",\n], # Local development` has inconsistent indentation. That is existing array formatting and not a regression, but a future formatting improvement will need to update this snapshot. A short doc comment explaining the scenario would help, as the AGENTS.md guidelines suggest for non-obvious regressions.
- The test is placed just before `add_group_comment` and sits between that test and its doc comment. This is cosmetic.
- There is no test for the sibling path, the "ensure group exists" helper (it appears to be used by `uv add --group` with no requirements, or similar). Its early return is new behavior, and a test that it leaves the document byte-identical for an existing group would be cheap.
- The `--frozen` flag with `ok==1.0.0` avoids resolution and network access, so no `test-...` feature gate seems necessary.

**Performance and security:** No concerns. Skipping the reformat on the common path is a negligible gain.

**Verdict:** Good, focused fix. The suggestions above are non-blocking: a helper for the duplicated `fmt` block, and a test or comment documenting the new-group insertion behavior.

**Review of PR 23017: Preserve inline comments when updating an existing dependency group** (already merged)

**Summary:** The fix is sound. Skipping the whole-table `fmt()` when only an existing array changes is the right way to keep the neighbouring comments. I didn't build the change or run the tests.

**Potential issues**

  ```

  "ok==1.0.0",
  ], # Local development

The removed old comment said "you can't put comments between items in an inline table", which this test shows is false for multi-line inline tables. Inserting a group into a commented table still loses comments. This is a known limit, but a test or a note would make it explicit.

**Performance and security:** No concerns. This is a small, local edit.
