# REVIEW A

**Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`** (already merged, with an approval from javache)

**Summary:** `object_name[..1]` slices one byte. If the name starts with a multi-byte UTF-8 character such as `한`, the slice lands inside the character and Rust panics. The PR replaces it with `object_name.chars().next()`, which reads the first character safely.

**Correctness**
- The fix is correct and minimal. `.chars().next()` is boundary-safe. The `is_some_and(|c| c.is_ascii_alphabetic() || c == '$' || c == '_')` check then returns `false` for non-ASCII first characters. That matches the TS regex, which is roughly `/^(?:[a-zA-Z$_][a-zA-Z$_0-9]*)Ref$/`, so behavior is consistent between the two compilers.
- The `object_name.len() > 3` check counts bytes rather than characters. Since `"Ref"` is 3 bytes and the name must also start with an ASCII character, this is harmless. Non-ASCII names are rejected earlier by the first-character check. It would still be worth a short comment, or a second look, if the port is meant to mirror the TS `.length` semantics.
- The same pattern may exist elsewhere. Other byte-slicing like `[..1]`, `[0..n]` or `&s[1..]` on identifier names in `compiler/crates/` could panic the same way. It would be worth running `rg '\[\.\.\d\]|\[\d+\.\.'` over the crates to check. This is a suggestion for a follow-up, not a defect in this PR.

**Style and conventions**
- The change is small and idiomatic, and the PR description clearly links the issue (#38023).
- The `[rust-compiler]` title prefix matches recent commits.

**Test coverage**
- The fixture `repro-ref-like-name-non-ascii.js` reproduces the panic, and the PR reports it passing under `yarn snap`, `yarn snap --rust` and `test-rust-port.sh`.
- Nit: the fixture covers only the case where the first character is non-ASCII. A Rust unit test for `is_ref_like_name` would pin the behavior more directly and run faster. It could cover `"한글Ref"`, `"fooRef"`, `"$Ref"`, `"_Ref"`, `"ref"` and `"Ref"`. Names where only a later character is non-ASCII, such as `"a한Ref"`, would also be worth including.
- The expected output shows `한글Ref.current` being treated as a plain mutable property, not a ref access. That follows from the name not being treated as ref-like. The test records current behavior and matches the TS output, so it is acceptable.
- The file name starts with `repro-`, which is the usual convention in this fixtures directory.

**Performance and security**
- There is no performance impact. `.chars().next()` is O(1) for the first character.
- This is a denial-of-service fix for the compiler, since input source could crash a build tool. It has no other security implications.

**Verdict:** LGTM. The fix is correct and well tested. My only suggestions are an optional Rust unit test and a sweep for similar byte-slicing elsewhere in the crates.

# REVIEW B

**Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`**

**Summary:** The change replaces the byte slice `object_name[..1]` with `object_name.chars().next()`. The old slice panics when the first character is multi-byte, because the slice lands inside a UTF-8 code point. The PR is already merged and approved. The diff looks correct.

**Code quality and correctness**
- The fix is minimal and idiomatic. `chars().next()` reads the first Unicode scalar without slicing, so it can't panic on a char boundary.
- Behavior matches the TS regex. `한글Ref` starts with a non-ASCII character, so `is_ascii_alphabetic() || '$' || '_'` is false and the function returns `false`.
- The `object_name.len() > 3` check counts bytes, not chars. That is harmless here, since it is only a cheap precheck and `ends_with("Ref")` plus the first-char test decide the result. A name like `Ref` alone (length 3) is still excluded as intended. If it ever needs to match the TS semantics exactly, the TS check is probably `/^[a-zA-Z_$]\w*Ref$/`-like. The Rust version doesn't verify that the middle characters are `\w`, but that gap existed before this PR.
- A quick grep for other `[..1]`, `[0..1]` or similar byte slices on user-controlled identifier strings in `compiler/crates/` would be worthwhile. The same class of bug may exist elsewhere, for example in `is_ref_or_ref_value` style helpers or hook-name checks like `use[A-Z]`.

**Potential bugs**
- I found none in the change itself.
- The edge case where the first character is non-ASCII but the name should otherwise be ref-like is intentional and matches TS.

**Performance**
- `chars().next()` is O(1), so there is no regression.

**Security**
- This removes a compiler panic that untrusted or unusual source could trigger, so it is a small robustness gain. There are no new concerns.
