# REVIEW A

**Review of PR 36944: assert message functions and printf-style arguments** (already merged)

Moving message handling into a shared `innerFail` is the right design. It removes the duplicated `innerFail` in `assert.ts` and the per-call `AssertionError` construction. Enabling `parallel/test-assert.js` in `tests/node_compat/config.jsonc` is good coverage. I only read the diff and did not run anything.

**Issues**

1. **Commented-out code left in `internalMatch`.** The old `ObjectPrototypeIsPrototypeOf(ErrorPrototype, message)` block, `const err = new AssertionError({`, `err.generatedMessage = …` and `throw err` are all commented out instead of deleted. This should be cleaned up. If `ObjectPrototypeIsPrototypeOf` and `ErrorPrototype` are no longer used in `assert.ts`, the destructured imports are dead too.

2. **`message[0] ||=` mutates the caller's rest array.** It's harmless today because the array is freshly created. But it also relies on `||=` treating `""` as missing, which would swallow an explicit empty-string message. Building a separate local array would be clearer.

3. **`generatedMessage` is wrong for `match` with an explicit `undefined` message.** `assert.match(s, re, undefined)` gives `message.length === 1`, so `generatedMessage` is `false` even though the default text is used. `innerOk` handles this case with `args[1] == null`. Please check what Node does here and make the two consistent.

4. **Possible `[undefined]` message in `compareExceptionKey`.** It now passes `message: [message]`. If `message` is `undefined`, which is the usual case when the user gave none, `innerFail` sees `typeof undefined`, which is not a string, error or function. That falls into the `ERR_INVALID_ARG_TYPE` branch. Please confirm that call site always has a defined string. Otherwise it should be `message === undefined ? [] : [message]`. Fixing this also keeps `innerFail` from rejecting `[undefined]` on its own.

5. **`expectsError` and `expectsNoError` ignore user messages.** They wrap their generated text in `[…]`. User-supplied messages for `throws`, `doesNotThrow` and similar presumably go through other paths. Function and printf messages for `throws`, `rejects` and `doesNotThrow` therefore likely remain unsupported. That fits the PR's "part of #35293" scope, but it's worth noting in the issue.

6. **`innerFail` return behavior.** It is typed `never`, but TypeScript can't prove that for the `generatedMessage` branch. This is fine.

**Smaller notes**

- The `catch {}` around the message function matches Node (the default message is used) and is documented in a comment.
- `ERR_AMBIGUOUS_ARGUMENT` for trailing arguments after an Error or function matches Node.
- The `args.length === 1 || args[1] == null` fallback to `[]` when `getErrMessage` returns `undefined` is a good defensive fix.
- Because `innerOk` now takes `...args`, `Assert.prototype.ok` and `assert` spread through `SafeArrayIterator`. That is safe, though slightly slower on the hot path. `assert(cond)` passing is unaffected, because the work happens only on failure.

**Tests:** the only coverage is the upstream Node test, which is reasonable for a compat fix. A small spec or unit test for the edge cases above would help: `match` with explicit `undefined`, a message function that throws, and a function followed by trailing arguments.

**Verdict:** the approach is sound. The leftover commented code (#1) and the `[undefined]` risk (#4) are worth a quick follow-up.

# Review of PR #36944: assert message functions and printf-style arguments

The PR is already merged and approved. These notes are from reading the diff only. I didn't build it or run the tests.

## What it does well
- Putting message resolution in one `innerFail()` helper removes the duplicated `AssertionError` construction. `innerOk`, `internalMatch` and the comparison functions now share it.
- The `MessageTuple` type and its doc comment make the internal convention clear.
- Validation is in place: `ERR_AMBIGUOUS_ARGUMENT` for trailing args after an `Error` or function, and `ERR_INVALID_ARG_TYPE` for other types.
- A message function that throws or returns a non-string falls back to the default message, as the PR says Node does.
- The fix in `innerOk` for an unavailable source expression (`getErrMessage` returning `undefined`) is sensible.
- Re-enabling `parallel/test-assert.js` in `config.jsonc` gives real coverage against upstream.

## Issues and suggestions

1. **Leftover commented-out code in `internalMatch`** (`assert.ts`). The old `if (ObjectPrototypeIsPrototypeOf(ErrorPrototype, message))` block, `const err = new AssertionError({`, `err.generatedMessage = ...` and `throw err` are commented out rather than deleted. These should be removed. If `ObjectPrototypeIsPrototypeOf` and `ErrorPrototype` are now unused in `assert.ts`, they should also be dropped from the destructuring to keep lint clean.

2. **`message[0] ||= ...` in `internalMatch` mutates the rest-args array and has edge-case quirks.**
   - If the caller passes `""` as the message, `generatedMessage` is `false` (the length is 1), but the message is still overwritten by the default. Node's `!message` check gives `generatedMessage = true` in that case.
   - When the message is `[]`, it writes index 0 and so changes the array's shape. Building a new tuple would be clearer, for example `const msg = message.length ? message : [defaultMsg]`.
   - A falsy first argument followed by format args (`match(s, r, "", "x")`) is likewise inconsistent.

3. **`compareExceptionKey` now passes `message: [message]` unconditionally.** If `message` can be `undefined` there, the tuple is `[undefined]`. `innerFail` would then throw `ERR_INVALID_ARG_TYPE` instead of using the default message. Please check that every call site passes a defined string. A safer helper would treat `[undefined]` as `[]`. `innerOk` already guards against this explicitly, but `innerFail` doesn't.

4. **Inconsistent `message == null` handling.** `innerOk` treats `args[1] == null` as "no message" even when more args follow, for example `assert(false, undefined, "x")`. `innerFail` treats `[undefined, ...]` as an invalid type. This probably matches Node, but it deserves a comment or a test.

5. **Behavior change for `strictEqual(a, b, undefined)` and similar.** With `...message`, an explicit `undefined` now becomes `[undefined]`, not "no message". This risks a regression: Node's `innerFail` has to handle it, and here it would throw `ERR_INVALID_ARG_TYPE`. Please verify against Node 26, or normalize `[undefined]` to `[]`.

6. **Message functions and `Error` handling.** `isError(message[0])` is checked after the `typeof === "string"` branch. That is fine. The function branch calls the user function with no `this` and swallows all exceptions, which matches the PR description.

7. **Tests.** Coverage rests on the upstream Node test only. A small spec or unit test in `tests/` would be worth adding for the Deno-specific parts, because node_compat can be skipped or reconfigured. It should cover:
   - a function message
   - a printf message (`%s`, `%d`)
   - the trailing-args error for `Error` and function messages
   - `strictEqual(a, b, undefined)`
   - the `match` / `doesNotMatch` message paths

8. **Performance.** The rest args and the tuple allocation are only on the assertion path, apart from the `...message` rest allocation on every call. This is negligible. `innerOk` spreads through `SafeArrayIterator` on the success path, as it did before.

9. **Minor.**
   - The `getErrorSourceExpression` destructuring was reformatted to multi-line for no reason, which is a drive-by change.
   - The PR description says "Node.js 26 behavior". A link to the upstream commit would help future maintainers.

## Security
Nothing of concern. User-supplied functions run only in the failure path, and their exceptions are contained.

## Verdict
The design is sound and the PR is a good step toward #35293. The follow-ups I'd do are:
- clean up the commented-out code
- harden the `undefined` / empty-string message edge cases (items 2, 3 and 5)
- add a few targeted tests
