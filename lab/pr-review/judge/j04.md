# REVIEW A

I approve this PR. The fix is correct and minimal. My one main point is that it only partly closes the gap with the TypeScript regex, and that's worth a follow-up.

## Summary
`is_ref_like_name` used to take `object_name[..1]`, which slices the first byte rather than the first character. That panics when a `*Ref` name starts with a multi-byte UTF-8 character, such as `한글Ref`. The PR switches to `object_name.chars().next()`, which can't panic, and adds a fixture that reproduces the original crash.

## Correctness
- **The fix is right.** `chars().next()` returns the first Unicode scalar value, so it's safe on any `&str`. Wrapping it in `is_some_and` also handles the empty case, although `len() > 3` already rules that out.
- **`object_name.len() > 3` is fine as written.** It counts bytes, but together with `ends_with("Ref")`, more than 3 bytes means at least one whole character comes before `Ref`. So the "bare `Ref` doesn't match" rule still holds for non-ASCII names.

## Remaining mismatch with TypeScript (pre-existing, worth a follow-up)
The comment and the TS source (`InferTypes.ts:785`) use:
```js
/^(?:[a-zA-Z$_][a-zA-Z$_0-9]*)Ref$|^ref$/
```
That regex checks every character before `Ref`. The Rust version only checks the first one. So any name that starts with an ASCII letter, `$` or `_` and has non-ASCII characters later still disagrees:

| name | TS | Rust (after this PR) |
|---|---|---|
| `한글Ref` | false | false ✅ (fixed here) |
| `a한글Ref` | false | **true** ❌ |
| `fooéRef` | false | **true** ❌ |

The PR description says these names "now return `false` like the TS regex does". That's only true when the non-ASCII character comes first. Where they disagree, Rust gives the object a ref type when TS doesn't, so `yarn snap --rust` output could differ from TS for those names. Checking the whole prefix would match the regex exactly:

```rust
fn is_ref_like_name(object_name: &str, property_name: &PropertyNameKind) -> bool {
    // ...
    if object_name == "ref" {
        return true;
    }
    let Some(prefix) = object_name.strip_suffix("Ref") else { return false };
    let mut chars = prefix.chars();
    chars
        .next()
        .is_some_and(|c| c.is_ascii_alphabetic() || c == '$' || c == '_')
        && chars.all(|c| c.is_ascii_alphanumeric() || c == '$' || c == '_')
}
```
This also removes the byte-based `len() > 3` check, because an empty `prefix` already fails at `chars.next()`. That's cleaner and doesn't depend on bytes versus characters. This could go in a follow-up since it predates this PR, but it's small and fits the issue being fixed.

## Test coverage
- The new fixture `repro-ref-like-name-non-ascii.js` covers the panic, and its expected TS output confirms the name isn't treated as a ref. Good.
- **Suggestion:** add a second fixture where the non-ASCII character comes after an ASCII first character, e.g. `const a한글Ref = useRef(0)`. With the current Rust code, `yarn snap --rust` should differ from TS on it, which is exactly the kind of regression the fixture suite is there to catch.
- A small Rust unit test on `is_ref_like_name` would be cheap and test it directly: `"ref"`, `"Ref"`, `"fooRef"`, `"$Ref"`, `"_Ref"`, `"1Ref"`, `"한글Ref"`, `"a한글Ref"`, and a name not followed by `.current`.

## Other notes
- **Other byte slices:** I searched `compiler/crates` for byte-range slicing of strings like `[..1]` and `[1..]`. The only other hit is `disjoint_set.rs:39`, which slices a slice of items, not a string, so it's safe. I didn't find other byte-slicing panics of this kind.
- **Performance:** no concern. `chars().next()` costs the same as the old code.
- **Security:** no concerns. If anything, removing a panic that any input source can trigger makes the compiler more robust.
- **Conventions:** the `[rust-compiler]` title prefix matches `compiler/.claude/rules/commit-convention.md`. The fixture uses the `repro-` naming used for regressions.

# REVIEW B

The fix is correct and ready to merge; the main follow-up is a remaining mismatch with the TypeScript regex (point 1).

## Review: PR #38025, `[rust-compiler] Fix non-ASCII panic in is_ref_like_name`

### Summary
`object_name[..1]` takes the first *byte* of the string. When the name starts with a multi-byte UTF-8 character (e.g. `한글Ref`), byte 1 falls inside that character and the slice panics. Calling `object_name.chars().next()` reads the first full character instead, so the panic is gone. Because `is_ascii_alphabetic()` is false for `한`, the function now returns `false`. That matches the TS regex `/^(?:[a-zA-Z$_][a-zA-Z$_0-9]*)Ref$|^ref$/`, which also rejects it.

The change is small and clearly correct.

### Code quality
- Dropping the slice and calling `.chars().next()` directly is the idiomatic fix. The `[..1]` slice did nothing useful even in the ASCII case.
- `object_name.len() > 3` counts bytes, not characters. That's still fine: `ends_with("Ref")` requires 3 ASCII bytes at the end, so `len() > 3` correctly means "at least one byte before `Ref`". Since `chars().next()` is now safe, nothing else in the function depends on byte boundaries.

### Remaining mismatch with the TS regex (worth fixing here or in a follow-up)
The Rust version only checks the **first** character. The TS regex also requires every character between the first one and `Ref` to be in `[a-zA-Z$_0-9]`. So non-ASCII characters in the middle of the name still produce different results:

| Name | TS `RefLikeNameRE` | Rust (after this PR) |
|---|---|---|
| `한글Ref` | false | false ✅ |
| `a한글Ref` | false | **true** ❌ |
| `fooÜberRef` | false | **true** ❌ |

When Rust returns true, it unifies the object with the `BuiltInUseRefId` shape and TS doesn't. That changes the output and the ref-access validation results for these names. This bug existed before the PR and doesn't cause a panic, but it sits right next to this fix. A version that matches the regex exactly:

```rust
fn is_ref_like_name(object_name: &str, property_name: &PropertyNameKind) -> bool {

    if object_name == "ref" {
        return true;

```

This also removes the byte-length check, so the code no longer depends on byte counts.

- A small `#[cfg(test)]` unit test for `is_ref_like_name` would be cheap and would cover the edge cases directly: `ref`, `Ref`, `aRef`, `$Ref`, `_Ref`, `1Ref`, `한글Ref`, `a한글Ref`, `fooRef` with a non-`current` property.

### Performance and security
- **Performance:** no concerns. `chars().next()` costs the same as the old slice.
- **Security:** the change removes a way for user-controlled input (an identifier name) to crash the compiler. That's a small robustness win, especially for any tooling that runs the compiler on untrusted code.
