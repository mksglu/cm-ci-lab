# Review: PR #37046 — fix(tls): distrust compromised eMudhra certificate authorities

## Summary

The PR does three things:

1. **TLS verifier:** bumps `rustls-webpki` to 0.103.16, which rejects certificate chains that contain the eight compromised eMudhra keys, including cross-signed ones.
2. **Root bundles:** bumps `webpki-roots` and `webpki-root-certs` to 1.0.10, which drops `emSign ECC Root CA - G3`. It also pulls in `webpki-roots` 0.26.11, which is just a thin wrapper over 1.0.10, so `reqwest` and `hyper-rustls` get the fixed bundle too.
3. **AWS-LC:** bumps `aws-lc-rs` to 1.18.2 and moves `ext/crypto/mldsa.rs` from the `unstable::signature` API to the stable `signature` API.

The security goal is sound and the approach is right: fix it in the verifier (`rustls-webpki`) and not only by removing the root, because removing the root alone wouldn't stop cross-signed paths. The `0.26.11` wrapper trick is a neat way to make sure no transitive copy of the old roots is left behind. My concerns are about side effects of the AWS-LC bump.

## Issues

### 1. Two copies of AWS-LC are now linked (medium)

`Cargo.lock` now has both `aws-lc-sys 0.40.0` and `aws-lc-sys 0.46.0`:

- `aws-lc-rs 1.18.2` → `aws-lc-sys 0.46.0`
- The workspace `aws-lc-sys = "0.40.0"` (`Cargo.toml:195`) → used directly by `deno_crypto_provider`, `ext/node_crypto` and `libs/crypto`

What this means:

- **Binary size and build time:** two full copies of libcrypto get compiled and linked into `deno`. The symbols are prefixed per version, so this links fine, but it's a measurable size increase. It would be worth comparing the release binary size before and after.
- **Two separate crypto states:** `rustls`/`aws-lc-rs` run on 0.46 while `node:crypto` raw FFI (`EVP_*`, `AES_*`, `EVP_PBE_scrypt`, the `PKey`/`Bio` wrappers in `libs/crypto/ffi.rs`) runs on 0.40. Each copy has its own RNG, its own error queue, its own FIPS state, and so on. Nothing today passes raw pointers between the two (`aws-lc-rs` doesn't expose them), so I don't see a memory-safety bug now. But it's a trap: if anyone later passes an `EVP_PKEY*` from one side to the other, it will compile and then corrupt memory.
- **Windows NASM:** the workspace turns on `features = ["prebuilt-nasm"]` only for 0.40. The new 0.46 build doesn't get that feature, so Windows x86_64 builds might need a system NASM unless 0.46 handles this differently. CI passed, so this is probably fine, but please confirm it was a deliberate choice.

**Suggestion:** bump the workspace `aws-lc-sys` to `0.46.0` (keeping `prebuilt-nasm`) so there's only one copy, or explain in the PR why that wasn't done. That probably means rechecking the raw FFI calls in `ext/node_crypto` and `libs/crypto` against the newer bindings, which may be enough for a follow-up PR. Either way, it should be tracked.

### 2. Leftover `unstable` feature on `aws-lc-rs` (low)

`ext/crypto/Cargo.toml:21` still has `aws-lc-rs = { workspace = true, features = ["unstable"] }`. After this PR nothing in `ext/`, `libs/` or `cli/` imports `aws_lc_rs::unstable::`. If ML-DSA was the only reason for the feature, drop it so nobody can quietly start using unstable APIs again.

### 3. Changing `to_pkcs8()` to `to_pkcs8v1()` isn't covered by a test (low to medium)

The doc comment at `ext/crypto/mldsa.rs:313-319` says export produces the seed-only form (`[0] OCTET STRING seed`). In 1.18, `to_pkcs8()` apparently changed what it produces, which is why the PR switches to `to_pkcs8v1()`. The only test is a round trip in `tests/unit/webcrypto_mldsa_test.ts:176` (export pkcs8 → import → sign/verify). That test would still pass if the export format changed, because `from_pkcs8_native` accepts more than one encoding.

The exported PKCS#8 bytes are an interoperability format other tools consume. Please add a check that pins it, for example:
- assert the exported length for each variant (the seed-only form is a fixed size), or
- assert the exported bytes match a known vector for a fixed seed.

That would catch the next silent change in `aws-lc-rs`.

### 4. No test for the actual security change (low)

There's no test showing that a chain through the distrusted eMudhra keys is now rejected, or that `emSign ECC Root CA - G3` is gone from `TLS_SERVER_ROOTS` / `TLS_SERVER_ROOT_CERTS`. The upstream crates own and test this behaviour, so leaving it out is reasonable. Still, a small Rust unit test in `ext/tls` that checks the root is absent from the bundled roots would protect against an accidental downgrade, such as a future lockfile refresh that picks an older `webpki-roots` 0.26.x without the wrapper.

## Smaller notes

- **Version pins:** `rustls-webpki = "0.103.16"` and `webpki-roots = "1.0.10"` act as minimum versions, which is what a security fix needs. Since `rustls` itself is pinned with `=` here, consider whether `rustls-webpki` should be pinned the same way to make it harder to resolve to a version without the fix. The lockfile covers normal builds, so this is optional.
- **`deno_node` root store:** the `webpki-root-certs` 0.26 → 1.0 jump is a major-version API bump. Its uses in `ext/node/ops/tls.rs:122,194,214` (`TLS_SERVER_ROOT_CERTS`) still compile, and behaviour should only differ by the removed root. That's worth one line in the PR description, since it changes what `tls.rootCertificates` returns in Node compatibility mode.
- **`pkg-config` bump:** 0.3.30 → 0.3.34 comes in through `aws-lc-sys 0.46`. It's harmless.
- **Scope:** the PR covers a TLS trust fix, an AWS-LC upgrade with an API migration, and a `deno_graph` bump. CLAUDE.md asks for minimal changes, but these all seem to be forced by the dependency graph (the fixed `rustls-webpki` needs the newer AWS-LC). The PR description explains that well.

## Verdict

The security direction is correct and the change is ready in substance. Before or soon after merging, I'd ask for:

1. A fix or explanation for the duplicate `aws-lc-sys` (0.40 and 0.46).
2. A test that pins the ML-DSA PKCS#8 export format, given the switch to `to_pkcs8v1()`.

The other points are optional cleanup.

# REVIEW B

The PR is already merged, so this review is retrospective. Overall it's a sound, well-scoped security fix. It updates two things: the TLS verifier (`rustls-webpki`), so certificates signed with the compromised eMudhra keys are rejected, and the two bundled Mozilla root lists (`webpki-roots`, `webpki-root-certs`). The PR description explains the dependency chain and links the upstream fixes.

## Summary of changes
- `rustls-webpki` 0.103.13 → 0.103.16. This version rejects any chain containing the eight compromised keys, including cross-signed certificates.
- `webpki-roots` 0.26 → 1.0.10 and `webpki-root-certs` 0.26.5 → 1.0.10. Both drop `emSign ECC Root CA - G3`. reqwest and hyper-rustls still pull in `webpki-roots` 0.26, so that is now 0.26.11, which just wraps 1.0.10.
- `aws-lc-rs` 1.16.3 → 1.18.2, with ML-DSA moved from the `unstable::signature` module to the stable `signature` module.
- `deno_graph` 0.111.0 → 0.111.1, so its copy of the TLS dependencies is fixed too.

## Strengths
- **Raising the minimum to `rustls-webpki = "0.103.16"`** in `Cargo.toml` is the right call. `"0.103"` would have let a fresh resolution, or a downstream embedder, end up on a vulnerable version.
- **Fixing the transitive `webpki-roots` 0.26.x** is easy to miss. Without it, reqwest/hyper-rustls (used by tooling such as upgrade/fetch-like HTTP clients) would still trust the removed root.
- **Bumping `deno_graph`** closes the same gap in a dependency outside this repo.
- **Using `to_pkcs8v1()` in `ext/crypto/mldsa.rs:327`** keeps the export format unchanged. The deprecated `to_pkcs8()` may later default to v2 (which includes the public key), and that would quietly change `exportKey("pkcs8")` output and could break existing round-trip tests or interop.

## Concerns and suggestions

### 1. Two copies of AWS-LC are now linked (performance, build, and audit cost)
`Cargo.lock` now has both `aws-lc-sys 0.40.0` and `aws-lc-sys 0.46.0`:
- `aws-lc-rs` 1.18.2 uses 0.46.0.
- `deno_crypto`, `deno_crypto_provider` and `libs/crypto` still use the workspace pin `aws-lc-sys = "0.40.0"` and call raw FFI directly, e.g. `ext/node_crypto/cipher.rs` and `libs/crypto/ffi.rs`.

What this means:
- **Binary size and build time:** AWS-LC is a large C library and its cmake build is slow. It is now compiled and linked twice, on every platform, including the release binary and `denort`.
- **Symbol conflicts:** I expect none, because aws-lc-sys prefixes its symbols by version. Still, it's worth confirming on all release targets (especially Windows MSVC and musl, if built), since CI passing on the PR may not cover every release job.
- **Separate global state:** each copy has its own RNG, CPU feature detection and error queue. That's fine as long as nothing passes raw pointers between the two. I didn't find any such crossing, but the risk is easy to introduce later without noticing.
- **Security patching:** AWS-LC fixes now have to be applied to two versions.
- **`prebuilt-nasm`:** the workspace sets `features = ["prebuilt-nasm"]` only on the 0.40.0 dependency. The 0.46.0 copy pulled in by `aws-lc-rs` doesn't get it. Please check that Windows release builds (and contributors' Windows machines) don't now need NASM installed, or that 0.46 falls back automatically.

**Suggestion:** as a follow-up, bump the workspace `aws-lc-sys` to `0.46` so there's a single copy. If that's out of scope for an urgent security fix, open a tracking issue.

### 2. `deno_tls` publicly re-exports `webpki_roots`, which affects embedders
`ext/tls/lib.rs:30` has `pub use webpki_roots;`. Going from 0.26 to 1.0 changes the type of that re-exported crate. That is a semver-relevant change to the published `deno_tls` crate (and to `deno_runtime::deno_tls::webpki_roots`, used in `cli/lib/args.rs:22`). It's probably fine since these crates aren't 1.0, but the release notes or crate version bump should mention it.

### 3. Test coverage
No tests were added. Testing a key compromise end to end is hard, but a cheap regression guard would help:
- A small Rust unit test in `ext/tls` that asserts no entry in `webpki_roots::TLS_SERVER_ROOTS` has the `emSign ECC Root CA - G3` subject.
- A node-compat assertion that `tls.rootCertificates` (backed by `webpki_root_certs` in `ext/node/ops/tls.rs:122`) doesn't contain it.

Either would catch a future lockfile downgrade or a revert by mistake. For the ML-DSA change, check that an existing test pins the exact PKCS#8 bytes, not just a round-trip. A round-trip test would still pass if the v1→v2 format change that `to_pkcs8v1()` avoids ever happened.

### 4. Scope and process
- Updating AWS-LC and moving ML-DSA to the stable API are only needed to satisfy the new `rustls-webpki`, and the description justifies them. It's still worth noting in the changelog that ML-DSA now runs on a newer AWS-LC.
- The `pkg-config` bump 0.3.30 → 0.3.34 is a transitive requirement of `aws-lc-sys` 0.46. That's fine.
- The description says Codex helped prepare the PR. The lockfile changes look consistent with the manifest changes, and I saw no unexplained version jumps.

## Security assessment
- The fix covers both places Deno checks certificates: the rustls verifier used by `fetch` and `Deno.connectTls`, and the cert list behind `node:tls`.
- The only remaining exposure is the system or native trust store (`DENO_TLS_CA_STORE=system`, via `deno_native_certs`). There, the root-list change has no effect, but the new `rustls-webpki` still rejects the compromised keys during chain building. It would help to mention this in the release notes: users of the system store are protected by the verifier, not by the root removal.

## Verdict
**I'd approve it.** It's the right fix and well scoped for an urgent security update. The main follow-up is merging the two `aws-lc-sys` versions into one, plus a small regression test for the removed root.
