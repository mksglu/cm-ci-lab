# REVIEW A

## Review of PR #100935: store `ChunkGroupInfo::chunk_groups` as a `Vec`

This PR is already merged and was approved by mischnic and sokra. I reviewed the diff only and did not build it or run the tests.

### Summary
`ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. The motivation is correct. `IndexSet`'s `PartialEq` ignores order, so the `#[turbo_tasks::value]` cell treats a renumbered recomputation as unchanged. In that case the old order is kept, while `module_chunk_groups` bitsets and `chunk_group_indices` use the new numbering. Modules then resolve to the wrong chunk groups. A `Vec` makes the equality check order-sensitive, so this is the right fix.

### Code quality
- The doc comment on the field explains why it must be a `Vec`. This matters because someone could otherwise "tidy" it back into an `IndexSet`.
- The `get_index(i)` to `get(i)` call-site updates in `module_batches.rs` and the test helper are mechanical and correct.
- The `#[bincode(with = "turbo_bincode::indexset")]` attribute is removed, which is right because `Vec` has native bincode support.
- **Cache compatibility:** the persisted encoding changes from the indexset encoding to the `Vec` encoding. That is presumably covered by the usual turbo-tasks cache versioning or invalidation. I couldn't confirm it from the diff. Check that the backing-storage version is bumped if that isn't automatic.

### Potential issues and follow-ups
- **`chunk_group_keys` is still an `IndexSet`.** It is marked `unsafe_ignore` and is index-aligned with `chunk_groups`. If it is excluded from equality, it can go stale in the same way if only its order changes. It is safe only if `chunk_groups` equality always implies the same key order. The key-to-group relationship looks 1:1, so that probably holds. A short comment saying so would help.
- **Duplicates:** the `IndexSet` deduplicated implicitly. Confirm that the construction path still can't push the same `ChunkGroup` twice, and that nothing relied on `insert` returning the existing index. The diff doesn't show the construction site, so I assume it dedupes via `chunk_group_keys` or a map.
- **Lookups:** if any code path uses `get_index_of(&group)` or `contains` on `chunk_groups`, it would now be O(n). The diff shows none, and the other call sites index by position.
- The author notes that other `IndexSet`-style fields may have the same problem. A follow-up audit of `ModuleToChunkGroups` and similar cell types would be worthwhile.

### Performance
There is no meaningful regression. Indexing a `Vec` is cheaper than an `IndexSet`, and the hash table is no longer built or serialized.

### Security
No concerns. This is internal bundler data structure code with no request-header or input handling.

### Test coverage
- `test_chunk_group_info_reordered_entries` is a good integration-style regression test. It uses an invalidatable `State`, flips the entry order, and asserts that the module-to-chunk-group mapping stays correct after recomputation. This is exactly the failure mode described.
- It matches the repo guidance to prefer behavior tests over implementation-mirroring ones.
- The test reads `page1`/`lazy1` mappings only. Asserting `page2`/`lazy2` as well would catch cross-wiring in the other direction. This is minor.
- The test builds `lazy2` through the graph but never binds it to a variable. That is fine, and `page2` is bound.
- I didn't verify that the test fails without the fix. The parent commit (`test ChunkGroupInfo after reordering graph entries`) suggests the author did.

### Verdict
This is a correct, minimal fix with a solid regression test. My only requests are to double-check the cache-version implication and to document why `chunk_group_keys` can stay an `IndexSet`.

- The `get_index(i)` to `get(i)` changes in `module_batches.rs` and the test helper are mechanical and correct.

### Potential issues
- **`chunk_group_keys` has the same risk.** It is still an `FxIndexSet<ChunkGroupKey>` with `#[turbo_tasks(unsafe_ignore)]`. Each index in `chunk_group_keys` should match `chunk_groups`, so it's worth confirming that a reordering can't leave it stale. The PR description says other places are still being checked.
- **Other order-sensitive containers.** `chunk_group_indices` is a keyed cell mapping key to index, so it should change when the numbering changes. The `ChunkingHeuristicsInfo` fields are positional too (see the comment at line 66), and they are `Vec`s, so they should be fine.

### Performance
- Nothing notable. `Vec` indexing is as cheap as `IndexSet::get_index`. The set's hash table is no longer built or serialized. Since `chunk_group_keys` still holds the keys, nothing in this PR looks up a chunk group by value.

### Security

### Test coverage
- `test_chunk_group_info_reordered_entries` is a good regression test. It builds the same entry set in two orders, and the order flip comes from a `State` toggle, so the recomputation goes through the real cell-update path.
