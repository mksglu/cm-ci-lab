# Review: PR #345283 — run the `--runList` unit tests in parallel workers

## Summary
All three unit test runners (Electron, node.js, browser) ignored `--workers` when given a `--runList`, so the tests ripple selects on macOS and Windows PR CI always ran in one process. This PR lets `--workers` apply to `--runList`. A new helper, `getWorkerCountForFiles`, picks how many workers to start: one per 75 files, at least 2, and never more than `--workers` or the number of files. The "Running the N test files…" message now prints once, from the process that starts the workers. The PR description is unusually thorough, with measurements, how to test it, and a validation matrix.

## What's good
- **The worker-count rule is sound and explained.** `Math.max(1, Math.min(count, fileCount, Math.max(2, floor(fileCount / 75))))` matches the documented behaviour: 1 file gives 1 worker, 2–224 files give 2, and 300 or more give 4. The reason for "at least 2" (one slow file shouldn't hold up the rest) is backed by data.
- **The Electron main process finds the listed files once.** `findTestFiles` moves into `test/unit/electron/testFiles.ts`. When only one worker is needed, the main process passes the files it found to the window as `run: files`, so the window doesn't search again and the list message isn't printed twice. Reruns still build their arguments from `args` (`index.js:816`), so they are unaffected.
- **The Electron startup error can't go unhandled.** `listedTestFiles?.catch(() => {})` stops an early rejection from becoming an unhandled rejection. The real error is still reported where the promise is awaited in `app.on('ready')`. Because `readFileSync` runs inside the async function, a missing list file also ends up as a rejection there.
- **The node.js runner finds its files only once.** `findTestModules` caches the file search, so when the count falls back to 1, `main()` reuses the result instead of searching again or printing the message twice.
- **Workers don't re-apply `--workers`.** Each worker is started without `--workers`, so it can't start workers of its own. Each runner suppresses the duplicate message in its workers (`!worker`, `!opts.workerDir`, `!args.worker`).

## Potential issues / suggestions

1. **`getWorkerCountForFiles` both computes and logs** (`test/unit/parallel.ts`). A pure function would be easier to test, and the log line could move to the call sites (or into a small wrapper). It would also stop the message appearing in edge cases, such as `Using 1 instead of 4 worker processes for 0 test files` in the Electron runner.

2. **The Electron runner doesn't stop early on an empty list, unlike the other two.** The node.js and browser runners exit with 0 when no listed file applies to them. The Electron path sets `firstRunArgs = { ...args, run: [] }`, and because `[]` is truthy the renderer takes the `opts.run` branch and loads nothing. That matches the old behaviour, so it isn't a regression. But now that the main process already knows `files.length === 0`, it could skip opening a window, which would save a few seconds when ripple selects no Electron tests.

3. **The new helpers have no tests.** No test file covers `parallel.ts`, and nothing tests `getWorkerCountForFiles` or `findTestFiles`. The worker-count function is small, pure (apart from the log) and full of edge cases (0, 1, 2, 74, 75, 224, 225, 300, and a `count` below 2), so it is a cheap candidate for a few table-driven tests. The PR also says CI never exercises the `--runList` worker path, because touching `test/unit/**` makes ripple run every test. Unit tests would partly make up for that.

4. **`workersApply` means slightly different things in each runner.**
   - Electron and node.js: `workerCount > 1 && …`
   - Browser: `args.workers !== undefined && …`, with no `workerCount > 1` check

   This difference predates the PR, and the browser version is deliberate (with `--workers`, browsers run one at a time even when only one worker is left). Still, the same name for different meanings is a small trap for later edits; a comment or a more specific name in the browser runner would help.

5. **The 75 files per worker was tuned on one machine.** The constant comes from an 18-core M5 Pro, while the CI runners have 5 cores (macOS) and 8 (Windows), and the PR says the per-worker cost there hasn't been measured yet. Since every worker loads all listed files, worker startup may matter more on slower runners. Consider checking CI timings after merge and keeping the constant easy to adjust.

6. **The docs list different exclusions in different places.** The `--workers` paragraph in `SKILL.md` says it is ignored with `--run, --runGlob, bare file paths, --grep, --coverage or --dev`. The Electron help and `README.md` also list `--testSplit` and `--waitServer`. It's minor, but the skill file is what agents read, so it's worth keeping in sync.

7. **Nit: the Electron runner works out the output folder in two places.** `index.js` computes `out-build` vs `out` itself in the call to `findTestFiles`, while the renderer uses `initLoadFn`. If the rules for choosing the output folder change, the main process could search a different folder from the one the renderer loads from. A small shared helper in `testFiles.ts` (for example `getOutDir(build)`) would keep them aligned.

## Performance
Overall a clear gain for medium and long lists: 300 files go from about 27 s to 16.5 s in Electron, 37 s to 20.5 s in WebKit, and 61 s to 43 s in node.js. The cost is a small slowdown on short lists of quick tests (Electron with 10 files: 2.8 s to 5.9 s, although those 10-file timings were taken on a busy machine). The PR accepts that cost on purpose, as protection against a single slow file.

## Security
No concerns. The changes only affect local and CI test running. The list file was already read in every runner; the only new reader is the Electron main process.

## Test coverage
The validation is manual but extensive: 363 of 364 local runs passed, and reruns, `.only`, `--tfs` and running several browsers were each checked. The gap is the one in point 3: no automated tests for the new helpers, and CI on this PR doesn't exercise the `--runList` worker path.

**Verdict:** a good, well-explained change. The suggestions above are about robustness and maintainability, not correctness.

That is intended and documented, but the different meaning of the same variable name could confuse later edits. 6. **Short lists get slower.** The PR's own numbers show 10-file runs getting slower with 2 workers: Electron 2.8 s → 5.9 s, node 4.2 s → 5.5 s, WebKit 11.0 s → 11.9 s. The "at least 2" floor is justified by the slow-file tail, and the 10-file data is admittedly noisy. Still, ripple selections are often small, so most CI runs may sit in this band. It would be worth watching CI durations after merging (macOS has 5 cores, Windows 8, and neither was measured) and adjusting the floor or the 75 constant with real data. Making the constant overridable through an environment variable could make that tuning cheaper.

## Performance
- In Electron, the main process now globs the output folder once while the app starts, in parallel with startup. It then passes the result to a single window instead of letting it glob again. That's a net win.
- In node, the parent globs once before deciding how many workers to start, and each worker globs again. This is a small cost next to loading the modules.

## Security
No concerns. The changes are limited to local test tooling, read files the user passed in, and spawn the same executable with arguments built from the existing `argv`.
