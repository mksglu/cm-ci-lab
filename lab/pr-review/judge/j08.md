# REVIEW A

**Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`** (already merged)

**Summary:** The fix is correct and minimal. `object_name[..1]` slices by byte, so it panics when the first character is multi-byte. Reading the first character with `.chars().next()` is safe and matches the TS regex `^[a-zA-Z$_].*Ref$`-style check. Non-ASCII leading characters now return `false`.

**Code quality**
- The change is a one-line swap that preserves the existing logic, which is what you want here.
- A small cleanup is possible. The `.chars().next().is_some_and(...)` chain now sits right after `len() > 3` and `ends_with("Ref")`. It would read slightly better as `object_name.chars().next().is_some_and(...)` on one line, but `cargo fmt` accepted the current layout, so this is cosmetic.
- `object_name.len() > 3` counts bytes, not characters. This is harmless. It is a loose length guard that matches the TS behavior, and `ends_with("Ref")` plus the first-char check do the real work. A name like `가Ref` is 6 bytes, so it passes the length check. It is then rejected by the first-char test, which is the intended outcome.

**Potential bugs**
- I found no remaining problems in this function.
- Worth a quick audit: other byte-slicing patterns elsewhere in the Rust port (`[..1]`, `[1..]`, `&s[..n]` on identifier names) could have the same panic. A `grep` over `compiler/crates` would be cheap insurance. Nothing in this PR indicates whether that was done.

**Performance:** No concern. `chars().next()` is O(1).

**Security:** No concern. The old behavior was a panic (a compiler crash) on attacker- or user-controlled identifier names. That is a robustness issue rather than a memory-safety one, and this PR fixes it.

**Test coverage**

- The expected output shows the name is not treated as a ref, so it is memoized into the cache. This matches the TS behavior, and the author reports both `yarn snap` and `yarn snap --rust` pass.

- The fixture name `repro-ref-like-name-non-ascii` follows the existing `repro-*` convention.

**Verdict:** Approve. It is a correct, well-scoped fix with a regression fixture. The optional follow-ups are a grep for similar byte-slicing and a small unit test.

# REVIEW B

**Review of PR #38025: Fix non-ASCII panic in `is_ref_like_name`**

**Verdict:** Approve. The PR is already merged, and I found nothing blocking.

**The fix**
- `object_name[..1]` slices one byte. If the name starts with a multi-byte character such as `한`, that cuts through a UTF-8 boundary and panics. The panic is real.
- Replacing the slice with `object_name.chars().next()` removes it. The `.chars().next().is_some_and(...)` chain was already there, so the change is minimal and idiomatic.
- Names that start with a non-ASCII character now return `false`. The TS regex presumably behaves the same way, since it uses an ASCII-only first-character class like `/^(?:[a-zA-Z$_][a-zA-Z$_0-9]*)Ref$/`. The PR description says as much, but I didn't check the TS source.

**Potential issues**
- `object_name.len() > 3` counts bytes, not characters. The TS check is `.length`-based or regex-based, so this differs only for names whose first character is non-ASCII. Those return `false` either way, so behavior matches. A name like `aé…Ref` is handled by `ends_with("Ref")`, which is UTF-8-safe.
- Other places in the Rust port may use similar byte slicing, such as `[..1]` or `[0..n]` on strings derived from user identifiers. Non-ASCII identifiers are valid JS, so this class of bug could recur. I'd grep `compiler/crates` for `[..` and `[0..` on `&str` values. For example, `rg '\[\.\.\d\]|\[0\.\.\d\]' compiler/crates`. Nobody needs to do this before merge.

**Test coverage**
- The fixture `repro-ref-like-name-non-ascii.js` reproduces the panic, and the expected output is sensible. The name stays a plain local and is not treated as a ref. `.current` access inside the closure compiles cleanly.
- The PR also reports that the TS (`yarn snap`) and Rust (`yarn snap --rust`) suites pass, and `cargo fmt --check` is clean.
- Optional improvement: add a Rust unit test for `is_ref_like_name` covering `한글Ref`, `ref`, `fooRef`, `$Ref` and `_Ref`. It would catch regressions without a full fixture run. The fixture is enough for now.
- Another optional improvement: add a case with a non-ASCII name that does not end in `Ref`, and one with an ASCII-prefixed non-ASCII name such as `aé`.

**Performance and security**
- No performance impact. The change replaces a slice with a char iterator.
- It also removes a way to crash the compiler on valid user input. That's a small robustness and availability gain, with no new security surface.

**Style**
- The change follows the repo conventions. The commit title uses the `[rust-compiler]` prefix, and the description is clear and links the issue.
