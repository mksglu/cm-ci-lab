# REVIEW A

**Review of PR 23017: Preserve inline comments when updating an existing dependency group**

The PR is already merged. I read the diff but didn't build it or run the tests.

**What it does:** `PyProjectTomlMut::add_dependency_to_group` now sorts and reformats the inline `dependency-groups` table only when it inserts a new group. Editing an existing group's array leaves the surrounding key comments alone. The second function, which ensures a group exists, now returns early when the group is already there. That removes the nested `if !group_exists` and gives both functions the same shape.

**Code quality**
- The logic is correct. `fmt()` and `sort_values()` are the calls that rewrite whitespace and comments, and they now run only when the table layout changes.
- The early `return Ok(())` in the ensure-group function is cleaner than the old version. The `new_group` flag in the other function is clear.
- The new comment ("Formatting after an array edit would clear the comments...") explains the rationale without referring to history. It's also good that the old comment, which said comments between inline-table items can't exist, was removed, because the PR's own example shows they can.
- The two functions still each carry their own copy of the "insert, sort if it was sorted, format if inline" sequence. A small shared helper would stop them drifting apart. This is optional.

**Potential issues**
- **Reformatting on insert:** inserting a new group into an inline table still calls `fmt()`, so comments on neighbouring keys are still lost in that case. That matches the PR's stated scope, but the PR doesn't say so and no test covers it. A note or a test would help.
- **Output formatting:** the snapshot shows an ugly result:
  ```
  dev = [
  "ok==1.0.0",
  ], # Local development
  ```
  The array is multi-line with no indentation. The comments survive, which is the goal, but the array's own formatting is poor. The snapshot locks in that layout, and a later formatting improvement will need to update it. A follow-up could make the array render as `dev = ["ok==1.0.0"], # ...` or indent it properly.
- `sort_values()` runs on the new-group path only. Previously it also ran when an existing group was edited, but sorting then was a no-op because no keys changed, so behaviour is unchanged.

**Performance and security:** no concerns. The change only removes work.

**Test coverage and conventions**
- The new test follows the neighbouring tests: `uv_snapshot!`, `assert_snapshot!` and `context.read`.
- It covers the `uv add --dev` path on an existing group.
- The second changed function, the ensure-group path, has no test. That path is the one used for `uv add --group` when the group exists in an inline table and for similar commands. Early-returning there is the behaviour change, so one more test would help. For example, run a command that ensures an existing group and assert the file is untouched.
- There is no test for adding a new group to an inline table with comments. It would document the remaining limitation.
- The test sits between unrelated tests (just before `add_group_comment`). That's fine, but placing it next to the other dependency-group tests would group related cases.
- `--frozen` with `ok==1.0.0` avoids needing a lockfile, which keeps the test fast. No `test-...` feature gate looks necessary, since it doesn't touch the network.

**Verdict:** a sound, narrowly scoped fix. I'd suggest follow-ups for a test of the ensure-group path and for the awkward array formatting.

**Review of PR #23017: Preserve inline comments when updating an existing dependency group** (already merged)

**Summary:** The change is correct and narrowly scoped. It runs `sort_values()` and `fmt()` on an inline `dependency-groups` table only when a key is actually inserted. Appending to an existing group's array no longer wipes the comments on neighboring keys.

**Code quality**
- The `new_group` flag in `add_dependency_group` is clear. The comment explains the rationale rather than the history.
- The second function (the group-ensure path) now returns early when the group exists. That is cleaner than the old `group_exists` flag, and the behavior is the same: nothing changes when the group exists, and the `fmt()` call was the only thing that ran in that case.
- This change removes the old comment saying reformatting "can drop comments between keys". That comment was wrong for inline tables, so removing it is fine.
- Minor: `if new_group { ... if let Some(..) = ... }` could be flattened with a let chain, as AGENTS.md prefers. The `if let` is nested inside `if new_group`, so `if new_group && let Some(..)` would not work directly, because `sort_values` sits between them. This is nitpicking.

**Potential issues**
- The inserting path still calls `fmt()`, so adding a new group to an inline table still drops comments on the existing keys. That is outside the PR's scope, but it is worth a follow-up or a documented limitation.
- The snapshot shows the edited array formatted oddly:
  ```
  dev = [
      "ok==1.0.0",
  ], # Local development
  ```
  The element is indented at the same level as the key, and the closing bracket is at the key's level. This is a side effect of not calling `fmt()`. It is valid TOML and the comments survive, but the indentation is ugly. Pinning it in a snapshot makes it look intentional. Consider a follow-up that formats only the edited array, for example with a decor-aware multiline reformat.
- Because the test passes `--frozen`, it only exercises the edit path. That is fine for this change.

**Test coverage**
- The new test `add_dev_preserves_inline_group_comments` is in the right module. It uses `uv_snapshot!` and `assert_snapshot!` like nearby tests and has no loops.
- It covers adding to an existing group, which is the regression. It does not cover the ensure-group path's early return (an existing group with no dependency added). Check whether an existing test covers that path, for example for `uv add --group` with a source. If none does, a small test would be worthwhile.
- It also does not cover the unchanged behavior that inserting a new group still sorts and formats. Existing tests probably cover this, but I did not check.
- The test is probably unaffected by feature gates, since it needs no network, but I did not verify that.

**Performance and security:** No concerns.

**Verdict:** Good, minimal fix. The main suggestion is a follow-up to improve the indentation of the reformatted array.
