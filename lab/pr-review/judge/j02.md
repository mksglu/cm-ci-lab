# Review: PR #36944 — fix(ext/node): support assert message functions and format arguments

## Summary

The PR puts all message handling for comparison and `ok` assertions into one `innerFail()` in `internal/assert/utils.ts`. It accepts message tuples: `[]`, `[string, ...args]`, `[Error]` and `[fn]`. It also turns on `parallel/test-assert.js`. Moving the handling into one place is a good change, and the tuple design matches Node. There is one likely regression for callers that pass `undefined` or `null` as the message, and the PR leaves commented-out code in place.

I couldn't run a debug build or Node in this environment, so the behaviour described below comes from reading the code, not from running it.

## Potential bugs

### 1. An explicit `undefined` or `null` message now throws `ERR_INVALID_ARG_TYPE` (high)
`equal`, `strictEqual`, `deepStrictEqual` and the other comparison functions now take `...message`. So `assert.strictEqual(1, 2, undefined)` produces `message = [undefined]`. In `innerFail` (`ext/node/polyfills/internal/assert/utils.ts:128`), `[undefined]` is not empty, not a string, not an Error and not a function. It falls into the last branch:

```ts
} else {
  throw new ERR_INVALID_ARG_TYPE("message", ["string", "function"], message[0]);
}
```

Code that forwards an optional message is very common, for example:

```js
function check(a, b, msg) { assert.strictEqual(a, b, msg); }
```

Before this PR, these calls failed with an `AssertionError` that used the default diff message. Now they throw a `TypeError` with a different error code, and the useful diff output is lost. `null` hits the same branch.

`innerOk` already handles this with `args[1] == null`, but the comparison functions don't get that protection. Before merging, it's worth checking upstream Node 26's `innerFail` for how it treats `undefined`. I'd expect it to treat `[undefined]` like `[]`, since anything else would break a lot of existing code. A simple fix:

```ts
if (message.length === 0 || message[0] === undefined) { resolved = undefined; }
```

Please also add a regression test (`assert.strictEqual(1, 2, undefined)` should throw an `AssertionError`).

### 2. Edge cases in `internalMatch` (`ext/node/polyfills/assert.ts:768-772`)
- `generatedMessage = message.length === 0` sets it to `false` for `assert.match(s, re, undefined)` and `assert.match(s, re, "")`. Yet `message[0] ||= ...` then fills in the default message, so `generatedMessage` is wrong. The old code used `!message` and returned `true`.
- `message[0] ||= ...` replaces any falsy first element. So `[0]` and `[false]` silently get the default message, while every other assertion now throws `ERR_INVALID_ARG_TYPE` for them. That's inconsistent.
- `match(s, re, undefined, "x")` becomes `[default, "x"]` and runs through `format()`, which appends `"x"` to the default message.
- The function writes into the array that came from the caller's rest parameters. That's harmless today, but fragile.

A cleaner approach: work out `generatedMessage` from whether `message[0]` is a usable value, and build a new tuple instead of mutating this one.

### 3. `generatedMessage` when a message function throws or returns a non-string (low)
`innerOk` passes `generatedMessage: false` for any user message. If the message is a function that throws or returns a non-string, `innerFail` falls back to the default message but still sets `error.generatedMessage = false`. It's worth checking whether Node reports `true` in this case.

## Code quality

- **Remove the commented-out code.** `internalMatch` has seven leftover lines like `// if (ObjectPrototypeIsPrototypeOf(ErrorPrototype, message)) {`, `// const generatedMessage = !message;`, `// const err = new AssertionError({` and `// err.generatedMessage = generatedMessage;`. They add noise and shouldn't have been merged.
- **Formatting churn.** The `getErrorSourceExpression` import was split onto several lines for no reason. Per CLAUDE.md, keep changes minimal.
- **Inconsistent handling remains.** `expectedException`, `fail` and `ifError` still build `AssertionError` directly and handle `Error` messages themselves. That's acceptable for this PR's scope, but `throws`/`rejects` with a custom message now behave differently from the comparison functions (no function or printf support). A short note or TODO pointing to #35293 would help.
- The `as MessageTuple` cast in `innerOk` hides exactly the case from issue 1. A runtime guard would be better than relying on the cast.

## Performance

- Rest parameters (`...message`) allocate an array on every assertion call, including ones that pass. Node does the same, so this is acceptable, but it's a small cost on hot test loops.
- `format(...new SafeArrayIterator(message))` only runs on failure, so it's fine.

## Security

No concerns. User-supplied message functions run only on failure, inside a `try/catch`, and only receive values the caller already has.

## Test coverage

- The only test change is enabling `parallel/test-assert.js` in `tests/node_compat/config.jsonc`. That covers the upstream behaviour, but nothing protects Deno-specific regressions. I'd add a small unit test in `tests/unit_node/assert_test.ts` covering:
  - an explicit `undefined` or `null` message on `strictEqual`/`deepStrictEqual`/`match` (issue 1),
  - the `generatedMessage` value for `match` with `undefined` or `""`,
  - a printf-style message with `match`/`doesNotMatch`,
