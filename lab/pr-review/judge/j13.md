# REVIEW A

## Review of #41512: escape node metadata in Mermaid labels

The PR is already merged. The fix is sound and the diff is small and focused. Below are a few non-blocking points.

### What works
- **Escaping order.** `#` is escaped first, so the entity codes added afterward (`#91;` and so on) aren't double-escaped. `#quot;` is a valid Mermaid entity.
- **Stable output.** Sorting sets keeps the output stable between runs. Items are converted to `str` before sorting, so sets of mixed types won't raise `TypeError`.
- **Full label escaping.** Escaping `f"{key} = {formatted}"` covers keys as well as values.
- **Typing and style.** The helpers have type hints and the code follows the repo conventions.

### Issues and suggestions
1. **Silent data loss for dicts and nested values.** Dropping them is a defensible way to fix the parse failure. It still changes what users see. Before, they got an ugly or broken label, and now the information just disappears. A cheap alternative is a compact placeholder or `json.dumps` of the value, which the escaper would then make safe. At minimum, document the omission in the `draw_mermaid` docstring.
2. **Newlines in string values.** `\n` and `\r` inside a value or key aren't escaped. Labels are already joined with `"\n"`, so an embedded newline can still produce an invalid or odd label. Consider replacing them with `<br/>` or a space.
3. **Other Mermaid-significant characters.** `&` and `;` aren't escaped. Backticks and `*`/`_` are only handled elsewhere, for node names, via `MARKDOWN_SPECIAL_CHARS`. Metadata values can still trigger markdown-string parsing if Mermaid treats the label that way.
4. **Empty collections.** `[]` renders as `key = ` with a trailing empty value. Skipping the line, or showing `key = (empty)`, would read better.
5. **Minor cleanup.** `bool` is a subclass of `int`, so listing it in `scalar_types` is redundant but harmless. `scalar_types` is also rebuilt on every call, so it could be a module constant.
6. **Public-API note.** The functions are private and the signatures are unchanged. The output format did change for any previously valid list or dict metadata. The release note covers this, but it could say that dicts are now omitted.

### Test coverage
Coverage is good for the main cases: list, sorted set, dict omission, string escaping, and the all-omitted case. Gaps:
- There is no test for tuples, bools or numbers, empty collections, or a list containing a dict, which should be omitted entirely.
- There is no test for newline handling.
- The test asserts on exact substrings, which is fine. A round-trip check against a real Mermaid parser, for example through `draw_mermaid_png` in an integration test, would show the output actually renders.
- The `tags = a, b, c` assertion confirms sorting only for string items. A set of ints such as `{10, 9}` sorts as strings (`"10" < "9"`). That is deterministic but possibly surprising.

### Security and performance
There are no concerns beyond the escaping above. The escaping reduces the chance of label or markup injection through metadata, and the cost is negligible.

**Verdict:** a good fix. I'd follow up on newline escaping and the empty-collection case, and add the few extra tests.

# REVIEW B

## Review of PR #41512: escape node metadata in Mermaid labels

This PR is already merged, so these notes are for follow-up. The fix is sound. Escaping `#` first and then the other characters is the right order, and the output is deterministic. Escaping also stops a `{`/`}` in a label from breaking the later `.format(...)` call.

### Potential issues

1. **`None` metadata values are now dropped.** `_format_metadata_value` accepts only `str, int, float, bool`. Before this PR, `{"x": None}` rendered as `x = None`, and now it is omitted with no mention in the PR description. The same applies to a list containing `None`, such as `[None, "a"]`, which is dropped entirely. Either add `type(None)` to the scalar types or state the omission as intentional. Keeping `None` seems more useful.

2. **Newlines inside values are not handled.** Entries are joined with `"\n"`, so a string value containing `\n` or `\r` adds lines the code never meant to emit. Mermaid may handle that badly inside a quoted label. Consider replacing newlines with a space, or with `<br/>`, in `_escape_mermaid_label`.

3. **Empty containers render as `key = `.** `[]` and `set()` pass the `all(...)` check vacuously and produce a dangling `=`. Skip empty containers or render them explicitly.

4. **Silent information loss for dicts and nested values.** This is a deliberate trade-off, and it fixes the `__tools` and `__subagents` crashes. Something like `key = {…}` or `key = <dict>` would still show that the metadata exists. At minimum, mention it in the docstring.

5. **Unescaped Markdown characters.** `MARKDOWN_SPECIAL_CHARS` (`*_\``) already exists in this module for node names. Metadata values with those characters, such as `__tools`, which contains underscores, may be rendered as Markdown in some Mermaid renderers. The existing snapshot shows how node names are handled. Check whether metadata needs the same treatment.

6. **Node names are still not escaped.** `label` is built from `node_name` and the escaping covers only metadata. A name containing brackets could still break rendering. This is out of scope here, but worth a follow-up issue.

### Code quality

- The new helpers have no docstrings and `_format_metadata_value` has no return-type explanation. They are private, so this is minor. `AGENTS.md` asks for type hints, and those are present.
- `isinstance(value, (list, tuple, set))` misses `frozenset`, which would be silently dropped. Using `(set, frozenset)` costs nothing.
- Calling `sorted` on the stringified items is correct. It avoids a `TypeError` on mixed types and keeps the order stable.

### Performance and security

- Performance is not a concern. The work is linear in the size of the metadata.
- Escaping a label is the right defense against Mermaid syntax injection through user-controlled metadata. The `<` and `>` escapes also stop HTML injection into the rendered label, which is a real XSS vector when Mermaid runs with a permissive `securityLevel`. The fix is good for security.

### Tests

The new test covers lists, sorted sets, dicts, special characters and the all-omitted case. It asserts substrings rather than a full snapshot, which makes it resilient. Missing cases:
- `None` values and empty containers (items 1 and 3).
- Newlines in values (item 2).
- Tuples, since the code handles them but the test never uses one.
- A `draw_mermaid_png` path or a `ToolNode` graph. These were the user-facing symptoms, and one end-to-end check would guard against regressions.

### Verdict

The change is correct for the reported bug. I'd follow up on items 1–3, since they are small edge-case cleanups. Item 1 changes existing behavior, so it matters most.
