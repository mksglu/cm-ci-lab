# REVIEW A

## Review of PR #41520: `chore(model-profiles): refresh model profile data`

This is an automated data refresh from the `refresh_model_profiles` workflow. It changes only the generated `_profiles.py` files for `huggingface` and `openrouter`, with no logic changes. It's already merged, so these notes are for follow-up.

### Overall

- The title follows Conventional Commits with a scope, and the generated summary in the description makes the diff easy to audit.
- Security and performance: no concerns. These are static dict literals.
- Tests: none are needed for generated data. The models touched here aren't hardcoded in any package logic I could find; for example, `ChatOpenRouter` in `chat_models.py` never reads `max_output_tokens`. So the main risk is to users and middleware that read `model.profile`.

### Data issues to check upstream

1. **The DeepSeek V4 Flash values look swapped back and forth.**
   - `deepseek/deepseek-v4-flash` goes from 943,717 to 131,072 max output tokens.
   - `deepseek/deepseek-v4-flash-0731` goes the other way, from 131,072 to 943,718.
   - The same back-and-forth shows up in `deepseek-v4.1-flash` and `~z-ai/glm-latest`.

   943,718 is about 90% of a 1,048,576-token context, which looks like a fallback guess ("output = 0.9 × context") rather than a published limit. Many other OpenRouter entries still carry 943,718 or 943,717, and so did the old `gemma-3-4b-it` and `gemma-4-31b-it` values (117,964 and 235,929, also about 0.9 × context). If the source data fluctuates between runs, every refresh will produce noisy diffs and wrong numbers like these. Two possible fixes:
   - Pin these limits in `profile_augmentations.toml`.
   - Have the CLI drop or flag values that equal `floor(0.9 * max_input_tokens)`.

2. **`xiaomi/mimo-v2.5-pro` changes from 945,000 to 235,929.** 235,929 is 0.9 × 262,144, which is the same suspected heuristic. The model's `max_input_tokens` is 1,050,000, so this new number doesn't come from its own context either. It's probably wrong, though the model is marked `deprecated`, so the impact is small.

3. **The new `MiniMaxAI/MiniMax-M3.1-Flash` entry on Hugging Face looks inconsistent with its siblings.**
   - It has `"open_weights": False`. Every other `MiniMaxAI/*` entry in this file (M1, M2, M2.x, M3) is `True`, and the model is served under a Hugging Face org repo. This may be an upstream data error.
   - It has no `structured_output` key, while `MiniMax-M2.7` and `MiniMax-M3` include `"structured_output": True`. Code that checks `profile.get("structured_output")` will treat this model as not supporting it.
   - 512,000 max output tokens, half the context window, is unusually high and worth a sanity check.

4. **Two models were removed** (`arcee-ai/trinity-large-thinking`, `ibm-granite/granite-4.0-h-micro`). Users of these IDs will silently get an empty profile instead of an error. That fits how the refresh tool works, but a deprecated status on the model is more useful than deleting it outright. If the upstream source supports it, consider keeping removed models with `"status": "deprecated"` for one release cycle, as is already done for `bytedance-seed/seed-1.6` and `xiaomi/mimo-v2.5*`.

### Smaller notes

- `z-ai/glm-5.1` (131,072 → 128,000) and `qwen/qwen3.5-27b` (65,536 → 81,920) look like real corrections.
- The new `openai/gpt-6.1-terra` and `openai/gpt-6.1-terra-pro` entries are internally consistent with the other OpenAI reasoning models (`temperature: False`, `structured_output: True`, PDF input).

### Verdict

The PR is fine to merge as generated data. Items 1 and 2 point to a systematic quality problem: max-output values that look like 0.9 × context guesses rather than real limits, and that flip between runs. I'd fix that in `langchain-profiles` or the augmentation files so future refreshes stop introducing wrong limits. Item 3 should be reported upstream or overridden in the Hugging Face augmentations.

**Review of PR #41520: `chore(model-profiles): refresh model profile data`**

This is a bot-generated refresh of two data files: the Hugging Face and OpenRouter `_profiles.py`. The code side is fine. The data side has a problem: several values keep flipping back and forth between refreshes.

### Code quality and best practices
- Both files stay valid and follow the existing pattern. Keys are sorted, the schema is unchanged, and `tool_call_streaming: True` still matches the `profile_augmentations.toml` override.
- The title follows Conventional Commits with a scope, and the PR body summarizes the changes clearly.
- None of the removed models (`arcee-ai/trinity-large-thinking`, `ibm-granite/granite-4.0-h-micro`) or changed models are used anywhere in `libs/` outside the generated profile files. The removals break no tests or code.

### Potential bugs or issues
1. **`max_output_tokens` keeps flipping between refreshes (main concern).** I compared this PR with the last few refresh commits. The same entries swap between a real limit and a value that is about 90% of the context window:

   | Model | #41469 | #41494 | This PR |
   |---|---|---|---|
   | `deepseek/deepseek-v4-flash-0731` | 131,072 → 943,718 | → 131,072 | → **943,718** |
   | `~z-ai/glm-latest` | 943,718 → 131,072 | → 943,718 | → **131,072** |
   | `google/gemma-4-31b-it` | — | 16,384 → 235,929 | → **16,384** |

   Values like 943,717/943,718 (0.9 × 1,048,576), 235,929 (0.9 × 262,144) and 117,964 (0.9 × 131,072) are almost certainly a "90% of context" fallback from OpenRouter or models.dev, not real limits. Many changes here move away from that fallback (`deepseek-v4-flash`, `deepseek-v4.1-flash`, `gemma-3-4b-it`, `gemma-4-31b-it`, `mimo-v2.5`, `glm-latest`), which is good. Two move toward it:
   - `deepseek/deepseek-v4-flash-0731` → 943,718. The other v4-flash variants are now 131,072, so this one is very likely wrong.
   - `xiaomi/mimo-v2.5-pro` → 235,929. That is 0.9 × 262,144, even though the listed input context is 1,050,000. This looks like a fallback taken from a different endpoint's context window.

   **Impact:** anything that sizes requests from `model.profile["max_output_tokens"]` (summarization middleware, token budgeting, user code) will alternate between asking for about 131K and about 944K output tokens from one day to the next. The larger value can be rejected by the provider or cause runaway costs.

   **Suggestions:**
   - Short term: pin these models in `profile_augmentations.toml`, which supports per-model overrides.
   - Longer term: make `langchain-profiles refresh` (or the refresh workflow) treat `max_output_tokens == floor/round(0.9 × max_input_tokens)` as suspect. It could keep the previous value or flag it in the PR summary for a human, instead of committing it silently.

2. **The new entries look plausible but are unverified.**
   - `MiniMaxAI/MiniMax-M3.1-Flash` lists 512,000 output tokens on a 1M context, which is unusually high.
   - `openai/gpt-6.1-terra` and `openai/gpt-6.1-terra-pro` list `temperature: False`, which is consistent with other OpenAI reasoning models on OpenRouter.

   These come from upstream, so they are only worth a quick sanity check against the provider docs, not a blocker.

### Performance considerations
None. This is static dictionary data, and roughly 23 net added lines make no difference to import time.

### Security concerns
None. The files are generated, contain only literals, and there is no executable logic.

### Test coverage
- Hand-generated data needs no new unit tests, and the existing profile-loading tests cover the structure.
- The flip-flop pattern is something tooling could catch: a check in the refresh workflow (or a test in `libs/model-profiles`) that flags entries where `max_output_tokens` is about 90% of `max_input_tokens`.

### Verdict
Fine to merge as routine data. Most of the changes fix inflated output limits. Before or right after merging, though, pin `deepseek/deepseek-v4-flash-0731`, `xiaomi/mimo-v2.5-pro`, `~z-ai/glm-latest` and `google/gemma-4-31b-it` with overrides so the next refresh doesn't undo the fixes.
