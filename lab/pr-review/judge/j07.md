# REVIEW A

**Review of PR 37046: distrust compromised eMudhra CAs** (already merged)

**Summary:** This is a security dependency bump. It moves `rustls-webpki` to 0.103.16, `webpki-roots` and `webpki-root-certs` to 1.0.10, and `aws-lc-rs` to 1.18.2. It also moves the ML-DSA code in `ext/crypto/mldsa.rs` from `unstable` APIs to the stable ones. Both the approach and the scope look appropriate for the problem.

**What looks good**
- `rustls-webpki = "0.103.16"` is a minimum version, not an exact pin. That is the right choice, because it stops a future lockfile regeneration from silently resolving to a vulnerable version.
- The transitive `webpki-roots` 0.26.x was handled through the 0.26.11 wrapper, which re-exports 1.0.10. reqwest and hyper-rustls therefore get the same fixed bundle, with no duplicate stale root store. This is the part of a CA fix most likely to be missed.
- The ML-DSA change is mechanical. It swaps `to_pkcs8()` for `to_pkcs8v1()`, and the PR says this keeps the existing export format. `mldsa_export_pkcs8` is the only call site that changed behaviorally.
- The PR bundles the `deno_graph` 0.111.1 bump, so its own TLS stack also gets the fix.

**Concerns and suggestions**
1. **Two `aws-lc-sys` versions in the lockfile.** The lockfile now has 0.46.0 (pulled in by `aws-lc-rs` 1.18.2) and 0.40.0 (pinned in the workspace and used directly by `deno_crypto_provider` and `deno_crypto`). That means two copies of AWS-LC get compiled and linked. This risks longer builds, a larger binary, and possible symbol or ABI confusion. Direct use of `aws-lc-sys` types from 0.40 next to `aws-lc-rs` on 0.46 is hazardous if any raw pointers or structs cross that boundary. I'd bump the workspace `aws-lc-sys` pin (`Cargo.toml`) to 0.46 in a follow-up so there is one copy. If the pin is held back deliberately, for example because of `prebuilt-nasm` or `ed448-goldilocks`, a comment saying so would help.
2. **Test coverage.** The PR has no automated test showing that a chain through a compromised eMudhra key is rejected, or that `emSign ECC Root CA - G3` is gone from the root store. A spec test is hard because it needs a fixture chain. A small unit test in `deno_tls` could assert the removed root's subject is absent. At minimum, the existing ML-DSA WebCrypto unit tests should confirm the PKCS#8 export is byte-compatible. The PR relies on CI for that and doesn't say so explicitly.
3. **`webpki-root-certs` 0.26 → 1.x is a major bump.** Callers that read the `TrustAnchor` or `CertificateDer` types in `deno_tls` and `deno_node` should keep compiling, since the PR reports `cargo check` passing. It is still worth confirming that `tls.rootCertificates` in Node compat returns the expected PEM set, because that list will change in content and possibly in ordering.
4. **Minor:** `pkg-config` 0.3.30 → 0.3.34 and the other lockfile churn are unavoidable here. The PR description should have said that `deno_graph`'s bump is unrelated in mechanism, since it came in through its own PR, but this is cosmetic.

**Security:** There are no new concerns. The change closes a real trust-store issue. Make sure a release note or backport covers supported release branches.

**Verdict:** Approve. The follow-ups I'd want are a single `aws-lc-sys` version and a small regression test for the removed root.

# REVIEW B

**Review of PR 37046: distrust compromised eMudhra CAs** (already merged)

**Summary:** This is a dependency-only security fix, plus a small ML-DSA API migration. It raises `rustls-webpki` to 0.103.16, `webpki-roots` and `webpki-root-certs` to 1.0.10, `aws-lc-rs` to 1.18.2 and `deno_graph` to 0.111.1. The ML-DSA code in `ext/crypto/mldsa.rs` moves to the stable signature API. The approach looks right. I only read the diff, and I didn't build it or run any tests.

**Good**
- `rustls-webpki = "0.103.16"` sets a minimum version, so the fix can't be lost to a lockfile regression. Pinning `webpki-roots` and `webpki-root-certs` to 1.0.10 does the same for the bundled roots.
- The `webpki-roots` 0.26.11 shim is a thin wrapper over 1.0.10. Reqwest and hyper-rustls therefore get the fixed root set without being patched.
- The ML-DSA migration is small. It uses `to_pkcs8v1()` to keep the exported PKCS#8 format unchanged, and the PR description says why.

**Concerns and suggestions**
1. **Two `aws-lc-sys` versions in the lockfile.** `aws-lc-rs` now pulls in `aws-lc-sys` 0.46.0. The workspace still pins `aws-lc-sys = "0.40.0"` with `prebuilt-nasm`, which `deno_crypto` and `deno_crypto_provider` use.
   - **Build cost:** AWS-LC is compiled twice, which adds build time and binary size.
   - **Possible symbol conflict:** Both builds export C symbols. `aws-lc-sys` uses a version-prefixed symbol scheme to avoid collisions, so this probably links fine. CI passing would confirm it.
   - **Behavior drift:** `deno_crypto_provider` calls `aws-lc-sys` 0.40 directly, while `aws-lc-rs` runs on 0.46. If any data crosses between the two, such as key material, behavior could drift.
   - **Missing `prebuilt-nasm`:** The 0.46.0 entry in the lockfile doesn't show the `prebuilt-nasm` feature. Windows builds may then need NASM installed, unless the feature is unified some other way. Please check the Windows CI job.
   - **Suggestion:** Bump the workspace `aws-lc-sys` pin to match 0.46 in a follow-up so only one copy remains.
2. **Major-version jump in `webpki-root-certs` (0.26 to 1.x).** The `deno_tls` and `deno_node` checks passed, but I'd confirm that nothing relies on the old `TLS_SERVER_ROOTS` type shapes at runtime. The 1.x `rustls-pki-types` types should be compatible.
3. **No regression test.** The PR has no spec test showing that a chain through the compromised eMudhra keys is rejected, or that `emSign ECC Root CA - G3` is gone from the bundle. A fixture-based test would be hard to build, since it needs the compromised keys. A cheap alternative is a unit test that checks the bundled roots don't contain that subject. Otherwise, the fix rests on upstream test coverage alone.
4. **Mixed concerns.** The PR bundles the ML-DSA API migration and the `deno_graph` bump with the security fix. The description justifies both: the `aws-lc-rs` bump forced the migration, and `deno_graph` carries the same TLS fix. Still, CLAUDE.md asks for minimal, focused PRs. The `deno_graph` bump is an unrelated-looking line in an otherwise coherent description.
5. **Possible unfixed paths.** Other TLS roots paths may remain, such as `deno_native_certs` and `DENO_CERT` or `--cert` user-supplied stores. Those are intentionally user-controlled. The system store could still trust eMudhra, but the OS vendors control that. It would help to say so in the release notes.

**Security:** No new risks in the diff. The change reduces risk. Lockfile checksums come from the crates.io registry, as expected.

**Verdict:** Looks good. The main follow-ups are checking the duplicate `aws-lc-sys` and `prebuilt-nasm` situation, and adding a small test that the bundled roots exclude the removed CA.
