# REVIEW A

**Review of PR 345293: hide non-user-invocable agents from the Cloud picker**

The PR is already merged. I read the diff only and did not run the tests.

**Summary:** The change is small and focused.
- Remote agents with `user_invocable === false` are filtered out of the picker.
- The full remote-name list is still passed to `getLocalCustomAgentFiles`, so a hidden remote agent can't reappear as a "Missing from…" local-only warning.
- Local-only entries now honor `user-invocable: false` from frontmatter, parsed with the existing `PromptFileParser`.

**Code quality**
- Filtering with `!== false` keeps the default as visible, and the test covers that.
- The PR reuses `PromptFileParser` instead of a hand-rolled frontmatter regex. The new tests cover CRLF line endings, inline comments, nested keys, and a body-only mention.
- The comment "Match all remote names so hidden agents cannot reappear…" explains the non-obvious part well.
- Nit: `new PromptFileParser()` and `new TextDecoder()` are created inside the loop. Hoisting them above the loop is cheap and tidier, if the parser is stateless.

**Potential issues**
1. **Sequential reads.** Each local-only file is now awaited one at a time inside the `for` loop. The agents directory is normally small, so this is minor. `Promise.all` would remove the latency if the directory grows.
2. **Parse failures.** If `parse` throws, the file is logged and skipped, so the user sees no warning entry. That is reasonable for unreadable or deleted files. A file with malformed frontmatter would also vanish silently. The parser probably tolerates bad frontmatter, but it's worth confirming that a parse error doesn't hide an agent the user expects to see.
3. **Warning log content.** The warning interpolates the raw `error`, which is fine. The test only checks that the file name appears in the message.
4. **Stale remote state.** The picker is filtered but nothing guards the selection path. If a user already has a hidden agent id stored from before this change, it may still be submitted and hit the HTTP 400. Consider validating the stored selection against the filtered list. This is outside the PR's stated scope.

**Performance:** The only added cost is one file read and parse per local-only agent file, and files that match a remote agent are not read.

**Security:** I found no concerns. The files read are workspace `.github/agents` entries already enumerated by the existing code, and nothing is executed. Parsing is done by the existing parser.

**Test coverage:** Coverage is good. The seven cases cover:
- visibility defaults, including `manual-only` and an empty `display_name`
- every remote agent hidden, which omits the group
- remote visibility winning over local frontmatter, with case-insensitive file matching
- local frontmatter variants, run both with and without a remote fetch failure
- deleted and unreadable files, logged while discovery continues

Two small gaps:
- There is no test for a parse error, as opposed to a read error.
- The test mocks (`FileSystemError`, `window`, `asRelativePath`) are reasonable, but `FileSystemError` is a bare `Error` subclass with a fixed `code`. That is fine for these tests but could hide divergence from the real class.

**Verdict:** Approve. It's correct, minimal, and well tested. The points above are optional follow-ups: hoisting the allocations, parallelizing reads, and checking stored selections.

# REVIEW B

**Review of PR #345293: hide non-user-invocable agents from the Cloud picker**

The PR is already merged. It is a small, well-scoped fix, and I found no blocking issues.

**What it does well**
- It filters at the picker boundary with `agent.user_invocable !== false`. Agents that omit the field stay visible, and `disable_model_invocation` agents are untouched.
- It passes the full remote list to `getLocalCustomAgentFiles`. A hidden remote agent therefore still counts as a "match", so its local file can't reappear as a "Missing from remote" warning. The comment explains why.
- It reuses `PromptFileParser` instead of a regex. The tests cover CRLF line endings, trailing YAML comments, nested keys and body-only text, which are the cases where a hand-rolled parser would usually break.
- The per-file `try/catch` with `logService.warn` means one bad file doesn't stop discovery of the others.
- The tests are thorough. There are seven cases, including one that runs with the remote fetch failing.

**Minor points and suggestions**
1. **Sequential reads.** Each local-only file is read with `await` inside the loop. This is fine for a handful of agent files, but `Promise.all` would be a cheap improvement if directories get large. Reads now only happen for unmatched files, so the cost is limited.
2. **Decoding.** `new TextDecoder().decode(content)` is created per file. It could be hoisted outside the loop. There may also be a shared helper in `fileSystemService` for reading a file as a string. This is cosmetic.
3. **Parse errors.** If `parse` throws on malformed frontmatter, the file is dropped from the picker with only a warning. A malformed file is probably better shown as a local-only warning, because that's the existing behaviour for files that can't be classified. The PR describes it as "log and continue", so this is a judgment call. I'd mention it for consistency.
4. **Filtering location.** Filtering is at the picker only. If a previously selected hidden agent ID is persisted in session options, it may still be sent to the API. That could still produce the 400 from the linked issue. It's worth checking whether a stale selection is validated elsewhere.
5. **Test mocks.** The `vscode` mock now has a local `FileSystemError` stub and a changed `activeRepository`. Both are fine for this spec file. If other specs need the same mocks, they could move to shared test utilities.

**Security and performance**
- No security concerns. The change reads workspace files that were already being enumerated, and the parsing is local.
- There is no meaningful performance impact beyond the extra reads in point 1.

**Verdict:** Looks good. The only item I'd follow up on is point 4, to confirm that a stale hidden-agent selection can't still reach the API.
