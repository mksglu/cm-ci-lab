# REVIEW A

**Review of PR #100956: Fix prerendering of caught `'use cache'` errors**

**Verdict:** The fix is correct and narrowly scoped. It addresses the root cause without changing how caught errors are logged. I found no blocking issues. My comments are mostly nits and test-coverage suggestions. (The PR is already merged, so these would be follow-ups.)

### What the PR changes

`workStore.reactServerErrorsByDigest` had two jobs:
1. It maps digests back to the original errors, so errors from `'use cache'` boundaries can be logged and reported (#86500).
2. Through `digestErrorsMap`, it tells `prerenderToStream` whether the render failed (`app-render.tsx:2749-2768`).

The `'use cache'` wrapper's own error handler (`use-cache-wrapper.ts:1424`) writes into that same map. So an error thrown inside a cached function was recorded even when the page caught it. The prerender then treated it as a failure, which broke the build, or caused a 500 and no caching during on-demand generation.

The PR adds a separate map, `renderErrorsByDigest`, local to `prerenderToStream`. Only the page's own RSC handler (`serverComponentsErrorHandler`) fills it, and all eight `digestErrorsMap:` return sites now use it. The shared map is still used to recover the original error (`app-render.tsx:10418`), and the SSR handler still uses it to tell RSC errors apart from SSR errors.

### Correctness

- **Errors the page doesn't catch still fail the prerender.** When a cached error reaches the page's Flight `onError`, it already has a digest. The handler resolves the original error and now also records it in `renderErrorsByDigest` (`create-error-handler.tsx:119`), so build failures still happen.
- **Every RSC render in `prerenderToStream` that should count is covered.** That includes the final prerender (`app-render.tsx:9761`), the non-cache-components path, and the error-page render (`:10848`). The prospective/initial render (`:9360`) has its own `onError` and never wrote to the shared map, so nothing changes there.
- **Other render paths are unaffected.** The validation render at `:8695` and the dev-only abort path in `use-cache-wrapper.ts:1688` still write to the shared map. Neither feeds `digestErrorsMap`, and dynamic-usage aborts are handled separately through `workStore.invalidDynamicUsageError`.

### Code quality and nits

1. **The two maps keep different entries for a repeated digest.** The shared map keeps the first error per digest (`if (!reactServerErrors.has(...))`). The new map always overwrites (`renderErrorsByDigest?.set(...)`). `Map.set` keeps a key's original position, so `values().next()` still returns the first failing digest. But the value stored under it can differ between the two maps when two errors share a digest.
   - In production this doesn't matter, because `err` is replaced with the recovered original.
   - For consistency, consider recording the same object in both maps, for example `renderErrorsByDigest?.set(err.digest, reactServerErrors.get(err.digest)!)`, or use the same "first wins" guard.
2. **Positional optional arguments.** `createReactServerErrorHandler(..., onHTMLRenderRSCError, undefined, renderErrorsByDigest)` now passes `undefined` just to skip `spanToRecordOn`. With two optional trailing parameters, an options object would read better and avoid mistakes at future call sites.
3. **The parameter needs a doc comment.** The explanation lives at the call site (`app-render.tsx:9050-9053`). A short JSDoc on `renderErrorsByDigest` in `create-error-handler.tsx` would explain why there are two maps to anyone reading the handler alone.
4. **A nearby TODO now reads oddly.** The `// @TODO by putting this here and not at the top it is possible that we don't error the build…` comment (`create-error-handler.tsx:113`) still sits above the shared-map write. The code that actually decides build failure is now the next line. Moving the TODO or rewording it would help.

### Test coverage

The new e2e suite uses a real fixture directory as recommended. It covers both a build-time route (`generateStaticParams` → `/static`) and an on-demand one (`/runtime`), and checks `x-nextjs-cache: HIT` in start mode. Skipping the header check in deploy mode is the right call. Suggestions:

- **Add the opposite case.** Add a page where the cached function's error is *not* caught and assert that `next build` fails (or that on-demand generation returns 500 and isn't cached). This PR changes which errors count as failures, so a direct regression test for the uncaught case would guard against the new map missing errors. Existing `use-cache` suites may already cover this; if so, link them in the PR.
- **Assert that the caught error is still logged.** The PR says logging behaviour from #86500 is kept. Checking `next.cliOutput` for `Cached function failed: static` (and for `runtime`) would lock that in.
- **Add a passed-as-prop case (optional).** A page that catches the cached error and passes it to a client component exercises the interaction with the SSR handler's lookup in the shared map (`create-error-handler.tsx:194`).

### Performance

There is one extra `Map` per prerender and one `set` per reported RSC error, which is negligible.

### Security

There are no new header reads or user-controlled inputs. The change narrows which errors fail a prerender but doesn't change error obfuscation: production still records the recovered original error only on the server side. No concerns.

# Review: PR #100956 — Fix prerendering of caught `'use cache'` errors

## Summary

`workStore.reactServerErrorsByDigest` was doing two jobs:

1. **Logging lookup.** It maps a digest back to the original error, including errors that `use-cache-wrapper.ts` records when a `'use cache'` function throws.
2. **Failure signal.** `prerenderToStream` returned it as `digestErrorsMap`, and the caller treats any entry there as a render error (`app-render.tsx:2749`).

Because of the second job, a page that caught the error from a cached function (`try { await cached() } catch { return <Fallback/> }`) still failed the build or on-demand generation. The PR adds a separate `renderErrorsByDigest` map. Only the page's own RSC error handler fills it, and every `digestErrorsMap` return in `prerenderToStream` now uses it. The fix is small, well targeted and well explained. I'd approve, with the minor notes below.

## Correctness

- **The new map holds the right errors.** It is filled only inside `createReactServerErrorHandler`, after the digest has been resolved. So it only contains errors that actually reached the outer RSC renderer. An error caught in userland never reaches the handler, so it stays out of the map. That is the intended behaviour.
- **Errors from a cached function that are *not* caught still fail the build.** They reach the outer handler with the cached function's digest, the original error is looked up, and it is written into `renderErrorsByDigest`. In production, `err` has already been replaced by the de-obfuscated original, so build failure messages are as good as before.
- **All return sites are covered.** All seven `digestErrorsMap` returns in `prerenderToStream` were switched, including the error-boundary paths. The `new Map()` return at around line 10097 is unchanged, which is correct.
- **The shared map is still used where it should be:**
  - `throw reactServerErrorsByDigest.get(...) ?? err` (around line 10418)
  - the SSR-error dedupe filters (around lines 10520 and 10834)

  These are lookups to recover or dedupe errors, not failure checks, so they correctly keep using the shared map.
- **The prospective render is not affected.** Its `onError` handlers (around lines 9360 and 9498) don't call `serverComponentsErrorHandler`, so errors that only happen during the warm-up render don't leak into the new map.

## Minor nits

1. **The positional `undefined` argument hurts readability.**
   ```ts
   createReactServerErrorHandler(..., onHTMLRenderRSCError, undefined, renderErrorsByDigest)
   ```
   The function now has two optional trailing parameters, one of them typed `any`. Consider an options object (`{ spanToRecordOn, renderErrorsByDigest }`) so call sites explain themselves. Not blocking.

2. **The two maps treat repeated digests differently.** The shared map keeps the *first* error per digest (`if (!has) set`). `renderErrorsByDigest?.set(...)` always overwrites, so for a repeated digest the value is the *last* error, while the key keeps its first insertion position. The caller reads `values().next()`, so it may now report a different error object than before. In practice, errors with the same digest are almost always equivalent. Still, `if (!renderErrorsByDigest.has(err.digest))` would match the existing behaviour.

3. **The comment sits in the wrong file.** The explanation is in `app-render.tsx`, but the new parameter in `create-error-handler.tsx` has no doc. A short JSDoc there ("errors that surfaced in this render; used to detect render failures, unlike `reactServerErrors`, which also holds errors from caught cached functions") would stop a future caller from mixing the two maps up again.

## Test coverage

The new e2e fixture is a minimal reproduction and covers both the build-time path (`/static` via `generateStaticParams`) and the on-demand path (`/runtime`). It uses `files: __dirname`, as the repo guidelines require. Suggestions:

- **Add a negative case.** Add a route where a `'use cache'` function throws and the error is *not* caught, and assert that it still produces an error (500 or error boundary in start mode). This protects the other half of the change: an uncaught error from a cached function must still end up in `renderErrorsByDigest`. A regression there would quietly turn real failures into successful builds, which is worse than the original bug.
- **Header assertion in deploy mode.** The `x-nextjs-cache` check only runs under `isNextStart`. That's fine, but it means deploy runs only check status and body. Since the PR says deploy tests are the reason for using a branch PR, it would help to also check a deploy-appropriate cache signal, or note why that isn't needed.
- **Dev mode.** In dev, the test only checks for a 200 and the fallback content. That's reasonable, because dev rendering doesn't go through `prerenderToStream`.
- **Unit test.** Optionally, a small unit test of `createReactServerErrorHandler` could check that a digest found in `reactServerErrors` is still copied into the render map. AGENTS.md discourages implementation-mapped unit tests, though, so the e2e negative case above is the better choice.

## Performance and security

- **Performance:** Negligible: one extra `Map` per prerender and one `set` per surfaced error.
- **Security:** No concerns. No new headers or inputs, and error recovery and obfuscation behave as before.

## Out of scope

The runtime-prerender path (`app-render.tsx:2015`) still has `// TODO(runtime-ppr): do we need to produce a digest map here?`. Whatever that path ends up doing, it should follow the same split: report only errors that reached its own handler, and not read the shared map.
