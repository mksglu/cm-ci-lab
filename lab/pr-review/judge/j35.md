# REVIEW A

**Review of PR #100956: Fix prerendering of caught `'use cache'` errors** (already merged and approved)

**Summary:** The fix is sound and narrowly scoped. `reactServerErrorsByDigest` is shared with `'use cache'` error recording, which exists so the renderer can recover original errors for logging (#86500). Prerendering also used it as the failure signal, so an error the page caught still failed the build. The PR adds a separate `renderErrorsByDigest` map that only the page's RSC error handler fills. The prerender result now returns that map, and the shared map stays in place for logging.

**What looks good**
- **Scope:** Every `digestErrorsMap` return site in `prerenderToStream` is switched, including the error-fallback paths (`errorServerResult`). I see no site left on the old map.
- **Backward compatibility:** `renderErrorsByDigest` is an optional trailing parameter and uses `?.set`, so other callers of `createReactServerErrorHandler` are unaffected.
- **Placement:** The `set` runs after the digest is guaranteed to exist and before dev-only formatting. This matches how the shared map is populated.
- **Comment:** The explanation next to the new map is clear and says why the second map exists.

**Nits and suggestions**
1. **Call site readability:** `undefined` is passed positionally for `spanToRecordOn` in the call to `createReactServerErrorHandler`. The function now takes two optional trailing parameters, and this will get worse if more are added. An options object would be cleaner. This is minor and may not be worth churning for.
2. **Possible overlap:** Errors in `renderErrorsByDigest` are a subset of what flows through the handler, and `reactServerErrors.set` is conditional on the error being a `'use cache'` one. If those conditions ever change, the two maps could diverge. A short comment in `create-error-handler.tsx` at the new `set` line would help the next reader. The comment currently lives only in `app-render.tsx`.
3. **Other callers:** I'd confirm that other render paths, such as the dynamic or runtime prefetch renders that pass `reactServerErrorsByDigest` to consumers, don't have the same issue. The PR description doesn't say whether these were checked.

**Potential bugs:** None found. The one behavior change is that errors recorded only through the `'use cache'` path no longer appear in `digestErrorsMap`. That is the intent. Be aware that anything downstream relying on that map to find the original error for SSR-error matching would now see only page-level errors. The diff doesn't show that happening.

**Performance:** The cost is one extra `Map` per prerender and one `set` per error. This is negligible.

**Security:** Nothing relevant. The change reads no request headers.

**Tests**
- The new e2e suite follows the repo conventions: it uses `nextTestSetup` with `files: __dirname` and a real fixture directory, and it has no `check()` or `setTimeout`.
- It covers both build-time (`static` via `generateStaticParams`) and on-demand (`runtime`) prerendering. It also asserts that the fallback is cacheable through the `x-nextjs-cache: HIT` header in start mode.
- **Gaps:**
  - The `HIT` check on the second fetch for `runtime` assumes the first fetch populated the cache. That should hold, but it is the likeliest source of flakiness.
  - There is no case for a caught error alongside an uncaught one on the same page. That would confirm real failures are still detected through `renderErrorsByDigest`.
  - The suite only runs with `cacheComponents: true`. The PR doesn't say whether the non-cacheComponents `'use cache'` path (legacy PPR) goes through the same code.
  - The `pnpm test-dev-turbo`, `test-start-turbo` and `test-start-webpack` results aren't in the PR description. They're worth confirming.

**Verdict:** Approve. The nits are optional, and the extra coverage for a mixed caught and uncaught error is the only follow-up I'd consider.

# REVIEW B

**Review of PR #100956: Fix prerendering of caught `'use cache'` errors** (already merged, approved)

**Summary:** Errors thrown inside `'use cache'` functions are recorded in the shared `workStore.reactServerErrorsByDigest` map so the page renderer can log the original error (#86500). Prerendering also used that map to decide whether the render failed. As a result, a page that caught a cached function's error could still fail the build or on-demand generation. The PR adds a separate `renderErrorsByDigest` map. The RSC error handler fills it only with errors the page's RSC renderer reports. All `digestErrorsMap` returns in `prerenderToStream` now use the new map. The shared map is left alone for logging.

**Code quality**
- The change is small and targeted. The comment at the declaration explains why there are two maps.
- All 7 `digestErrorsMap: reactServerErrorsByDigest` return sites are switched. I found no stale one in the diff. Because the diff is partial context, it is worth confirming with a grep that no other consumer in `prerenderToStream` still reads the shared map for failure detection.
- `createReactServerErrorHandler` now takes a positional `renderErrorsByDigest` parameter after `spanToRecordOn`. Call sites have to pass `undefined` for the earlier optional argument, as the diff does. This works but is awkward. An options object, or putting the new map before the optional span, would be cleaner. This is minor, since there are few callers.
- `renderErrorsByDigest?.set(...)` runs on every path that reaches that line. I'd check whether early returns above it, such as the "response closed" and bailout/postpone cases, skip it the same way they skip the shared map. From the diff it sits right after the shared-map `set`, so the behavior should match. The one difference is that the shared-map write is conditional (`reactServerErrors.set` appears inside an `if`) and the new write is unconditional. That is probably intended, because the cache-specific recording happens elsewhere. Even so, a short comment would help.

**Potential bugs**
- I found no correctness problems. One thing to confirm: errors from cached functions that are not caught, and that propagate through the page, still reach the page renderer's handler, so they land in `renderErrorsByDigest` and still fail the build. They should, since React reports them to `onError`. The test only covers the caught case, though.

**Performance**
- The cost is one extra `Map` per prerender and one `set` per error. That is negligible.

**Security**
- No new request headers are read, and nothing is exposed to users.

**Tests**
- The new e2e test uses a real fixture directory with `nextTestSetup({ files: __dirname })` and `it.each`. This follows the repo conventions. It covers both a `generateStaticParams` path (build-time) and a runtime path (on-demand). In start mode it checks that the fallback is cacheable (`x-nextjs-cache: HIT`).
- The test has no negative counterpart. Add a case where the cached function's error is not caught and confirm the build or generation still fails, so the fix can't mask real failures. It is also worth checking that dev mode doesn't log a spurious error. The existing logging behavior (#86500) isn't asserted either, so a regression there wouldn't be caught.
- The `'runtime'` id isn't in `generateStaticParams`. The page's `use cache` reads `id`, so this assumes that route renders on demand. That is correct, but a comment would make the intent clearer.
- A fixture with `cacheComponents: true` works, but the repo's gate-tests approach may be needed if this behaves differently without that flag.

**Verdict:** Looks good. The suggestions are optional: add an uncaught-error test, and consider an options object for the handler signature.
