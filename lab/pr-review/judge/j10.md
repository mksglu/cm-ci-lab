# Review of PR #100935: Turbopack: store `ChunkGroupInfo::chunk_groups` as a `Vec`

**Verdict:** Looks correct to me, with only minor notes. This is a small, well-aimed fix for a real cache-correctness bug, and it comes with a regression test. (The PR is already merged, so these are follow-up suggestions.)

## The bug and the fix

`ChunkGroupInfo` is a `#[turbo_tasks::value]`, so when a task recomputes, turbo-tasks compares the new cell value with the old one and keeps the old value if they are equal. `FxIndexSet`'s `PartialEq` compares as a set and ignores order. So a recomputation that only renumbered chunk groups (for example, because the graph entries were reordered) compared equal, and the cell kept the **old** order.

Meanwhile, `module_chunk_groups`, `async_loader_chunk_groups` and `chunk_group_indices` are separate `ResolvedVc` cells. They did update to the **new** numbering. The struct compares those fields by cell identity, so they never caused a mismatch on their own.

The result was that `get_chunk_groups_for_module` (`chunk_group_info.rs:109-116`) indexed `self.chunk_groups[index]` with new-numbering bitset indices into an old-numbering list. Modules could map to another entry's chunk groups. That is a silent miscompile in incremental builds, so the fix matters.

A `Vec` makes equality order-sensitive. It also makes indexing `O(1)` with no hashing, and serialization can use the default bincode impl instead of `turbo_bincode::indexset`. Nothing needed set semantics: every caller only did `get_index(i)` or `[i]`, and all of those were updated.

## Correctness notes

1. **`chunk_group_keys` is still an `FxIndexSet` marked `#[turbo_tasks(unsafe_ignore)]`** (`chunk_group_info.rs:56-58`). This is safe now only because `chunk_groups` is built 1:1 from the same `chunk_groups_map` (`chunk_group_info.rs:956, 968-990`), and each distinct key produces a distinct `ChunkGroup` (same variant, same fields). Any reorder of the keys therefore shows up as a difference in `chunk_groups`, the whole cell updates, and the ignored field updates with it. That invariant is implicit, and `get_shared_merged_chunk_group` (`:136-141`) depends on it, because it indexes `chunk_groups` with a position taken from `chunk_group_keys`. I'd suggest a short comment on `chunk_group_keys` saying it relies on `chunk_groups` for change detection and must stay in the same order. Otherwise a future change could make two keys produce the same `ChunkGroup` and quietly bring the bug back.
2. **`ChunkingHeuristicsInfo` is already order-sensitive** (`Vec<Vec<u16>>` plus a `Bitset`), so it stays consistent with the new numbering. Good.
3. **The other `FxIndexSet<ResolvedVc<Box<dyn Module>>>` uses** at lines 543, 578 and 769 are local to the computation. Merged entries are collected into `Vec` before being stored (`:979, :987`), so they don't have this problem. The description says other places are being audited. Worth a follow-up: any `#[turbo_tasks::value]` that stores an `IndexSet` or `IndexMap` whose positions act as indices is the same hazard. A grep for `bincode(with = "turbo_bincode::indexset")` / `indexmap` on value types would turn them up quickly.

## Test coverage

`test_chunk_group_info_reordered_entries` is a good regression test:
- It uses a `State<bool>` to flip the entry order inside a single `TurboTasks` instance, so it actually exercises the "recompute and compare equal" path rather than a cold computation.
- It checks the observable symptom (which groups `page1.js` and `lazy1.js` map to), not internal layout, so it won't break on harmless refactors.
- `read_strongly_consistent()` after the state change is the right way to wait for invalidation to settle.

Smaller test suggestions:

- `_ => "other"` in the `kind` match is fine. An explicit `unreachable!` or a full mapping would make an unexpected group type fail loudly instead of producing a confusing string diff.

## Performance and security

- **Performance:** neutral to slightly better. `Vec` avoids the hash table that `IndexSet` keeps, and every access is positional anyway. Equality is now positional, which is a little cheaper than set comparison. The cost of comparing the whole value is unchanged and still `O(n)`.
- **Security:** no concerns. This is internal bundler state with no external input or header handling.

## Style

- It follows `turbopack/AGENTS.md`: no new cells or tasks, and keyed-cell access in `get_index_of` is unchanged.

# REVIEW B

I'd approve this PR. The fix is correct and small, the test exercises the exact failure, and I found no blocking issues. (It's already merged, with approvals from mischnic and sokra.)

## Summary
`ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. `IndexSet`'s `PartialEq` ignores order. So if a recompute produced the same chunk groups with new numbers, turbo-tasks treated the new cell as equal to the old one and kept the old order. Meanwhile `module_chunk_groups` (bitsets) and `chunk_group_indices` were stored as separate cells, got updated, and used the new numbering. Every index-based lookup, such as `self.chunk_groups[index]` in `get_chunk_groups_for_module` and `get_chunk_group`, could then return a different entry's chunk group.

## Correctness
- **The fix is sound.** `Vec` equality depends on order, so any renumbering now marks the cell as changed. That is the property every index-based consumer relies on.
- **`chunk_group_keys` now also stays in sync.** It is still an `FxIndexSet` marked `#[turbo_tasks(unsafe_ignore)]`, so it plays no part in equality. Before this change, a reorder left `chunk_group_keys` stale as well, and those keys feed `AvailableChunkGroups::hash` (`keys.get_index(id)`) and `translate_chunk_group`. Now the whole struct is replaced on a reorder, so the keys stay coherent too. This works because `ChunkGroupKey` and `ChunkGroup` map one-to-one: the merged variants carry the same `parent` index and `merge_tag`. Two suggestions:
  - Add a comment on `chunk_group_keys` saying `unsafe_ignore` is only sound because `chunk_groups` has the same length and order and is compared by order. That keeps a future refactor from quietly bringing the bug back.
  - Longer term, consider building both from a single source, e.g. a `debug_assert` that `chunk_groups[i]` corresponds to `chunk_group_keys[i]`.
- **The `get_index` → `get` call-site changes in `module_batches.rs` and the test helper are mechanical and correct.** Nothing used set lookups on `chunk_groups`; those go through `chunk_group_keys` or `chunk_group_indices`.
- **The `ChunkGroupKeyToIndex` doc comment already describes the same `IndexSet` hazard.** This change makes the main struct consistent with that reasoning.

## Performance
- **This is likely a small improvement.** A `Vec` has no hash-table overhead, cloning is cheaper, and the cell equality check becomes a linear element-by-element comparison instead of a hash lookup per element.
- **There may be more invalidation.** A reorder now correctly invalidates readers of `ChunkGroupInfo`. That is the point of the fix, and the previous "savings" were bugs.
- **The persistent cache format changes, from the `indexset` bincode adapter to a default `Vec` encoding.** That should be covered by the normal cache versioning, but it's worth confirming that no manual cache-version bump is needed.

## Tests
- **`test_chunk_group_info_reordered_entries` is well aimed.** It builds two entries that each have an async child, reverses the entry order through a `State`, and checks that `page1.js` and `lazy1.js` still map to their own entry and async group. Without the fix, the stale order would produce something like `page1.js: entry page2.js`, so the test should fail. If not already done, it's worth briefly confirming that by reverting the fix locally.
- **Minor gaps:**
  - It only checks `page1` and `lazy1`. Also describing `page2` and `lazy2` would catch swaps in both directions for little extra cost.
  - The `_ => "other"` arm would hide unexpected group kinds. Printing the variant, or using `unreachable!`, would make a failure more informative.
  - It doesn't check the `chunk_group_keys` path, e.g. `get_shared_merged_chunk_group` or `AvailableChunkGroups::hash` after a reorder. That path is fixed implicitly here, but it isn't tested.

## Related follow-ups
The description mentions looking for other places with the same risk. In `module_graph/`:
- **`VisitedModules::modules`** (`FxIndexMap<_, GraphNodeIndex>`) looks safe, because the map values carry the indices, so renumbering still changes equality.
- **`StyleGroups::shared_chunk_items`** (`FxIndexMap`) is worth checking. Its doc comment says its order "fully determines the final per-chunk-group ordering". If a pure reorder with identical `StyleItemInfo` values is possible, it has the same problem.
- **More generally,** any `#[turbo_tasks::value]` field typed `IndexSet` or `IndexMap` whose position carries meaning has this bug class. A clippy or ast-grep lint, or a short note in `turbopack/AGENTS.md`, would help prevent it.

None. This is internal bundler data structure code.
