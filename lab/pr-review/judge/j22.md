# REVIEW A

**Review of PR #100956: Fix prerendering of caught `'use cache'` errors** (already merged and approved)

**Summary:** The fix is correct and small. `reactServerErrorsByDigest` on the work store is shared. Cached functions record errors into it for logging (#86500), even when the page catches them. Prerendering also used that map as `digestErrorsMap` to decide whether the render failed. So a caught `'use cache'` error failed the build or on-demand generation. The PR adds a second map, `renderErrorsByDigest`. Only the page's own RSC error handler fills it. The map feeds all `digestErrorsMap` return sites. The shared map still serves logging.

**Code quality**
- The change is minimal and well commented. The new optional parameter on `createReactServerErrorHandler` is backwards compatible.
- Passing `undefined` positionally for `spanToRecordOn` is a bit awkward. An options object would be tidier if this signature grows again. This is minor.
- I checked that every `digestErrorsMap: reactServerErrorsByDigest` in `prerenderToStream` was switched. The diff shows 7 sites (dynamic and static paths, plus the error-render paths), and none appear missed. It is worth grepping once more for any remaining use of the shared map as an error signal. One example is the PPR/resume or `prerenderToStream` paths for other render modes.
- `renderErrorsByDigest?.set(...)` sits after the early-return paths. Errors that the handler deliberately skips, such as bailout and postpone errors, are therefore not recorded. That matches the existing behaviour for the shared map, which is what you want.

**Potential issues**
- If a cached function's error is not caught and propagates through the page, the page's RSC renderer should still call the handler with the same digest. The failure is therefore still detected. That path has no test.
- The `error` and `digestErrorsMap` consumers key on digest. Errors with the same digest from the page and from the cache are now stored separately. That is intended, and I see no collision problem.

**Performance:** Negligible. It adds one `Map` per prerender and one `set` per reported error.

**Security:** No concerns. No request headers are read.

**Test coverage**
- The e2e test covers a build-time route (`static`) and an on-demand route (`runtime`). It checks the 200 status, the fallback content, and an `x-nextjs-cache: HIT` on the second request in start mode. That confirms the fallback is cacheable.
- The test follows the repo's conventions: it was generated as a fixture directory and uses `nextTestSetup({ files: __dirname })`.
- Gaps, all optional:
  - No assertion that the build does not log or fail. It passes if the build succeeds, so this is implicit.
  - No negative test that an uncaught `'use cache'` error still fails prerendering.
  - Dev mode just checks the content.
  - A `cacheComponents: false` variant is not covered. `'use cache'` requires the flag, so this is probably fine.

**Verdict:** LGTM. The one follow-up worth considering is a regression test confirming that uncaught cached-function errors still fail the build.

# REVIEW B

**Review of PR #100956: Fix prerendering of caught `'use cache'` errors**

The PR is already merged and approved. I read the diff and found no blocking issues.

**What it does**

Errors from `'use cache'` functions were being recorded in the shared `workStore.reactServerErrorsByDigest` map, which exists so errors can be logged (#86500). The prerender path also used that map as `digestErrorsMap` to decide whether the render failed. So a page that caught a cached function's error still failed the build or on-demand generation.

The fix adds a separate `renderErrorsByDigest` map. It is filled only by the page's RSC error handler and is what prerender failure detection now uses. The shared map is still populated, so logging is unchanged.

**Code quality**
- The change is small and targeted. `createReactServerErrorHandler` gets an optional trailing parameter, and the existing call sites are unaffected.
- The comment in `app-render.tsx` explains why there are two maps.
- All 7 `digestErrorsMap` return sites are switched: the dynamic prerender, the static Fizz path, and the error-fallback variants. I saw no leftover site that still uses the old map.
- Call-site readability: `undefined` is passed positionally for `spanToRecordOn` so the new argument can follow it. A named options object would read better if this signature grows again. That is minor.

**Potential issues**
- **Missing digest guard.** `renderErrorsByDigest?.set(err.digest, err)` runs unconditionally, while the shared-map write sits behind a condition (the diff shows `reactServerErrors.set(err.digest, err)` inside an `if`). I only saw the diff context, so I can't tell whether `err.digest` is always defined at that point. The invocation of `onReactServerRenderError` nearby suggests it is.
- **Other consumers.** Any other code that reads `reactServerErrorsByDigest` to detect failures would still have the same bug. In this diff only `prerenderToStream` was changed. It's worth confirming that the dev/runtime render path (`renderToStream`) and the `'use cache'` resume or revalidate paths don't make the same failure decision from the shared map.
- **Error-fallback paths.** The fallback render uses `errorServerResult` with the same `renderErrorsByDigest` map. If the main render already recorded errors there, the fallback pass inherits them. That is probably intended, since the original error is what triggered the fallback. It does mean the map isn't reset between attempts.

**Performance**

The cost is one extra `Map` per prerender and one extra `set` per reported error. That is negligible.

**Security**

No new request headers are read, and there is no new input surface.

**Test coverage**
- The e2e suite covers both build-time (`static`, via `generateStaticParams`) and on-demand (`runtime`) prerendering.
- It asserts a 200 status, the fallback content, and, in start mode, an `x-nextjs-cache: HIT` on the second request. That confirms the page is cacheable, which is the actual regression.
- It uses `nextTestSetup` with `files: __dirname` and a real fixture directory, as the repo guidelines ask.
- Gaps:
  - There is no assertion that the cached function's error is still logged. That is the behavior the shared map preserves, and a test for it would guard against regressing #86500.
  - There is no dev-mode assertion. The test runs in dev too, but only checks content, which is fine.
  - Nothing exercises the PPR or `cacheComponents` error-fallback return paths with an error that is not caught. A test where the page does not catch the error and still fails the build would confirm detection still works.
- The test directory has no `README`. This is fine.

**Summary**

This is a clean, minimal fix with a good regression test. My suggestions, none of them blocking:
1. Add a negative test showing an uncaught `'use cache'` error still fails prerendering.
2. Assert that the caught error is still logged.
3. Confirm that no other code path decides failure from the shared `reactServerErrorsByDigest`.
