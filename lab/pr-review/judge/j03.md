# REVIEW A

**Review of PR #37046: fix(tls): distrust compromised eMudhra certificate authorities**

## Summary
The security change is sound. It moves to `rustls-webpki` 0.103.16, which rejects certificate paths containing the compromised eMudhra keys. It moves `webpki-roots` and `webpki-root-certs` to 1.0.10, which drops `emSign ECC Root CA - G3`. The 0.26.11 compatibility wrapper means reqwest and hyper-rustls also use the fixed root bundle. Raising the minimum to `rustls-webpki = "0.103.16"` instead of leaving it at `"0.103"` is the right call: downstream users of the `deno_*` crates can't resolve to a vulnerable verifier.

My main concern is collateral from the aws-lc-rs bump: the build now contains two copies of AWS-LC.

## Issues

### 1. Two versions of `aws-lc-sys` are now linked (main concern)
After the bump, `Cargo.lock` has both:
- `aws-lc-sys 0.46.0`, pulled in by `aws-lc-rs 1.18.2`, which rustls uses.
- `aws-lc-sys 0.40.0`, the workspace pin at `Cargo.toml:195`, used directly by `deno_crypto_provider` (`libs/crypto/ffi.rs`, `spki.rs`) and `deno_node_crypto` (`ext/node_crypto/cipher.rs`, `lib.rs`).

aws-lc-sys prefixes its symbols per version, so this links without errors. The costs:
- **Binary size and build time:** a second full libcrypto is compiled and linked. CI time and `deno` binary size will both grow noticeably.
- **Split global state:** the two libcrypto copies have separate RNG state, separate error queues and separate FIPS/self-test state. Today no raw pointers seem to cross between `aws_lc_rs` objects and `aws_lc_sys` calls; I grepped for this and found none. That is a hazard to keep in mind for later: an `EVP_PKEY*` from one copy passed into the other would be undefined behaviour.
- **Two copies to patch:** the 0.40 copy no longer gets AWS-LC fixes that land in later versions.

**Suggestion:** bump the workspace pin to `aws-lc-sys = { version = "0.46.0", features = ["prebuilt-nasm"] }` so there's a single copy. If the 0.40 to 0.46 FFI changes are too large for an urgent security PR, at least mention the duplication in the PR description and open a follow-up issue.

### 2. `pkg-config` 0.3.30 → 0.3.34 is a new build dependency
`aws-lc-sys 0.46.0` now depends on `pkg-config`. This is harmless, but it may change behaviour on systems where pkg-config finds a system AWS-LC or OpenSSL. Worth confirming that the release/static builds still use the vendored or prebuilt library.

### 3. `unstable` feature on aws-lc-rs looks unused now
`ext/crypto/Cargo.toml:21` still has `aws-lc-rs = { workspace = true, features = ["unstable"] }`. With the ML-DSA imports moved to `aws_lc_rs::signature`, I found no `unstable::` usages left in `ext/crypto`, `ext/node_crypto` or `libs`. Dropping the feature, here or in a follow-up, would stop new unstable APIs from slipping in unnoticed.

### 4. ML-DSA PKCS#8 export format
`to_pkcs8()` → `to_pkcs8v1()` is meant to keep the old output. The test at `tests/unit/webcrypto_mldsa_test.ts:176` only round-trips (export, then import into the same implementation). It would still pass if the encoding changed, for example seed-only vs. expanded key, or v1 vs. v2 (OneAsymmetricKey). Please add a byte-exact check of the exported PKCS#8 against a known vector for at least one parameter set, so the encoding is pinned for interop with Node, browsers and other WebCrypto implementations.

## Test coverage
- No regression test proves the eMudhra distrust works. A spec test that tries a TLS handshake to a chain containing the compromised keys would be ideal, but it needs fixture certificates that may be hard to get. Acceptable to rely on the upstream webpki tests here.
- A cheap check: assert in `tests/unit_node/tls_test.ts` that `tls.rootCertificates` no longer contains `emSign ECC Root CA - G3`. That guards against a future accidental downgrade of `webpki-root-certs`.
- `Deno.connectTls` and `fetch` use `webpki_roots::TLS_SERVER_ROOTS` (`ext/tls/lib.rs:266`, `cli/lib/args.rs:152`) and now get 1.0.10 directly. The API shape is the same in 1.x, so no code changes are needed there.

## Conventions and process
- This one PR bundles a security fix, a crypto-library minor bump, an API migration and a `deno_graph` bump. CLAUDE.md asks for minimal, focused PRs, but the bundling is justified: the webpki fix needs the newer aws-lc-rs, and `deno_graph` had to move to stop pulling the old roots. The description explains all of this well.
- Validation was a set of targeted `cargo check` and `clippy` runs plus CI. Because this changes the TLS stack, it would help to also run `cargo test unit::tls_test unit_node::tls_test unit::webcrypto_mldsa_test` explicitly before merge.

## Verdict
Approve in substance; the security fix is correct and urgent. Before or soon after merge, I'd recommend deduplicating `aws-lc-sys` (item 1) and pinning the ML-DSA PKCS#8 export bytes with a test (item 4).

# Review: PR #37046, fix(tls): distrust compromised eMudhra certificate authorities

**Overall:** This is a good, security-relevant dependency bump. The webpki and root-store changes are the right response to the eMudhra key compromise. The main thing to fix is that the lockfile now pulls in **two copies of `aws-lc-sys`** (0.40.0 and 0.46.0). There are also a couple of small follow-up cleanups.

## What looks good

- Pinning `rustls-webpki = "0.103.16"` closes the main hole. A bare `"0.103"` would have let a stale lockfile resolve to a version that still trusts the compromised keys.
- Moving `webpki-roots` and `webpki-root-certs` to 1.0.10 covers both root stores Deno uses:
  - `webpki_roots::TLS_SERVER_ROOTS` in `ext/tls/lib.rs:266` and `cli/lib/args.rs:152`
  - `webpki_root_certs::TLS_SERVER_ROOT_CERTS` in `ext/node/ops/tls.rs`, which backs `node:tls`
- Moving the transitive `webpki-roots 0.26` to 0.26.11, which is just a wrapper around 1.0.10, means reqwest and hyper-rustls also drop the bad root. That one is easy to miss.
- In the ML-DSA migration, choosing `to_pkcs8v1()` keeps the PKCS#8 export format unchanged. Without it, exported keys could silently change shape.

## Issues

### 1. Two `aws-lc-sys` versions get compiled and linked (medium)

`aws-lc-rs` 1.18.2 depends on `aws-lc-sys 0.46.0`. The workspace still pins `aws-lc-sys = { version = "0.40.0", features = ["prebuilt-nasm"] }`, and three crates call it directly with FFI: `deno_crypto`, `deno_node_crypto` and `deno_crypto_provider`.

What that means:
- **Build time and binary size:** AWS-LC is a large C/asm library, and it is now built twice and both copies end up in the `deno` binary. That's a real increase in release size and CI time.
- **Windows builds:** `prebuilt-nasm` is only turned on for 0.40.0. The 0.46.0 copy that `aws-lc-rs` pulls in doesn't get it, so x86_64 Windows builds may now need NASM installed. Please confirm Windows CI passed with no NASM on the runner.
- **Two separate C libraries in one process:** Symbol prefixing should prevent link conflicts. But TLS, WebCrypto (through `aws-lc-rs` / 0.46) and `node:crypto` FFI (through `aws-lc-sys` / 0.40) now run on different copies, each with its own global state, RNG and FIPS/CPU-capability init. Nothing in the tree passes raw pointers between the two today; I grepped `ext/node_crypto` and `libs/crypto`. Still, a future change that mixes them, such as handing an `aws-lc-rs` key's `EVP_PKEY` to an `aws_lc_sys::*` call, would be undefined behaviour.

**Suggestion:** Bump the workspace dependency to `aws-lc-sys = { version = "0.46.0", features = ["prebuilt-nasm"] }` so there's only one copy. If something in the 0.46 API blocks that, raise it in a follow-up and add a note to the PR description saying the duplication is intentional for now.

### 2. The `unstable` feature on `aws-lc-rs` is probably no longer needed (low)

`ext/crypto/Cargo.toml:21` still says `aws-lc-rs = { workspace = true, features = ["unstable"] }`. After this change, nothing under `ext/`, `libs/` or `cli/` imports from `aws_lc_rs::unstable::`. Dropping the feature would make the move to the stable API complete and stop anyone quietly depending on unstable APIs again. A follow-up PR is fine if you want to keep this one minimal.

### 3. The stated scope and the actual diff differ (nit)

The description says this bumps `deno_graph` to 0.111.1, and the diff does change `Cargo.toml`. The commit list, however, shows the `deno_graph` bump and the ML-DSA migration as separate commits on `main`. Because the PR squash-merges, that doesn't matter much. It would still help to say clearly in the description that the AWS-LC upgrade is required by `rustls-webpki` 0.103.16, so reviewers don't read it as an unrelated change.

## Test coverage

- No test checks that the compromised CA is actually rejected. Writing one is hard because it needs the real compromised certificates, and upstream webpki already tests this (rustls/webpki#546). Accepting that is reasonable, but please say in the PR that the coverage comes from upstream.
- On the ML-DSA change: `tests/unit/webcrypto_mldsa_test.ts:176` only round-trips PKCS#8 (export, import, sign, verify). It would still pass if the export format changed, say from v1 to v2 with the public key included, because the import side accepts both. Since `to_pkcs8v1()` exists precisely to keep the format stable, a small known-answer test would lock it in. For example, export a key made from a fixed seed and compare it to the expected v1 DER, or at least check the version byte.

## Security

- The fix works: both root stores and the path verifier are updated.
- Deno doesn't set `--unsafely-ignore-certificate-errors` or a custom CA store by default, so this applies to everyone right away. Users who pass `DENO_CERT` or `--cert`, or who use the system store through `deno_native_certs`, still depend on their own trust store. That's worth one line in the release notes.
