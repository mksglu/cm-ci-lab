# REVIEW A

**Review of PR 23017: Preserve inline comments when updating an existing dependency group**

The PR is already merged. I read the diff only and didn't build it or run the tests.

**Summary:** The fix is small and targeted. `add_dependency_group` now formats the inline `dependency-groups` table only when it inserts a new group key. That keeps the comments around existing keys intact when you add to an existing group. The second function's early return when the group already exists also removes a redundant format pass and simplifies the control flow.

**Code quality**
- The `new_group` flag and the early-return refactor are clear and match the repo's style.
- The new comment explains the rationale ("Only inserting a key changes the table layout…"). It doesn't refer to past behavior, as AGENTS.md asks.
- The nested `if new_group { … if let … }` could be a let chain, which AGENTS.md prefers. Here the `if new_group` also guards `sort_values`, so the nesting is defensible.
- The two functions now carry near-identical "sort if sorted, then fmt inline table" logic. A shared helper could avoid the duplication, but that isn't necessary.

**Potential bugs**
- The snapshot shows ugly output. `dev = [\n    "ok==1.0.0",\n], # Local development` is indented inconsistently, because the array is multi-line while its surroundings keep their original formatting. The comments survive, which is the goal. Still, the test now locks in this odd formatting, so a later formatting improvement would need a snapshot update. It could be worth a follow-up to format the edited array itself.
- The updated array is no longer re-formatted via the table `fmt()`. Other paths that call `add_dependency` on inline tables, such as remove and update flows or `[tool.uv] dev-dependencies`, may behave differently. I didn't check them.
- Behavior change to confirm: when a group is new and the table is inline, `fmt()` still drops comments between keys. The old comment claimed this is unavoidable. That's acceptable, but it is still a gap: adding a *new* group to an inline table with comments still loses them.

**Performance and security**
- There are no concerns. The change removes a redundant formatting call.

**Test coverage**
- The new test `add_dev_preserves_inline_group_comments` covers the main scenario. It follows the style of nearby tests, uses `uv_snapshot!` and `assert_snapshot!`, and uses `--frozen` to avoid resolution.
- Missing cases:
  - A test where a new group is inserted into an inline table. This would document that `fmt()` still runs and what happens to comments.
  - A test for the second function, the early-return path that ensures a group exists. This is probably reached via `uv add --group` or the `uv init` flow.
  - A sorted-versus-unsorted case, to confirm `sort_values` is not run when the group already exists.
- The test is placed between doc-commented tests and has no doc comment. AGENTS.md suggests explaining a non-obvious regression scenario in one.

**Verdict:** This is a good, minimal fix. Adding tests for the new-group path and a doc comment on the test would be useful follow-ups.
