# REVIEW A

## Review of PR #38034: View Transitions error classification for Chrome 153

Chrome 153 changed its `InvalidStateError` messages for view transitions, so React's exact-string match stopped catching them. The PR responds with an explicit list of messages that can't be acted on, instead of a broad `startsWith` match. Overall this is a careful, well-reasoned change. Below are a few suggestions, mostly about tests.

### Code quality and correctness

- **Switching to an allowlist was the right call.** Matching `startsWith('Transition was aborted because of invalid state')` would also have hidden the Chrome 153 reasons that do matter: `Snapshot capture failed`, `Animation start failed`, and `Unsupported layout or style`. The `switch` on `error.message` is easier to read than the old `||` chain, and grouping by browser with trailing comments makes the list easy to maintain.
- **Behavior in Chrome 152 and earlier is unchanged.** The bare `'Transition was aborted because of invalid state'` is still suppressed, so duplicate-name errors in older Chrome stay hidden, as before. That's acceptable, and the updated comment explains the tradeoff.
- **The `'Transition was aborted because of invalid state.'` case (with a period and no reason) needs a note.** It's suppressed, but it isn't clear when Chrome 153+ emits it. If it means "no specific reason recorded", it would help to say so in the comment, or link the Blink enum or source line. That way a future reader can tell it was deliberate and not a typo variant of the Chrome 152 string.
- **The new DEV hint says more than it can know.** `Snapshot capture failed` and `Animation start failed` can probably come from causes other than duplicate names. Examples include the capture failing on an element that is too large or fragmented, or the element being removed during capture. "This usually means…" hedges this, and `cause` keeps the original message, so this is minor. A softer phrasing would be more accurate, for example "One common cause is two elements having the same `view-transition-name`…".
- **The new DEV error matches existing conventions.** It follows the same pattern as the `TimeoutError` and `AbortError` branches (`__DEV__`-only, `{cause: error}`, and the `prod-error-codes` eslint suppression). In production it falls through to `break` and returns the original error, which is correct.
- **The `{ ... }` block around the last case isn't needed.** Nothing is declared inside it. It does match the style of the outer cases, so this is purely a nit.

### Potential issues

- **The string list will drift as browsers change.** Every vendor message change will need another PR like this one. That is inherent to the approach and probably still better than over-suppressing. Consider adding a link to the Chromium enum or commit (it's in the PR description) as a code comment next to the Chrome 153 cases, so the source is easy to find.
- **The Firefox strings need checking.** `'Skipped ViewTransition due to document being hidden'` and `'Skipped view transition due to viewport resize'` differ in capitalization ("ViewTransition" vs "view transition"). If this mirrors Gecko's actual messages, that's fine. A reference to the Gecko source would protect against a typo silently making these dead cases.

### Test coverage

- **The tests are good.** They cover the three main paths: suppressed, passed through unchanged, and DEV hint vs production pass-through. They use the existing `afterEach` in that `describe` block, which restores or deletes `document.startViewTransition`, so the mock doesn't leak.
- **Only one suppressed message is tested.** A small `it.each` (or a loop) over every suppressed string would catch typos and regressions in the list, and it costs almost nothing. Testing the Chrome 152 string would also confirm backward compatibility.
- **`Animation start failed` has no test.** Adding it to the same `it.each` for the DEV hint would be easy.
- **The mock always resolves `finished`.** That matches the spec for a skipped transition whose update callback succeeded, so this is fine. One option is a test where the update itself throws, but that's out of scope here.

### Performance and security

- **Performance:** no concerns. This is a string `switch` on an error path.
- **Security:** no concerns. Error messages are only classified and wrapped, never interpolated into the DOM.

### Summary

I'd approve this. The suggestions are optional: test every suppressed string (plus `Animation start failed`), add source links for the browser message strings, and possibly soften the wording of the duplicate-name hint.

# REVIEW B

## PR review: View Transitions error classification for Chrome 153 (#38034)

This is a small, focused fix and I'd approve it. It moves from a generic message to known messages, keeps exact matching instead of `.startsWith()`, and adds a DEV-only hint with `{cause: error}`. That matches how the `TimeoutError` and `AbortError` branches in `customizeViewTransitionError` already work. I found no bugs, performance issues or security concerns; the points below are minor.

### Code quality

1. **The Chrome ≤152 comment sits above the whole case list.** At `ReactFiberConfigDOM.js:2130-2133`, the comment "we hide all of them and hopefully it surfaces in another browser" is placed above every suppressed case. It reads as if it explains the Firefox and Safari cases too, but it only applies to the reason-less Chrome strings. Suggested changes:
   - Move it directly above the first two `case` labels.
   - Note that the trailing-period variant (`'...invalid state.'`) is also deliberately suppressed because it carries no reason. That case is easy to mistake for a typo-tolerance hack.

2. **The `switch` is a good choice.** It's clearer than the old `||` chain, and the per-browser trailing comments make later updates easy. Since everything here is exact-match on strings browsers can change, it may be worth adding one line saying unknown messages fall through and get reported on purpose. Then the next person who sees a new Chrome reason surface won't "fix" it with a prefix match.

3. **The DEV message may overstate the cause.** "Snapshot capture failed" and "Animation start failed" come from Blink's name-verification step. In practice that is almost always duplicate names, but the capture path can also fail for other reasons. The message already hedges with "usually" and points to the console, which is reasonable. Consider wording like "This is usually caused by two elements having the same `view-transition-name`…" to make the uncertainty a little more explicit.

### Behaviour notes (not blocking)

- **Older Chrome still hides everything.** Before 153, duplicate-name errors stay hidden because Chrome only sent the generic message. The comment says so, which is the right trade-off.
- **The gesture path changes too.** `customizeViewTransitionError(error, true)` is also called from the gesture path (`ReactFiberConfigDOM.js:2827`), so the new classification applies there as well. That looks right, but the tests only cover the regular transition path.

### Test coverage

The new `skipped transitions` block is clean:
- The helper is reused across tests.
- `document.startViewTransition` is restored by the existing `afterEach` (`ReactDOMViewTransition-test.js:240-247`), so the mock doesn't leak.
- Both the DEV and prod branches are checked.

Gaps you could cheaply close by turning the tests into `it.each` tables:
- Only one suppressed string (`Document hidden`) is tested. A table of every suppressed message (Chrome no-reason, Chrome with trailing period, Viewport size changed, Firefox ×2, Safari ×3) would catch typos in those long literals. Typos are the most likely regression here, since a typo silently turns into "report this error".
- `'Animation start failed'` isn't tested; only `'Snapshot capture failed'` is.
- In the DEV hint test, `errors[0].message` could also be checked against the full new message, or at least for `Check the console`.
- Optionally, add one gesture-path test so the shared classification is covered for `ignoreAbort = true`.

### Style

- The `eslint-disable-next-line react-internal/prod-error-codes` plus DEV-only `new Error` follows the existing convention in this function.
- Prettier leaves the long `case` string lines alone, so that's fine.
