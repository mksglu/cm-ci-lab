# REVIEW A

**Review of PR #38034: View Transitions: update error message classification for Chrome 153**

This PR is already merged and approved. Overall it's a solid change.

**What it does**
- It replaces the `if` chain of `||` comparisons with a `switch` on `error.message`. The `switch` suppresses the unactionable `InvalidStateError`s (document hidden, viewport resized, and the reason-less message) for Chrome 152 and earlier, Chrome 153+, Firefox and Safari.
- It deliberately avoids `startsWith`, so unknown reasons such as `Unsupported layout or style` still reach `onRecoverableError`.
- In DEV it wraps `Snapshot capture failed` and `Animation start failed` in a more helpful error that points to duplicate `view-transition-name`s. The original error is kept as `cause`.

**Code quality**
- The `switch` is easier to read and extend than the long `||` chain, and the per-browser comments are useful.
- The inner `switch` has no `default`, so it falls through to the outer `break`. That is fine, but a short comment saying unknown messages are intentionally reported would help future maintainers.
- The `{cause: error}` option on `Error` is fine for the supported targets. Check that the Flow libdefs accept the two-argument constructor. CI presumably did.
- `// eslint-disable-next-line react-internal/prod-error-codes` is appropriate for a DEV-only message. Wrapping it in `__DEV__` keeps it out of the prod bundles and the error-code map.

**Potential issues**
- Matching exact message strings is brittle. Any later browser wording change will start surfacing noise again, as happened here. That is a conscious tradeoff, and the PR description explains it.
- The claim that `Duplicate view-transition-name` never surfaces is based on the author's investigation. The hint text says "usually", which is appropriately hedged. The `Snapshot capture failed` and `Animation start failed` reasons could also have other causes, but the hint says "usually" and the original error is preserved as `cause`, so little is lost.
- In prod the Snapshot and Animation errors are reported with the raw browser message. That is consistent with the rest of the file.

**Performance and security**
- Neither is a concern. It is a string `switch` on a rare error path, and there is no new input handling.

**Test coverage**
- The tests cover three cases: a suppressed message, an unknown message that is reported unchanged, and the DEV hint with `cause` (with a prod branch).
- Only one suppressed message (`Document hidden`) is exercised. A parameterized test over the full suppressed list would catch typos in the string literals, such as a missing trailing period. That is the likeliest regression in this kind of code.
- The Firefox and Safari strings are untested, though they are simple literals.
- The `@gate enableViewTransition` pragmas are used correctly, and the `DOMException` mock is a faithful way to simulate the browser.

**Verdict:** Looks good. The suggestions are minor: a comment on the intentional fall-through, and broader test coverage of the suppressed strings.

# REVIEW B

## Review of PR #38034: View Transitions error message classification for Chrome 153

(The PR is already merged and approved. This review is for reference.)

### Summary
The PR changes `customizeViewTransitionError` in `ReactFiberConfigDOM.js`. It uses an explicit allowlist of exact messages, now covering Chrome 153+, Firefox and Safari. These are the unactionable `InvalidStateError` cases: document hidden, viewport resized, and the reason-less message. A DEV-only hint is added for `Snapshot capture failed` and `Animation start failed`. Three tests are added.

### Code quality
- **Exact-match allowlist.** Not using `startsWith` is the right call. It keeps real problems such as `Unsupported layout or style` visible. The `switch` is more readable than the old chained `||`.
- **Comments.** The per-browser annotations are helpful. The comment on the first case group is slightly confusing. It says "Chrome 152 and earlier" but also covers the Firefox and Safari entries below it. Minor.
- **`{cause: error}`.** This preserves the original error. Confirm that the `Error` constructor's `cause` option is acceptable under React's supported-browser and Flow settings. The tests assert `.cause`, so it works in the test environment.
- **Lint suppression.** `eslint-disable-next-line react-internal/prod-error-codes` is appropriate because the message is DEV-only. The `break` for the non-DEV path correctly falls through to the default error handling.

### Potential issues
- **Brittle string matching.** This is inherent to the approach, and the PR acknowledges it. Browser messages will change again, which is what caused this PR. An unmatched message fails safe, because it surfaces as a recoverable error rather than being swallowed. Linking the Chromium and Firefox sources in comments, as the PR description does for Chromium, would make future updates easier.
- **Overly specific hint text.** `Snapshot capture failed` and `Animation start failed` are described as "usually" caused by duplicate `view-transition-name`s. The PR description says these are how duplicate names actually surface, so the hint is reasonable. The "usually" wording is appropriately hedged.
- **Trailing-period variant.** The case `...invalid state.` with a trailing period is presumably defensive. A short comment on why it exists would help.
- **Firefox and Safari strings.** I couldn't verify these against the browser sources here. Check the exact strings, including capitalization and punctuation, since a mismatch would silently reintroduce noise.

### Performance
There is no concern. The `switch` runs only on the error path.

### Security
There is no concern. The change only classifies error messages, and nothing is rendered or evaluated from them.

### Test coverage
- **Covered.** Document hidden is suppressed. An unknown reason is still reported. The DEV hint is added with `cause` preserved. The non-DEV path is also handled in the same test.
- **Gaps.**
  - Only one of the suppressed messages is tested, and none of the Firefox or Safari ones are. A `test.each` over the full allowlist would guard against typos in these long strings.
  - `Viewport size changed` and `Animation start failed` have no test.
  - The `InvalidStateError` from `finished` or `updateCallbackDone` paths isn't exercised. This is probably fine if the same function handles them.

### Verdict
This is a solid and well-scoped fix. The main suggestion is a table-driven test over every allowlisted and hinted message, to protect against typos in the string literals.
