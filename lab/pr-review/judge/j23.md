# REVIEW A

## Review of PR #100956: Fix prerendering of caught `'use cache'` errors

I read the diff and grepped the surrounding code in `app-render.tsx`. I didn't run the tests.

### Summary
`reactServerErrorsByDigest` on the work store is also written when a `'use cache'` function throws, even if the page catches the error. That is what #86500 needs for logging. Prerender failure detection reused the same map, so a caught cached error could fail the build or on-demand generation (#100829). The PR gives `prerenderToStream` its own map, `renderErrorsByDigest`. Only the RSC error handler of that prerender fills it, and it is what the prerender results return as `digestErrorsMap`. The shared map still feeds logging and error recovery.

### Assessment
The approach is sound and the change is small and well scoped.

- All 7 `digestErrorsMap` returns inside `prerenderToStream` now use `renderErrorsByDigest`. That covers the success, dynamic-prerender, and error-fallback paths, and I found no missed return site.
- `digestErrorsMap: new Map()` at ~line 10097 is unchanged, and it was already empty.
- The remaining uses of the shared map (`.get(digest) ?? err` at ~10418, `.has(digest) ? undefined : err` at ~10520 and ~10834) are about recovering or classifying thrown errors. Keeping the shared map there is correct, and it preserves the #86500 behavior.
- The consumer at ~line 2749 reads `response.digestErrorsMap.values().next()` to pick the first error. It now sees only errors the RSC renderer reported, which is the intent.
- The new parameter is optional and uses `?.set`, so the other three `createReactServerErrorHandler` callers (lines ~830–1486, 3703, 8695) are unaffected.

### Suggestions

1. **Parameter ordering.** The call site passes a literal `undefined` for `spanToRecordOn` to reach the new trailing parameter. That is fragile and hard to read. Consider an options object, or add a short comment at the call site. This is minor.
2. **Placement of the `set`.** `renderErrorsByDigest?.set(...)` runs after the early-return branches in the handler (I only saw part of the file). Confirm that errors that should fail the prerender, such as dynamic-usage or postpone errors, are handled the same way as before. Previously the shared map was written under the same conditions, but the diff shows `reactServerErrors.set` inside a conditional and the new `set` unconditionally. If the old `set` was gated, for example on `!silenceLog` or on the error type, then the new map now records more than the old one did. Please verify that the two maps match for errors that really fail the render. A comment on the new map would help.
3. **Naming.** `renderErrorsByDigest` and `reactServerErrorsByDigest` look alike. A name such as `prerenderFailureErrorsByDigest` would make the difference clearer.

### Tests
The test covers a caught cached-function error in both a `generateStaticParams` route (build-time prerender) and a runtime route (on-demand generation). It also asserts the fallback is cacheable (`x-nextjs-cache: HIT`) under `next start`. It follows the repo conventions: a real fixture directory, `nextTestSetup`, and no `check()` or `setTimeout`.

Gaps:
- The test only asserts the page content and the `HIT` header. A failed prerender would show up as a build failure under `next start`. Under `next dev` the test only checks a 200 response, which was probably already passing, so it adds little there. That is acceptable.
- There is no case for an uncaught `'use cache'` error, to check it still fails the build and is logged. A regression where the new map misses real failures would otherwise go unnoticed. A small second fixture or an existing test would cover this.
- Consider a PPR or `cacheComponents` case where the error is thrown inside a `<Suspense>` boundary. That would exercise the dynamic-prerender return path (~10143, 10707).
- The `runtime` route has no `generateStaticParams`, but under `cacheComponents` it may be prerendered anyway. If it is not prerendered at build time, the "runtime" case is on-demand, as intended.

### Other
- No security concerns. No headers are read and no new input surfaces are added.
- Performance impact is negligible: one extra `Map` per prerender and one `set` per reported error.
- The PR description is clear. It follows the AGENTS.md rule for branch PRs, and there are no Claude footers.

Overall the PR looks good to merge once point 2 is confirmed. The uncaught-error test would make it stronger.

# REVIEW B

**Review of PR #100956: Fix prerendering of caught `'use cache'` errors** (already merged and approved)

**Summary:** The fix is correct and well-scoped. `reactServerErrorsByDigest` is shared with the work store and is also populated by errors from `'use cache'` functions. Those errors are recorded so they can be logged, even when the page catches them. Prerender failure detection read that same map, so a caught error still failed the build. The PR adds a render-local `renderErrorsByDigest` map. The RSC error handler fills it, and every `digestErrorsMap` return in `prerenderToStream` now uses it. The shared map keeps its logging role from #86500.

**Code quality**
- The change is minimal, and the comment explains why there are two maps.
- Adding `renderErrorsByDigest` as a trailing optional parameter keeps other callers working. It does force `undefined` to be passed for `spanToRecordOn`. An options object would be cleaner, but that isn't worth a refactor here.
- I checked that the diff swaps all six `digestErrorsMap: reactServerErrorsByDigest` returns, in both the PPR/dynamic and the Fizz paths and in both the normal and error-render branches. A missed branch would reintroduce the bug, so I would grep for leftover uses to confirm.
- `renderErrorsByDigest?.set(...)` runs after the digest is guaranteed to exist. I couldn't see whether the early-return paths, such as the closed-response and bailout-error checks, sit before it. Errors that are intentionally ignored there stay ignored for failure detection, which is the right behavior.

**Potential issues**
- Is the `'use cache'` error is still recorded in `reactServerErrorsByDigest` and reaches the RSC handler only when it propagates to the render? That seems to be the case. If a cache function's error is thrown during the cache fill and then rethrown to the page, the page catches it. The handler would then not fire unless React reports it. The new test covers this.
- The cache-function error is still logged for caught errors, as before. This PR doesn't change that, and it may be worth a follow-up if it is noisy.

**Performance:** One extra `Map` per prerender, and one extra `set` per reported error. This is negligible.

**Security:** There are no new header reads or external inputs.

**Tests**
- The new e2e suite follows the repo conventions. It uses `nextTestSetup` with a real fixture directory and was generated in the expected layout.
- It covers build-time prerendering (`/static` through `generateStaticParams`) and on-demand generation (`/runtime`). It also asserts a cache `HIT` in start mode, so a non-cacheable fallback would be caught.
- Gaps:
  - Only `cacheComponents: true` is exercised. A non-PPR path would be worth checking, since the `reportErrors` and `isRoutePPREnabled` branches differ.
  - The test doesn't assert that no error is logged or that the build output is clean. It also doesn't cover errors from a non-cache component that is caught by an error boundary or `<Suspense>`. Those probably already worked.
  - `isNextStart` gating means dev mode only checks the 200 status and the body. That is acceptable.

**Verdict:** LGTM. The fix is targeted, the regression test is meaningful, and the risk is low. My only suggestions are to confirm no remaining `reactServerErrorsByDigest` uses feed failure detection, and to optionally move to an options object for the handler's trailing parameters.
