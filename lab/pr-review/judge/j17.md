# REVIEW A

**Review of PR #36944 (merged): `fix(ext/node): support assert message functions and format arguments`**

The PR moves message handling into a shared `innerFail()` and adds printf-style and function messages. The design is reasonable. It also re-enables `parallel/test-assert.js` in the node_compat config, which is the right test to enable. I found a few issues, mostly cleanup. I didn't run the code or check the other callers.

**Cleanup**
- `internalMatch` in `assert.ts` leaves a lot of commented-out code: the old `ErrorPrototype` check, `const err = new AssertionError`, `err.generatedMessage`, `throw err`, and the old `message ||=`. Delete it.
- After this change, `ObjectPrototypeIsPrototypeOf`, `ErrorPrototype` and possibly `AssertionError` may be unused in `assert.ts`. Check this and run `tools/lint.js --js`.
- `utils.ts` has a stray blank line between the `MessageTuple` doc comment and the type. The `getErrorSourceExpression` destructuring was also reformatted for no reason, which is a drive-by change.
- The doc comment says "print like substitutions". It should say "printf-style".

**Possible bugs and edge cases**
1. **`internalMatch` empty-string message.**
   - `message[0] ||= ...` replaces any falsy first argument, including `""` and `0`, with the default message.
   - `generatedMessage` is `message.length === 0`, so it ends up `false` even though a default message was generated.
   - Node only treats `undefined` or "no message" as default here.
   - The code also sets `message[0]` on the caller's rest array. That's harmless, but a bit hacky.
2. **`internalMatch` and printf arguments.**
   - When `message` is `[]`, `message[0] ||= ...` makes it `[defaultString]`, which `innerFail` handles correctly.
   - When the user passes `(string, regexp, fn)`, `message[0]` is truthy and stays a function, which is fine.
   - When the user passes `(string, regexp, "")`, it hits the empty-string case from item 1.
   - Add tests for `match` with a message function and with printf arguments.
3. **`innerOk` with a null message.**
   - `args[1] == null` ignores trailing arguments after a `null` or `undefined` message, for example `assert(false, undefined, "x")`.
   - This probably matches Node, but I haven't confirmed it.
4. **`innerOk` with a non-string, non-function message.**
   - A message such as `assert(false, 5)` goes through `ArrayPrototypeSlice` into `innerFail`, which throws `ERR_INVALID_ARG_TYPE`.
   - Node does the same, so this is probably correct. A test would be worthwhile.
5. **Message function errors.** `catch {}` swallows every error from a message function. That matches the stated intent, so it's acceptable. Say so in a comment.
6. **`compareExceptionKey`, `expectsError` and `expectsNoError`.**
   - These wrap generated strings as `[message]`, so they bypass `format`.
   - A `%` in generated text is safe because a single-element tuple is not formatted.
   - If `message` is already a user-supplied error or function in `compareExceptionKey`, it is now wrapped as `[message]`. That is correct, but it depends on the type of `message` at that call site.
7. **Remaining assertion functions.**
   - `ok`, `equal` and the other comparison functions use `...message` and pass it through.
   - Check that `fail`, `ifError`, `throws`, `rejects` and `partialDeepStrictEqual` are consistent. `partialDeepStrictEqual` was changed, but I didn't see the others in the diff.
   - The `arguments.length < 2` checks still work with rest parameters.

**Performance**
- Rest parameters add an array allocation per call, but only on the assertion path. The cost is negligible.
- `innerOk` spreads `args` through `SafeArrayIterator` into the rest parameter on every call, which is wasteful, though minor. It could take the args array directly.

**Security**
No concerns.

**Test coverage**
- The only coverage is the upstream Node test `test-assert.js`. That covers the behavior well.
- A Deno-side spec or unit test would help for the cases above (the `internalMatch` empty-string and `generatedMessage` case, and `assert.ok` with printf arguments), but the compat test is acceptable here.
- The PR description says the test was run locally. Confirm that CI ran the node_compat suite on all platforms.

**Verdict:** Functionally sound. The commented-out code should be removed, and the empty-string handling in `internalMatch` should be fixed or confirmed against Node. That fix and a lint run can go in a small follow-up PR.

# REVIEW B

**Review of #36944: assert message functions and printf-style formatting**

This PR is already merged, and I reviewed it from the diff alone. I didn't build it or run any tests. Moving message handling into a shared `innerFail` is the right design, and the tuple-based `MessageTuple` type is clear. Validation matches Node (ambiguous trailing args, invalid type). Enabling `parallel/test-assert.js` is a good sign.

**Possible bugs**
1. **`compareExceptionKey` may pass `[undefined]`.** It now passes `message: [message]`. If `message` can be `undefined` (the user passed no message to `assert.throws(fn, {…})`), `innerFail` sees `typeof message[0] === "undefined"`. That falls into the final branch and throws `ERR_INVALID_ARG_TYPE`. It should be `message === undefined ? [] : [message]`, as `innerOk` already does for `source`. Please check whether the call sites guard against this. If they don't, a missing message turns the real assertion failure into a type error. The same pattern applies to any other site that wraps a possibly-undefined message.
2. **`internalMatch` has regressions in `generatedMessage`.**
   - It now uses `message.length === 0`. Before, it used `!message`. So `assert.match(s, re, undefined)` or `assert.match(s, re, "")` now reports `generatedMessage: false`, even though the default text is used.
   - `message[0] ||= …` mutates the caller's rest array. With `["", extraArg]` it also swaps the default text in while still treating `extraArg` as a printf arg.
   - A cleaner way is to build `messageArgs = message.length === 0 || message[0] == null ? [defaultMsg] : message`, and compute `generatedMessage` from that.
3. **Throwing message functions are swallowed silently.** This matches the stated Node behavior, so it's fine. The `catch {}` is also fine.

**Code quality**
- `internalMatch` has several commented-out lines left behind (`// if (ObjectPrototypeIsPrototypeOf…`, `// const err = …`, `// err.generatedMessage…`). Delete them.
- After the refactor, `ObjectPrototypeIsPrototypeOf`, `ErrorPrototype` and possibly `AssertionError` in `assert.ts` may be unused. Check for dead imports and destructured primordials, and run `tools/lint.js --js`.
- The `MessageTuple` doc comment says "print like substitutions". It should say "printf-style substitutions".
- The `getErrorSourceExpression` import was reformatted for no reason. That's a drive-by change, which CLAUDE.md discourages.

**Performance**
- Every call to `equal`, `strictEqual` and the like now allocates a rest array, even when it's empty. That's negligible next to the cost of a failure, but it's on a hot path in test suites. Passing the message only on failure would avoid the allocation. I wouldn't hold the PR for this.

**Security**
- Nothing notable. User-supplied message functions run only on failure, and exceptions from them are contained.

**Tests**
- Coverage comes only from the upstream Node test `test-assert.js`. There's no spec or unit test in `tests/specs` or `tests/unit_node` for the new behavior. I'd add a small one covering:
  - a message function that returns a string, throws, and returns a non-string
  - `%s`/`%d` formatting
  - trailing args after an `Error` or function (`ERR_AMBIGUOUS_ARGUMENT`)
  - invalid message types
  - `assert.throws` with an object matcher and no message (finding 1)
  - `generatedMessage` for `match` with `undefined` or `""` (finding 2)

**Verdict:** The approach is sound. I'd follow up on findings 1 and 2 and the dead commented code, and add a focused test.
