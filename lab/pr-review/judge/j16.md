# Review of PR #345283: run `--runList` selections in parallel workers

The PR is already merged. I read the diff and the description. I didn't run the code or the tests.

**Overall:** This is a sound change. The worker count heuristic is clear and documented, and it comes with measurements. The runner logic is also factored well. Moving the Electron file discovery into a shared `testFiles.ts` and finding node's modules once through `findTestModules()` removes duplicated glob code. The "Running the N test files…" message is now printed once, not once per worker.

## Possible issues

1. **`getWorkerCountForFiles` logging and edge cases** (`test/unit/parallel.ts`)
   - It always logs "Using X instead of Y worker processes" when `forFiles < count`. That includes a run of 1 file and a run with `--workers 2` and 100 files. Under `--workers 2` the message says nothing useful, because 2 is already the floor.
   - With 0 matching files, the function returns `max(1, min(…, 0, …))`, which is 1. Then the Electron path passes `run: files` with an empty array. Please check that an empty `run` list doesn't make the renderer fall back to loading all tests. This is the likeliest regression, because an empty list in `args.run` is falsy-adjacent. In Electron the check is `args.run`, and an empty array is truthy in JS. Even so, the renderer's handling of `opts.run` should be confirmed.

2. **Electron `listedTestFiles` handling** (`test/unit/electron/index.js`)
   - `listedTestFiles?.catch(() => { })` suppresses the unhandled-rejection warning. The error is then reported at `await listedTestFiles` in the ready handler, which is correct. This depends on the await happening on every path. It's easy to break if code is added before that await later, so a short comment saying so would help.
   - When `parallelWorkers === 1`, `firstRunArgs = { ...args, run: files }`. This changes the semantics for reruns. The files in `args.run` are paths relative to `out`, and I did not check that `run` accepts that form. Because `run` is documented as taking source paths, the format needs checking. The PR says "as if they were passed with --run", so the author probably checked, but a test would pin it down.
   - The glob runs twice in a worker-less single-window run. It runs once in main and the renderer skips it, so that case is fine. In a multi-worker run each renderer still globs again (the `findTestFiles` call in `loadTestModules`). That is cheap, but it duplicates the main process's work.

3. **Node runner** (`test/unit/node/index.js`)
   - `findTestModules()` uses `args.worker` for the log guard. Elsewhere the code uses `opts.workerDir` (Electron) and `worker` (browser). Confirm that `args.worker` is the right flag for node worker processes.
   - When `count === 1`, it calls `main()` after `findTestModules()` has already resolved. That is fine, because the result is memoized. If `findTestModules` rejects inside `main()` through `.then(loadModules)`, the error goes to `cb`. The two error paths behave differently, though: the process exits with code 1 in one and goes through mocha's callback in the other.
   - The `else if (!runList)` / `else` structure with a top-level `.then` is a bit hard to read. Pulling it into a named function would help.

4. **Browser runner** (`test/unit/browser/index.js`)
   - Multiple browsers run one at a time whenever `workersApply` is true, "also when a single listed file … leaves one worker." That is consistent with #344448. It does mean `--browser a --browser b --workers 4 --runList small.txt` loses cross-browser parallelism for tiny lists, where the parallelism would have helped. The PR describes this as a deliberate trade-off. I'd suggest picking the strategy from the final `workers` value instead of `workersApply`.
   - `runTestsWithReruns(..., 1)` in the parallel-browsers branch is a magic number. A comment or a named constant would be clearer.

## Heuristic and performance
- The 75-files-per-worker threshold and the minimum of 2 workers are backed by the author's measurements. They are hard-coded, though, and are tuned to the CI runners (4 CPUs). They are untested on machines with more cores. `FILES_PER_WORKER` could be overridable, or at least noted as CI-tuned.

### Summary
The change lets `--workers` apply together with `--runList` in the Electron, node.js and browser unit-test runners. `getWorkerCountForFiles` in `parallel.ts` chooses the worker count: one per 75 files, at least 2, and at most `--workers` or the number of files. The description's measurements show a real speedup at 300 files and no gain at 10 files, and the 2-worker floor is justified with data.

### What looks good
- **Worker re-invocation is safe.** `removeArgument(…, 'workers')` makes `workerCount` 1 in a worker. Node and Electron then take the non-parallel path. The browser runner gets `workersApply` false and `workers = 1`.
- **The "Running the N test files…" message prints once.** Node uses `!args.worker`, Electron uses `!opts.workerDir`, and the browser uses `!worker`.
- **Test-file discovery is shared.** `findTestFiles` in `electron/testFiles.ts` is used by both the main process and the renderer, so they can't drift apart. The main process starts the glob before `app.ready`, and a rejected promise is caught early, so there's no unhandled rejection.
- **The single-worker Electron path avoids a second glob.** It passes `run: files` into the window.
- **`findTestModules` in node memoizes the promise.** The same file list is reused for the worker-count decision and for `main()`.
- **Multiple browsers run one at a time when workers apply.** This follows #344448, and the browsers run in parallel only when workers don't apply.
- **Docs are updated** in the skill file, the README and each runner's `--help`.

### Issues and suggestions
1. **Test coverage is the main gap.** `getWorkerCountForFiles` is pure and easy to unit test. Its edge cases are:
   - 0 files returns 1
   - 1 file returns 1
   - 2–149 files returns 2 (capped by `count`)
   - 300 files with `count` 4 returns 4

   `parallel.ts` has no tests in this PR. The description admits CI doesn't exercise `--runList` with `--workers`, because ripple runs everything for changes under `test/unit/**`. I also don't see CI covering reruns, `.only` or `--tfs` with a run list. Those were checked by hand, and a regression there would only show up on PR runs that select a subset.
2. **Electron fallback to one worker is untested with `--rerun-failed-files`.** When `parallelWorkers === 1`, `firstRunArgs = { ...args, run: files }`. Reruns then derive their plan from `runArgs` (`let runArgs = firstRunArgs`), so the setup is right in principle. That interaction is subtle, though. A short comment, or a test that a rerun still targets the same files, would help.
3. **Electron path semantics.** `run: files` goes through the `opts.run` branch, which strips `src/` and `.js`/`.ts`. Because `files` are already `out`-relative `.js` paths, this works. The two code paths are now coupled by convention, and a comment saying so would help. An empty `files` array is also truthy, so it loads zero modules. That behaves correctly, but only by accident.
4. **The console message in `getWorkerCountForFiles` is noisy.** It prints whenever `forFiles < count`, which is nearly always for short lists. `parallel.ts` is also a shared helper, so logging there makes it hard to reuse. 5. **The 75-files-per-worker constant is machine-dependent.** It was tuned on an M5 Pro with 18 CPUs and 48 GB. CI macOS and Windows runners are smaller and slower to start processes. The data supports the direction, but a note on how to re-tune it, or a pointer to the PR-run timing data, would help the next person.
6. **Browser runner:** `runTestsWithReruns(..., 1)` in the `Promise.all` branch is a bare magic number. A named constant or comment such as `/* no workers */` would read better.
7. **Duplicated runList parsing (nit).** `findTestFiles` in Electron and the node and browser runners each parse the run list separately.
