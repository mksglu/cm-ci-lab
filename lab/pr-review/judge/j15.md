# REVIEW A

**Review of PR #23017: Preserve inline comments when updating an existing dependency group** (already merged)

The fix is correct and narrowly scoped. Formatting and sorting now run only when a key is inserted, so adding to an existing group leaves the comments around the other keys alone. I didn't check out the branch or run the tests; this comes from reading the diff.

**Code quality**
- The `new_group` flag in `add_dependency_group` is clear. The new comment explains why formatting is limited to inserts.
- The early return in the second function (`return Ok(())` when the group exists) replaces a nested `if !group_exists` block. That's simpler and avoids reformatting in the no-op case, which also helps comment preservation.
- The two functions now repeat the "sort if was_sorted, then `fmt()` the inline table" step. A small helper would remove the duplication. This is a nit.
- The old comment claimed that reformatting "can drop comments between keys, but you can't put comments between items in an inline table anyway". That was wrong, and the PR removes it.

**Potential issues**
- **Misleading test snapshot:** the output keeps the comments but has awkward indentation (`dev = [\n    "ok==1.0.0",\n], # Local development`). This comes from the array's own formatting and doesn't affect correctness. Still, the snapshot locks in ugly output. The test doc comment could say that the indentation is expected for now.
- **Missing doc comment:** AGENTS.md asks for a doc comment on non-obvious regression scenarios. This test has none. A one-line comment saying inline-table comments used to be dropped on update would help.
- **Insert path untested:** when a *new* group is inserted into an inline table that has comments, `fmt()` still strips them. The PR deliberately doesn't change that, but a test or a note about it would document the remaining limitation.
- **`dependency-groups` as a regular table:** with a regular `[dependency-groups]` table, `fmt()` doesn't apply, so there is no behavior change. I didn't see a test for it, but it isn't affected by this change.

**Performance and security**
- No concerns. The change only skips some work.

**Test coverage**
- `add_dev_preserves_inline_group_comments` follows the existing style (`uv_snapshot!` plus `assert_snapshot!` on `context.read`). It covers the reported scenario: a trailing comment after `dev` and a standalone comment before `release`.
- It uses `--frozen`, so it needs no network access and probably needs no `test-...` feature gate. I couldn't confirm that.
- The test doesn't cover the early-return path in the second function, `add_dependency_group`. That path is used when adding to a group via `uv add --group`, and the change there is behavior-neutral.
- A second test could cover `uv add --group <existing>` on an inline table.

**Verdict:** Approve. The follow-ups are optional: a regression doc comment on the test, a shared helper for the sort-and-format step, and a test for the insert path.

# REVIEW B

**Review of PR 23017: Preserve inline comments when updating an existing dependency group**

The PR is already merged. The change is small and the intent is sound. I didn't build the code or run the tests.

**What it does**
- It runs `sort_values()` and `fmt()` on the inline `dependency-groups` table only when a new group key is inserted.
- Editing an existing group's array no longer reformats the outer table, so comments on neighbouring keys survive.
- It also flattens the group-creation function with an early return. The behavior is the same, and the code is easier to read.

**Code quality**
- The `new_group` flag is clear, and the new comment explains why the formatting is conditional.
- The early return in the second function (the group-ensure path) removes a nesting level.
- The `sort_values()` and `fmt()` block is now duplicated in two places. A small helper, for example `fn format_inline_groups(&mut self, was_sorted: bool)`, would keep the two paths from drifting apart. This is minor.
- In the first function, `if new_group { if was_sorted {…} if let … }` could use a let chain, as AGENTS.md prefers. The inner `if was_sorted` is separate, so a chain only partly applies. This is a nit.

**Potential issues**
- **Inserted-key formatting:** `sort_values()` reorders existing keys and `fmt()` rewrites the table. Both still run when a new key is inserted, so inline comments between keys are still lost in that case. The old comment said comments can't appear between items in an inline table. That claim is wrong, and the PR's own test shows comments there are legal. The PR drops the claim but doesn't say that the insertion case still loses comments. Worth a follow-up, or at least a note.
- **Snapshot formatting:** The snapshot shows `dev = [\n    "ok==1.0.0",\n], # Local development`. The array's indentation is ugly: the closing `]` sits at a different indent than the keys. This is pre-existing array decor behavior, and the test locks it in. If the formatting is improved later, the snapshot will need updating. That's acceptable, but the test documents suboptimal output.

**Test coverage**
- The test follows the nearby `uv_snapshot!` and `assert_snapshot!` style, and it uses `--frozen` and `context.read`.
- It covers only the existing-group path. It doesn't cover:
  - the insertion path in the second function (adding `--group` to an empty or new inline group), or
  - the `was_sorted` behavior for inline tables.

  Existing tests may cover those. Check that one does.
- The test belongs in `edit.rs`, which is the right module. It was inserted between a doc-commented test and its neighbour, which is fine.
- The test has no doc comment explaining the scenario. AGENTS.md asks for one only for non-obvious regressions, so this is optional.

**Performance and security**
- There are no concerns for either. The change removes some work.

**Verdict:** Looks good. The suggestions are to extract the duplicated format block into a helper, and to make sure the insertion path still has a test.
