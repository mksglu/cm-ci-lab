# REVIEW A

# Review of PR #100935: store `ChunkGroupInfo::chunk_groups` as a `Vec`

This PR is already merged, with approvals from mischnic and sokra. I read the diff only. I didn't build it or run the tests.

## Summary
`ChunkGroupInfo::chunk_groups` changes from `FxIndexSet<ChunkGroup>` to `Vec<ChunkGroup>`. `IndexSet` equality ignores order. If a recompute only renumbers the chunk groups, the new `ChunkGroupInfo` compares equal to the old one, and the cell keeps the old order. Meanwhile `module_chunk_groups` and `chunk_group_indices` use the new numbering. Modules then map to the wrong chunk groups. `Vec` equality is order-sensitive, so the cell is updated and the indices stay consistent.

The diagnosis is sound and the fix is minimal and correct in direction. The doc comment on the field explains the invariant well.

## Code quality
- The `#[bincode(with = "turbo_bincode::indexset")]` attribute is correctly removed, since `Vec` serializes natively.
- The `get_index(idx)` calls become `get(idx)` in `module_batches.rs` and in the test helper. This is a mechanical change that behaves the same.
- The diff doesn't show where the vector is built. I assume it is collected from the `IndexSet` or built alongside it, and I couldn't confirm that from the diff. The key point is that `chunk_group_keys` stays an `FxIndexSet` and is the dedup and index source. `chunk_groups` must remain index-aligned with it, because `chunk_group_indices` and the bitsets rely on that. A short comment or `debug_assert_eq!(chunk_groups.len(), chunk_group_keys.len())` where the info is constructed would protect this invariant.
- `chunk_group_keys` is still an `IndexSet` marked `unsafe_ignore`, so it isn't compared. That seems intentional. It is derived from the same ordering, so a renumbering is caught by `chunk_groups` differing. It would still be worth a comment saying so.
- The PR description says the author is checking other places with the same risk. Other `IndexSet`/`IndexMap` fields inside `#[turbo_tasks::value]` types that are indexed positionally have the same problem. A follow-up grep for `turbo_bincode::indexset` and `indexmap` usages in value types would be useful.

## Potential bugs
- Behavior change on duplicates: `IndexSet` deduplicated `ChunkGroup` values and `Vec` does not. If the build code previously relied on `insert` returning the existing index to dedupe, switching to `push` would introduce duplicates. The diff doesn't show the construction site, so I can't tell. Since `chunk_group_keys` is the real dedupe point, this is probably fine.
- Any remaining lookups by value (`get_index_of`, `contains`) would not compile against `Vec`. The change builds, so none exist. Value lookups on a `Vec` would be O(n), but nothing in the diff does one.

## Performance
- `Vec` equality is O(n) with order-sensitive comparison. `IndexSet` equality is also O(n) with hash lookups, so `Vec` is likely cheaper.
- Fewer cell invalidations are avoided only when the order is genuinely unchanged. When it does change, downstream tasks now correctly recompute, which is the intended trade-off.

## Security
No concerns.

## Test coverage
The new test `test_chunk_group_info_reordered_entries` is a good regression test:
- It builds two entries, each with an async child, and swaps the entry order through `turbo_tasks::State`.
- It then reads with `read_strongly_consistent` and asserts the per-module chunk group descriptions are identical.
