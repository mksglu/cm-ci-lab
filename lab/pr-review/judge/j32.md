# PR #345283: run `--runList` unit tests in parallel workers

## Summary
In CI, the macOS and Windows unit test jobs pass `--workers 4` together with `--runList`, but all three runners ignored `--workers` when given a list, so every selected run was serial. This PR lets `--workers` apply with `--runList` in the Electron, node.js and browser runners. A new function, `getWorkerCountForFiles`, picks the worker count: one per 75 files, at least 2, and never more than `--workers` or the number of files. The PR also moves the Electron test-file discovery into `test/unit/electron/testFiles.ts`, so the main process can count the files before it decides how many workers to start.

Overall the change is small and careful, and it fits the existing worker setup well. I found no correctness bugs. The points below are mostly about wording, measurements and test coverage.

## Correctness: paths I checked
- **Workers don't start their own workers.** Each worker is launched without `--workers`, so it falls back to one process. In Electron, `listedTestFiles` stays `undefined`; in node.js and the browser runner, `workersApply` is false.
- **The "Running the N test files" message prints once.** In Electron the renderer skips it when `opts.workerDir` is set or when `opts.run` is used. In node.js `findTestModules` checks `!args.worker`, and the browser runner checks `!worker`.
- **Electron finds files in the same folder as the renderer.** The main process uses `out` or `out-build` based on `args.build`, which matches `renderer.js:115`.
- **The Electron one-window shortcut is safe.** `firstRunArgs = { ...args, run: files }` only happens when there are 0 or 1 files, because `workersApply` already requires `workerCount > 1`. So the `argv` passed in the window URL stays small. Reruns still build on `args`, not on `firstRunArgs` (`index.js:816`), and coverage is excluded by `workersApply`, so `coverage.createReport(opts.run …)` is never reached here.
- **node.js doesn't search for files twice.** `findTestModules()` caches its promise in `testModules ??=`, so the main process and `main()` share one search. `TEST_GLOB`, `src` and `excludeGlobs` are all module-level constants defined before the bottom-of-file call.
- **Empty lists behave as before.** `getWorkerCountForFiles(n, 0)` returns 1. The browser runner still exits early on 0 modules. Electron runs `run: []`, which matches the old behaviour of loading nothing.
- **Errors are reported cleanly.** The early `listedTestFiles?.catch(() => {})` avoids an unhandled rejection before `ready`, and the error is still reported when the promise is awaited later.
- **CI keeps working.** `scripts/test-integration.sh` selects tests with `--runGlob`, which still turns workers off. All CI browser steps pass a single `--browser`, so running browsers one at a time changes nothing there.

## Suggestions

1. **The `FILES_PER_WORKER` doc comment is misleading** (`test/unit/parallel.ts:~100`). It says "test files per worker … *beyond its first 2 workers*". The formula is really `max(2, floor(n / 75))`: 150 files give 2 workers and 225 give 3. Something like "one worker per 75 listed test files, with a floor of 2" would be accurate.

2. **The "at least 2 workers" floor makes small lists slower in two of the four runners**, according to the PR's own table:
   - node.js, 10 files: 4.2 s → 5.5 s
   - Electron, 10 files: 2.8 s → 5.9 s

   The comment says "a second worker costs about a second", but Electron paid about 3 s here. The PR says those 10-file runs were taken on a loaded machine, so this may be noise. Still, Electron starts a whole new window per worker, so its cost per worker is the highest. Possible follow-ups: confirm on a quiet machine, use a small per-runner threshold before the floor of 2 applies, or at least soften the "about a second" wording. The tail-latency argument (one slow file holding up the rest) is sound, so I wouldn't drop the floor; it just deserves data from a CI agent.

3. **`getWorkerCountForFiles` has no tests.** It's a pure function with clear boundaries, so a small table-driven test would pin down the behaviour the docs promise: `(4, 0) → 1`, `(4, 1) → 1`, `(4, 2) → 2`, `(4, 224) → 2`, `(4, 225) → 3`, `(4, 300) → 4`, `(2, 1000) → 2`, `(1, 50) → 1`. Since `parallel.ts` has no tests yet, this would also be a cheap start for testing the claim and distribution helpers.

4. **The `--runList` parsing is now copied in three places**: `test/unit/node/index.js:73`, `test/unit/browser/index.js` and `test/unit/electron/testFiles.ts`. The duplication predates this PR, but the PR already touches all three files, and these copies must agree for "the same list works for every runner". One helper in `parallel.ts` or `testFiles.ts`, e.g. `readRunList(path): Set<string>` (strip `src/`, map `.ts` to `.js`, normalise `\`), would stop them drifting apart.

5. **The runners still decide whether workers apply in different ways.** node.js and Electron check `workerCount > 1`, while the browser runner checks `args.workers !== undefined`. The browser version is deliberate, so that browsers still run one at a time when the memory or CPU cap leaves 1 worker. A short comment there explaining why it differs would help the next reader, since the three blocks now look almost identical.

6. **The `Using X instead of Y worker processes` message is hard to read.** For a single file it prints "…but at least 2 and at most one per test file". It's correct, but it could say which rule applied, e.g. `Using 1 worker process for 1 test file` against `Using 2 of 4 workers for 40 test files (one per 75, minimum 2)`.

## Performance
- In Electron, the main process searches `out/**/test/**/*.test.js` before the app is ready, and the search overlaps with startup, which is a nice touch. With more than one worker, each worker's renderer searches again; that's unavoidable, since each worker is its own process.

- One Electron result looks odd: on a loaded machine, `--workers 2` took 23.1 s against 30.0 s for `--workers 4`. If that also shows up on CI agents, the per-runner caps may need tuning.

## Security
No concerns. This only changes the local and CI test runners. The list file is read from a path the caller gives, the same as before.

## Docs
The help text for each runner, `test/unit/README.md` and the unit-tests skill are all updated and match each other. The README's "up to 224 files in 2 workers, 300 or more in 4" example matches the formula. It leaves out 225–299 files, which get 3 workers; worth adding for completeness.

   - `count = 1` → 1

   A small test (for example next to the `build/lib/test` tests, or a node `--test` file for `test/unit`) would lock in the documented behaviour. The description admits that PR CI runs everything because `test/unit/**` is in `runEverything`, so CI never exercises the `--runList` path. Cheap tests matter more for that reason.

4. **Electron globs the output folder N+1 times.** The main process now globs `out/**/test/**/*.test.js`, and every worker renderer globs it again. That is cheap next to the test run, so it's fine. Still, consider passing the resolved list to workers, for example as a temp file used as their `--runList`, or through the existing claims directory. That way the parent's count and the workers' file set come from the same snapshot. Today they can only differ if `out` changes mid-run, as under `watch`, which is an edge case.

5. **`workersApply` is defined differently per runner.**
   - Electron and node.js include `workerCount > 1` in it.
   - The browser runner doesn't, on purpose, so that `--workers 1` with several browsers still runs them one at a time.

   A one-line comment at the browser definition would stop someone from "fixing" it later to match.

6. **The Electron single-worker optimisation only covers 0 or 1 files.** `parallelWorkers === 1` happens only then, because `workersApply` already needs `workerCount > 1` and the helper returns at least 2 for 2 or more files. The comment ("instead of finding them again") reads as if it were more general. Saying "a single listed file" would make the scope clear.

7. **Measurements and CI.** The 10-file results for Electron (2.8 s → 5.9 s) and node.js (4.2 s → 5.5 s) show the minimum of 2 workers costs about 1–3 s on short lists of fast tests. The tail-latency argument justifies this, but it is worth checking on the actual 5-core macOS and 8-core Windows agents after merge, as the description already notes. Something to consider: only apply the minimum of 2 above a small threshold, for example 5 or more files. The data shows little gain below that.

## Performance
The effect is positive overall: 300 files take 40–45% less time on every runner. Starting the Electron glob while the app is still launching hides its cost, which is good.

## Security
No concerns. This only changes local and CI test tooling, and it adds no new inputs beyond the existing `--runList` file.
